= Upgrades

[.validation]
NOTE: Validated on ROSA HCP 4.20 and 4.22 and ARO 4.21 in October 2026.
Steps and statements that were not checked on a live cluster carry a *Not validated* note.
The comparison tables and summaries come from vendor documentation.

On EKS you upgrade the control plane, then each add-on against a compatibility matrix, then the nodes.
On ROSA and ARO one release moves Kubernetes, the node OS and every platform Operator together, with checks that block an upgrade when something is not ready.
A real upgrade takes an hour or more, so this section inspects and schedules upgrades without running one.

== How an Upgrade Runs

The timeline shows what you run on each platform, in order, and what happens without you.

.Upgrade steps per platform
image::module-04-upgrade-timeline.svg["Upgrade steps on EKS, AKS, ROSA and ARO, colored by whether you run the step or it runs automatically.",width=100%,link=self,window=_blank]

The chart shows which parts of the platform move in the same update as the Kubernetes control plane, and which you update separately.

.What moves together
image::module-04-what-moves-together.svg["Matrix of platform components against EKS, AKS, ROSA and ARO, showing which components move with the control plane.",width=100%,link=self,window=_blank]

On ROSA and ARO, the CNI, DNS, ingress, storage drivers and monitoring are platform Operators.
They are tested together as one OpenShift release, so there is no compatibility matrix to check.
The difference between the two is the nodes: ROSA updates each machine pool separately, while standard ARO rolls the workers as part of the cluster update.

Operators you add from the Software Catalog (GitOps, Logging, OADP) support their own OpenShift version ranges; check the https://access.redhat.com/support/policy/updates/openshift_operators[Red Hat Operator life cycle] page and update them before a minor update.

== On EKS and AKS

* EKS: upgrade the control plane one minor version at a time, update add-ons, then roll node groups or let Auto Mode replace nodes.
Each version gets 14 months of standard support, then 12 months of extended support, which is on by default and costs more per hour.
EKS can roll the control plane back one minor version within 7 days.
* AKS: auto-upgrade channels and planned maintenance windows automate the control plane and node images.
Each version is supported for one year, and AKS long-term support keeps it for two years.

== On ROSA and ARO

Run each exercise in your cluster's terminal unless it says otherwise.
Where the steps differ, they appear in a *ROSA (AWS)* tab and an *ARO (Azure)* tab.

=== Exercise 1: See Where the Cluster Stands

Show the cluster's version, update channel and available updates:

[source,bash]
----
oc adm upgrade
----

Ask the cluster for its recommendation, including any known risks of the available updates:

[source,bash]
----
oc adm upgrade recommend
----

A new cluster can report `Upgradeable=False` with the reason `AdminAckRequired`.
That is an acknowledgment gate, covered in Exercise 4, and it blocks only the next minor version.
An ARO cluster created with managed identities reports `MultipleReasons` instead, because the `cloud-credential` Operator also blocks the next minor version until you prepare it, as Exercise 4 shows.

The update channel decides which versions are offered.
Patch releases arrive in the current channel, and a new minor version needs a channel change, which you make, apart from the exceptions in <<upgrades-without-you,When the platform upgrades without you>>.

[tabs]
======
ROSA (AWS)::
+
--
On ROSA the channel and the list of updates come from OpenShift Cluster Manager.
Show the cluster's channel and version:

[source,bash]
----
rosa describe cluster \
  --cluster "$CLUSTER"
----

List the versions you can upgrade the control plane to:

[source,bash]
----
rosa list upgrades \
  --cluster "$CLUSTER"
----

Machine pools carry their own version.
The `VERSION` column shows each pool's version, which can trail the control plane by up to two minor versions: a 4.22 control plane accepts a new 4.20 pool and refuses a 4.19 one.

[source,bash]
----
rosa list machinepools \
  --cluster "$CLUSTER"
----

You would change the channel with `rosa edit cluster` and its `--channel` flag, not with `oc`.
--
ARO (Azure)::
+
--
On ARO the channel is a field of the cluster's ClusterVersion, and it is not set by default.

If `oc adm upgrade` reported no channel, set it to the stable channel of the cluster's minor version, for example:

[source,bash]
----
oc adm upgrade channel stable-4.21
----

It warns that no channels are known to be compatible with the current version and sets the channel anyway: the cluster has not fetched the channel list yet.
Run `oc adm upgrade` again a minute later, and it lists the available channels and the recommended updates.
Setting the channel does not start an update.
ARO supports only the `stable`, `fast` and `eus` channels.
--

=== Exercise 2: Read the Update History

ClusterVersion keeps every update the cluster has taken, with its start and end time:

[source,bash]
----
oc get clusterversion version --output json \
  | jq -r '.status.history[]
      | [.version, .state, .startedTime, .completionTime]
      | @tsv'
----

The newest update is first, and a new cluster can list its install version more than once.
`Completed` means every Operator reached the new version, and `Partial` means the update did not finish.

Show the conditions the Cluster Version Operator reports:

[source,bash]
----
oc get clusterversion version --output json \
  | jq -r '.status.conditions[]
      | [.type, .status, .reason // ""]
      | @tsv'
----

`Progressing` is `True` while an update runs.
An `Upgradeable` condition appears, set to `False`, only when something blocks the next minor update.

=== Exercise 3: Schedule an Upgrade, Then Cancel It (ROSA Only)

[.validation]
NOTE: *Not validated:* the `UpgradeConfig` example, which was not created.
The ROSA steps were validated on a ROSA 4.22 cluster one patch release behind, including a recurring `--schedule`, and on a machine pool one patch release behind, where `rosa upgrade machinepool` without a schedule replaced the pool's node with one on the new version.

On ROSA you schedule upgrades with the `rosa` CLI or OpenShift Cluster Manager, and Red Hat runs them.
You schedule one here and cancel it before it starts.
If your cluster is ARO, read it without running it; the ARO way to start an update follows at the end.

If `rosa list upgrades` showed no available version, read through this exercise without running it.

Pick the first version in the list:

[source,bash]
----
TARGET=$(rosa list upgrades \
  --cluster "$CLUSTER" \
  | awk 'NR==2 {print $1}')
----

[source,bash]
----
echo "$TARGET"
----

Choose a date a week from now, in UTC.
On Linux:

[source,bash]
----
WHEN=$(date -u -d '+7 days' +%Y-%m-%d)
----

On macOS:

[source,bash]
----
WHEN=$(date -u -v+7d +%Y-%m-%d)
----

Schedule the control plane upgrade:

[source,bash]
----
rosa upgrade cluster \
  --cluster "$CLUSTER" \
  --version "$TARGET" \
  --schedule-date "$WHEN" \
  --schedule-time 03:00
----

If the CLI offers to upgrade account or operator roles, decline: that is needed only for a minor version, and you are cancelling anyway.
It also suggests running the command with `--dry-run` to check and acknowledge gates; a patch release has none to acknowledge.

Show the scheduled upgrade:

[source,bash]
----
rosa describe upgrade \
  --cluster "$CLUSTER"
----

Cancel it:

[source,bash]
----
rosa delete upgrade \
  --cluster "$CLUSTER"
----

Check that nothing is scheduled:

[source,bash]
----
rosa describe upgrade \
  --cluster "$CLUSTER"
----

For a real upgrade you would then upgrade each machine pool, after the control plane finishes:

[source,bash]
----
rosa upgrade machinepool \
  --cluster "$CLUSTER" \
  --version "$TARGET" \
  <machinepool-name>
----

Nodes created by the Red Hat build of Karpenter from the `default` node class follow the control plane version without this step.
ROSA can also apply patch releases automatically on a recurring schedule, with the `--schedule` flag and a cron expression.

.On ARO, for comparison (do not apply)
[%collapsible]
====
On standard ARO you start the update yourself, with the console, `oc adm upgrade --to`, or an `UpgradeConfig` for the managed upgrade operator, which waits for a time you set.

WARNING: Do not create this `UpgradeConfig` on your ARO cluster in this workshop: it would start a real update at that time.

[source,yaml]
----
apiVersion: upgrade.managed.openshift.io/v1alpha1
kind: UpgradeConfig
metadata:
  name: managed-upgrade-config
  namespace: openshift-managed-upgrade-operator
spec:
  type: "ARO"
  upgradeAt: "2026-11-01T03:00:00Z"
  PDBForceDrainTimeout: 60
  desired:
    channel: "stable-4.21"
    version: "<target-version>"
----
====

If Terraform or Bicep describes your clusters, read xref:module-04-scaling-nodes.adoc#nodes-as-code[node pools as code] in Scaling Nodes first, which says which tool owns the version and the node pools on each platform.

.EKS and AKS (reference only)
[%collapsible]
====
EKS upgrades start when you run them, with no scheduler:

[source,bash]
----
aws eks update-cluster-version \
  --name my-cluster \
  --kubernetes-version 1.34
----

The exception: a control plane left past the end of extended support (or the end of standard support, if extended support is off) is upgraded automatically, and add-ons and nodes are not.

Each add-on and node group follows, one command each:

[source,bash]
----
aws eks update-addon \
  --cluster-name my-cluster \
  --addon-name vpc-cni \
  --addon-version <version>
----

AKS, opt in to automatic patch upgrades inside a maintenance window:

[source,bash]
----
az aks update \
  --resource-group my-rg \
  --name my-cluster \
  --auto-upgrade-channel patch
----

[source,bash]
----
az aks maintenanceconfiguration add \
  --resource-group my-rg \
  --cluster-name my-cluster \
  --name aksManagedAutoUpgradeSchedule \
  --schedule-type Weekly \
  --day-of-week Sunday \
  --interval-weeks 1 \
  --start-time 03:00 \
  --duration 4
----

=== Exercise 4: Find What Would Block an Upgrade

==== Operators

A platform Operator that cannot move to the next minor version marks itself `Upgradeable=False`.
List any that do:

[source,bash]
----
oc get clusteroperators --output json \
  | jq -r '.items[]
      | select(any(.status.conditions[];
          .type == "Upgradeable"
          and .status == "False"))
      | .metadata.name'
----

No output means no Operator blocks a minor update.
If `operator-lifecycle-manager` appears, an installed catalog Operator declares a maximum OpenShift version; update that Operator first.
On an ARO cluster created with managed identities, `cloud-credential` appears, with the reason `MissingUpgradeableAnnotation`.
Its credentials are managed outside the cluster, so before you update it you set the `upgradeable-to` annotation on the cluster's CloudCredential resource with `az aro update --upgradeable-to <version>`, as https://learn.microsoft.com/azure/openshift/howto-upgrade-aro-openshift-cluster[Microsoft's update guide for managed-identity clusters] describes.
That command does not start the update.

Some minor updates also need an administrator's acknowledgment, for example of an API removal.
The platform lists these gates in one ConfigMap:

[source,bash]
----
oc get configmap admin-gates \
  --namespace openshift-config-managed \
  --output json \
  | jq '.data'
----

Your acknowledgments go in another, which prints `null` until you acknowledge a gate:

[source,bash]
----
oc get configmap admin-acks \
  --namespace openshift-config \
  --output json \
  | jq '.data'
----

A gate that is listed in `admin-gates` and not acknowledged in `admin-acks` blocks the next minor update, even when no Operator does.
`oc adm upgrade` reports it as `Upgradeable=False` with the reason `AdminAckRequired`.
On ARO 4.21, for example, a new cluster lists a gate about boot image management, which OpenShift 4.22 turns on for Azure clusters.

==== Removed APIs

OpenShift counts the requests to every API, and flags the APIs that a future Kubernetes version removes.
List the ones still in use, with the release that removes them:

[source,bash]
----
oc get apirequestcounts --output json \
  | jq -r '.items[]
      | select(.status.removedInRelease != null)
      | [.status.removedInRelease, .metadata.name]
      | @tsv'
----

The list is often empty, and that is a real answer.
OpenShift flags only the APIs it has scheduled for removal in a coming release, and on 4.20, 4.21 and 4.22 every API scheduled so far has already been removed.
An empty list means nothing on the cluster calls an API that is about to disappear; it fills in when a future release schedules more removals.

[.validation]
NOTE: *Not validated:* a non-empty result. The command returned nothing on every validation cluster, as expected on 4.20, 4.21 and 4.22.

To see who calls one of them, look at its users, for example:

[source,bash]
----
oc get apirequestcount <resource>.<version>.<group> \
  --output json \
  | jq -r '.status.last24h[]?.byNode[]?.byUser[]?
      | [.username, .userAgent]
      | @tsv' \
  | sort -u
----

Request counts show only what has already called an API, so a workload that runs rarely, or is not deployed yet, does not appear.
Also check your manifests and Helm charts against the https://kubernetes.io/docs/reference/using-api/deprecation-guide/[Kubernetes deprecated API migration guide].

==== Pod disruption budgets

Every node drains during an update: ROSA replaces each machine pool node with a new one, and ARO reboots nodes in place.
A PodDisruptionBudget that allows no disruptions stops the drain.
Create one for the sample application that does exactly that:

[source,bash]
----
oc apply --filename - <<'EOF'
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: sample-app
  namespace: sample-app
spec:
  minAvailable: 100%
  selector:
    matchLabels:
      app.kubernetes.io/name: sample-app
EOF
----

Find every budget in the cluster that currently allows no disruptions:

[source,bash]
----
oc get poddisruptionbudgets \
  --all-namespaces \
  --output json \
  | jq -r '.items[]
      | select(.status.disruptionsAllowed == 0)
      | .metadata.namespace + "/" + .metadata.name'
----

The sample application's budget is in the list.
Budgets in `openshift-*` namespaces, such as `packageserver-pdb`, can appear too; those belong to the platform and Red Hat manages them.

[.validation]
NOTE: *Not validated:* the ROSA, EKS and AKS drain behavior below, which comes from the vendors' documentation.
The ARO behavior was validated with a patch update from 4.21.22 to 4.21.36 started with `oc adm upgrade --to`.

What happens next depends on the platform:

* ROSA waits on the budget with no time limit, unless the machine pool has a node drain grace period.
After that period it evicts the remaining pods and replaces the node.
* Standard ARO waits on the node until the budget allows the eviction, so the update stalls on that node.
The node stays cordoned, and the Machine Config Operator retries the eviction every few seconds; after 10 minutes it retries every 5 minutes and records a `DrainThresholdExceeded` warning event on the node.
The ClusterVersion can already report the update `Completed` while this happens, because it tracks the Operators, not the nodes, so watch `oc get machineconfigpools` for the nodes.
With an `UpgradeConfig`, the managed upgrade operator forces the drain after `PDBForceDrainTimeout` minutes.
* EKS managed node group updates fail with a pod eviction error unless you force them.
* AKS upgrades fail on a node that cannot drain, unless you set the undrainable node behavior to cordon it and move on.

On ROSA, check the pool's node drain grace period and its `Management upgrade` settings.
By default the grace period is empty, which means no time limit, and nodes are replaced one extra node at a time (max surge 1, max unavailable 0):

[source,bash]
----
rosa describe machinepool \
  --cluster "$CLUSTER" \
  --machinepool <machinepool-name>
----

To have ROSA evict pods that a budget still protects after an hour, you would set a grace period on the pool.
The command then asks whether to turn on autoscaling and how many replicas to keep; answer with the pool's current settings, or pass them with `--enable-autoscaling` and `--replicas` or `--min-replicas` and `--max-replicas`:

[source,bash]
----
rosa edit machinepool \
  --cluster "$CLUSTER" \
  --node-drain-grace-period "1 hour" \
  <machinepool-name>
----

Replace the budget with one that lets one pod go at a time:

[source,bash]
----
oc patch poddisruptionbudget sample-app \
  --namespace sample-app \
  --type json \
  --patch '[{"op":"remove","path":"/spec/minAvailable"},
    {"op":"add","path":"/spec/maxUnavailable","value":1}]'
----

Its allowed disruptions are now 1:

[source,bash]
----
oc get poddisruptionbudget sample-app \
  --namespace sample-app
----

With a single replica, that eviction still means downtime during a drain, so run at least two (see App Teams Will Notice).

=== Where Upgrade Notices Arrive

[.validation]
NOTE: *Not validated:* these notification paths, which come from the vendors' documentation.

Set these up before you need them.

* ROSA: notices about scheduled, started, and completed upgrades, and about critical patches Red Hat applies, appear in the cluster's *Cluster history* in the Red Hat Hybrid Cloud Console.
Only the cluster owner receives them by email by default, so add your team as notification contacts.
Each contact must be a Red Hat account in the cluster owner's organization, so to reach a team mailbox, give it a Red Hat account of its own.
Act on the notices that ask for action, such as upgrading off an unsupported version: Red Hat may delete a cluster within 15 days if they are not addressed, even with delete protection on.
* ARO: Microsoft announces new versions in the ARO release notes.
In extreme cases you get 72 hours to apply a critical security patch, after which ARO SRE may apply it and notify you.
* Both: Red Hat SRE watches the cluster during an update, and the console shows its progress under *Administration* > *Cluster Settings*.

== What Matters

* Cluster upgrades are on the shared row of Module 1's xref:module-01-who-manages-what.adoc#_the_responsibility_line[responsibility line]: you choose the version and the time, the service carries out the update, and on ROSA you also move each machine pool.
* ROSA upgrades the control plane and each machine pool separately.
Machine pools can trail the control plane by up to two minor versions, so you choose when nodes are replaced.
Each replacement adds a new node before removing an old one, so the pool needs room in your EC2 quota and subnet.
* Standard ARO upgrades the control plane and workers together, and you start every update yourself.
* ARO patch releases ship about weekly, and nodes get OS fixes only through them.
Set a regular patch rhythm, for example an `UpgradeConfig` for each update that starts it in your maintenance window.
* A new minor version needs a channel change and sometimes an administrator acknowledgment.
* *How long a version lasts:* ROSA supports each minor version for about 18 months after general availability.
Even minor versions from 4.16 extend to 24 months with the Extended Update Support add-on, which the subscription includes, once you move the cluster to the `eus` channel group with `rosa edit cluster` and its `--channel-group` flag.
* ARO ends each minor version about 18 months after OpenShift's general availability, on the date in the ARO release calendar, and a cluster past that date drops to Limited Support, with no SLA.
Even minor versions from 4.16 extend to 24 months with Extended Update Support Term 1, which the subscription includes, on an `eus-4.y` channel.
* [[upgrades-without-you]]*When the platform upgrades without you:* on both services, Red Hat may apply a critical security fix, on ROSA to the control plane after two business days' notice, and on ARO after a 72-hour notice.
ROSA also upgrades clusters off a patch release that Red Hat deprecates, within 48 hours.
On ROSA, a control plane past its end of life is moved to the next supported minor version; EKS does the same at the end of extended support.
From June 1, 2027, AKS will upgrade clusters on an expired version too, after a 60-day grace period, ignoring maintenance windows and able to override PodDisruptionBudgets.
Otherwise a minor version never moves on its own.
* Existing ARO clusters can update to a new minor version once an update path reaches the fast channel.
New clusters can be installed on that version about six months after OpenShift's general availability, while ROSA offers it within a day of the release.
So if your ARO cluster already runs a minor version that new clusters can't install yet, a cluster you rebuild starts on an older minor version and needs an update before it matches.
* Standard ARO has no control-plane-only update, so an EUS-to-EUS update such as 4.20 to 4.22 takes every node through 4.21 as well.
On ROSA, machine pools can stay up to two minor versions behind while the control plane moves.
* OpenShift does not support rolling back an upgrade.
Test updates on a non-production cluster first.

== Where Each Wins

[cols="1,1",options="header"]
|===
|ROSA and ARO win |EKS and AKS win

|Platform components upgrade together in one tested release.
|Newer Kubernetes versions sooner.

|Upgrade-blocking checks and API usage counts catch problems before they start.
|AKS maintenance windows and auto-upgrade channels.

|Extended Update Support to 24 months on even minor versions, included in the ROSA and ARO subscriptions.
|AKS long-term support for two years.

|SRE watches the upgrade.
|EKS can roll the control plane back one minor version within 7 days.

|ROSA schedules and runs upgrades for you, and lets nodes trail the control plane.
|EKS upgrade insights and AKS also flag deprecated API use before an upgrade.
|===

== App Teams Will Notice

* Every node drains during an update, and ROSA replaces it while ARO reboots it, so every pod restarts at least once.
Applications need at least two replicas and a budget that allows one disruption to stay up.
* A budget that allows no disruptions holds up the update on both, unless a ROSA machine pool has a node drain grace period.
* Each Kubernetes minor version removes some deprecated APIs.
Manifests and Helm charts that use them fail after the update, and the API request counts show who still calls them.
