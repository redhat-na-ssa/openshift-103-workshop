= Who Manages What

NOTE: Validated on ROSA HCP 4.20 and 4.21 and ARO 4.21 in October 2026.
Steps and statements that were not checked on a live cluster carry a *Not validated* note.
The comparison tables and summaries come from vendor documentation.

On EKS and AKS, the cloud provider runs the control plane and you run almost everything else.
On ROSA and ARO, Red Hat site reliability engineers (SRE) and the cloud provider also run the worker operating system and the platform components, and some settings you are used to changing are no longer yours.
This section draws that line for all four platforms, and covers support, cost and backup, because they follow from the same line.

== On EKS and AKS

* AWS or Microsoft runs the API server and etcd.
* You choose, install and update the add-ons: CNI, CSI drivers, load balancer controller, metrics-server, autoscaler.
* You patch or replace nodes, or hand that to EKS Auto Mode or AKS node OS auto-upgrade.
* You open support cases with AWS or Microsoft, and with each vendor whose add-on you run.

.EKS and AKS (reference only)
[%collapsible]
====
On EKS, the node group's AMI release is yours to move forward:

[source,bash]
----
aws eks describe-nodegroup \
  --cluster-name <cluster-name> \
  --nodegroup-name <nodegroup-name> \
  --query nodegroup.releaseVersion
----

On AKS, the tier and the upgrade channels show what Microsoft does for you:

[source,bash]
----
az aks show \
  --resource-group <resource-group> \
  --name <cluster-name> \
  --query "{tier: sku.tier, upgrades: autoUpgradeProfile}"
----
====

== Where Each Platform Runs

The diagram shows where the control plane and the nodes of each platform run, and who operates them.

image::module-01-architecture.svg[Where the control plane and nodes run on EKS, AKS, ROSA and ARO]

Two things stand out:

* On ROSA, the control plane runs in a Red Hat-owned AWS account, like EKS runs it in an AWS-owned one. Your account holds only the worker nodes, reached over AWS PrivateLink. This architecture is called ROSA with hosted control planes (HCP), and it is the one this workshop uses.
* On ARO, the control plane and worker VMs run in your subscription, but in a managed resource group that a deny assignment locks against changes, even by subscription owners.

ARO also offers hosted control planes, in preview.
This workshop uses standard ARO.

== The Responsibility Line

image::module-01-responsibility.svg[Who is responsible for each area on EKS, AKS, ROSA and ARO]

Read the chart by row:

* *Control plane and etcd*: always someone else's job. On ROSA and ARO, Red Hat SRE is part of that team.
* *Node operating system and platform components*: this is the real difference. On EKS, AWS publishes patched AMIs and add-on versions, and you roll each of them out. On AKS, the default node OS channel applies Microsoft's node images for you. On ROSA and ARO, Red Hat ships the worker OS (Red Hat Enterprise Linux CoreOS) and every platform Operator in the OpenShift release, so there is no node image to track, and SRE monitors and repairs them. On ARO they all move in one cluster update. On ROSA the platform Operators move with the control plane, and the worker OS moves only when you upgrade each machine pool.
* *Cluster upgrades*: shared everywhere. On ROSA you schedule upgrades, or opt into automatic patch upgrades, and SRE monitors them; the control plane and each machine pool upgrade separately, control plane first. On ARO you start the upgrade yourself, and it updates the whole cluster at once. Neither service upgrades your cluster without you, except for a critical security fix and, on ROSA, a control plane past its end of life (see xref:module-04-upgrades.adoc#upgrades-without-you[When the platform upgrades without you]). Module 4 covers both.
* *Node capacity, identity, backup and workloads*: yours on every platform.

The cells are simplified.
The responsibility matrices in the references list each task in detail.

=== Before You Start

Open two terminals, one for each cluster, and log in to each as the cluster administrator.
Every exercise in the workshop runs in these terminals and uses the variables you set here.
If you open a new terminal later, run only the `export` steps in it: the kubeconfig file keeps your login.

[tabs]
======
ROSA (AWS)::
+
--
Give this terminal its own kubeconfig file:

[source,bash]
----
export KUBECONFIG=~/.kube/rosa
----

Set the cluster name:

[source,bash]
----
export CLUSTER=<rosa-cluster-name>
----

NOTE: *Not validated:* `rosa create admin`, which needs the `rosa` CLI logged in to the cluster's organization.
Logging in with the credentials it prints was validated.

Create a temporary cluster administrator:

[source,bash]
----
rosa create admin \
  --cluster "$CLUSTER"
----

The command prints an `oc login` command with a generated password.
Wait about a minute, then run that command.
If it says the cluster already has a `cluster-admin` user, your facilitator created it: run the `oc login` command they gave you instead.
--
ARO (Azure)::
+
--
Give this terminal its own kubeconfig file:

[source,bash]
----
export KUBECONFIG=~/.kube/aro
----

Set the cluster name and resource group:

[source,bash]
----
export CLUSTER=<aro-cluster-name>
export RESOURCE_GROUP=<resource-group>
----

Look up the API server URL:

[source,bash]
----
API_URL=$(az aro show \
  --name "$CLUSTER" \
  --resource-group "$RESOURCE_GROUP" \
  --query apiserverProfile.url \
  --output tsv)
----

Look up the kubeadmin password:

[source,bash]
----
KUBEADMIN_PASSWORD=$(az aro list-credentials \
  --name "$CLUSTER" \
  --resource-group "$RESOURCE_GROUP" \
  --query kubeadminPassword \
  --output tsv)
----

Log in:

[source,bash]
----
oc login "$API_URL" \
  --username kubeadmin \
  --password "$KUBEADMIN_PASSWORD"
----
--
======

Check who you are, in each terminal:

[source,bash]
----
oc whoami
----

ROSA shows `cluster-admin` and ARO shows `kube:admin`.
Module 2 replaces these shared logins with people's own.

=== Exercise 1: Identify the Architecture

[tabs]
======
ROSA (AWS)::
+
--
Describe the cluster, keeping only its control plane type and version:

[source,bash]
----
rosa describe cluster \
  --cluster "$CLUSTER" \
  --output json \
  | jq '{hcp: .hypershift.enabled, version: .version.raw_id}'
----

`hcp` is `true`, because the control plane runs in Red Hat's account.
--
ARO (Azure)::
+
--
Show the cluster profile:

[source,bash]
----
az aro show \
  --resource-group "$RESOURCE_GROUP" \
  --name "$CLUSTER" \
  --query clusterProfile
----

The `resourceGroupId` field is the managed resource group that holds the cluster's VMs.
--
======


You can read the same fact from inside the cluster, without cloud credentials.
The Infrastructure resource records where the control plane runs:

[source,bash]
----
oc get infrastructure cluster \
  -o jsonpath='{.status.controlPlaneTopology}{"\n"}'
----

ROSA shows `External`, because the control plane runs outside the cluster.
ARO shows `HighlyAvailable`: three control plane nodes in your own subscription.

List the nodes on each cluster:

[source,bash]
----
oc get nodes
----

The ROSA cluster shows only worker nodes, because its control plane is not in your account.
The ARO cluster also shows three control plane nodes with the `master` role.
On EKS and AKS, like on ROSA, you never see the control plane as nodes.

[#ex-module-01-who-manages-what-2]
=== Exercise 2: See How the Service Reaches Your Account

[tabs]
======
ROSA (AWS)::
+
--
Red Hat acts in your AWS account only through IAM roles you created when you set up ROSA.
List the account-wide roles:

[source,bash]
----
rosa list account-roles
----

The `Support` role is the one Red Hat SRE assumes to troubleshoot your cluster's AWS resources.
The `Installer` and `Worker` roles create the cluster and run its nodes.
The cluster's operator roles, shown by `rosa describe cluster`, give individual platform Operators, such as the ingress and storage Operators, just the AWS permissions they need.
--
ARO (Azure)::
+
--
The cluster's resources live in the managed resource group shown in Exercise 1.
Save its ID:

[source,bash]
----
MANAGED_RG=$(az aro show \
  --resource-group "$RESOURCE_GROUP" \
  --name "$CLUSTER" \
  --query clusterProfile.resourceGroupId \
  --output tsv)
----

List what is in it:

[source,bash]
----
az resource list \
  --resource-group "${MANAGED_RG##*/}" \
  --query "[].{name: name, resourceType: type}" \
  --output table
----

You can read these resources, but not change them.
The deny assignment on the resource group enforces this.
Build the Azure Resource Manager URL that lists it:

[source,bash]
----
DENY_URL="https://management.azure.com${MANAGED_RG}"
----

[source,bash]
----
DENY_URL+="/providers/Microsoft.Authorization/denyAssignments"
----

[source,bash]
----
DENY_URL+="?api-version=2022-04-01"
----

Read the deny assignment's name and the principals it exempts:

[source,bash]
----
az rest \
  --method get \
  --url "$DENY_URL" \
  --query "value[].properties.denyAssignmentName"
----

[source,bash]
----
az rest \
  --method get \
  --url "$DENY_URL" \
  --query "value[].properties.excludePrincipals[].id"
----

The deny assignment blocks every write by everyone else, including subscription owners.
Only the exempt principals, such as the ARO resource provider, may change the resources.
--
======

[#ex-module-01-who-manages-what-3]
=== Exercise 3: Find What SRE Owns in the Cluster

Platform namespaces start with `openshift-`.
Count them:

[source,bash]
----
oc get namespaces \
  --no-headers \
  | grep -c '^openshift-'
----

On ROSA, look for the managed-service namespaces that do not exist on a self-managed OpenShift cluster:

[source,bash]
----
oc get namespaces \
  --no-headers \
  | grep backplane
----

These namespaces hold the role bindings that give SRE and Red Hat support teams access to the cluster through backplane, Red Hat's support access path.
On ROSA they hold almost no pods: the SRE agents that monitor the cluster and apply managed configuration run with the hosted control plane in Red Hat's account.
What runs on your nodes is the connection back to that control plane, the `konnectivity-agent` pods:

[source,bash]
----
oc get pods \
  --namespace kube-system
----

On ROSA, the managed service also installs validating admission webhooks.
They stop even cluster administrators from changing resources SRE owns, such as the ClusterVersion, the machine API and the cluster autoscaler.
Their names start with `sre-`:

[source,bash]
----
oc get validatingwebhookconfigurations \
  | grep '^sre-'
----

On ROSA the webhook server itself also runs in the hosted control plane, so you see its configuration but not its pods.

=== Exercise 4: Try to Change a Managed Resource

Try to add a label to the ClusterVersion, the resource that controls upgrades.
The `--dry-run=server` flag sends the request through admission control without saving it, so nothing changes even if the request is accepted:

[source,bash]
----
oc label clusterversion version \
  workshop=test \
  --dry-run=server
----

On ROSA, a managed webhook refuses the request, even though you are a cluster administrator.
On ROSA you change upgrade settings through the `rosa` CLI or OpenShift Cluster Manager, never through the ClusterVersion.

On ARO, the request is accepted.
ARO protects its platform through the deny assignment on the Azure side and its support policy, rather than through admission webhooks, and you start upgrades in the cluster yourself.

On both, changes the service does not support can take the cluster out of support.
ROSA calls this _limited support_: SRE stops proactive monitoring and the SLA no longer applies until the cause is fixed.

NOTE: *Not validated:* the `Limited Support` section, because the workshop's ROSA cluster was not in limited support.

If your ROSA cluster is in limited support, `rosa describe cluster` shows a `Limited Support` section with the reasons.

=== Exercise 5: Know Your Support Path

[cols="1,2,2",options="header"]
|===
| |ROSA |ARO

|Where you open a case
|The Red Hat Customer Portal, or AWS Support
|The Azure portal, or the Red Hat Customer Portal

|Who answers
|Either side; the case is routed to Red Hat or AWS, and Red Hat can open AWS cases for you
|Microsoft and Red Hat support engineers together

|What you need
|An AWS support plan that includes technical support cases, to open ROSA cases with AWS. Red Hat support is included
|An Azure support plan to open cases with Microsoft, and the Red Hat pull secret on the cluster to open them with Red Hat
|===

When an EKS or AKS add-on from another vendor fails, you open a second case with that vendor.
On ROSA and ARO, the platform components are part of the service, so one case covers them.

== What Matters

* On ROSA, the control plane runs in a Red Hat account and is reached over AWS PrivateLink, like EKS. On ARO it runs in your subscription, locked by a deny assignment.
* Some cluster settings are SRE-owned. Changes to them are refused or reverted, so automation that worked on EKS or AKS may fail here. Test cluster-wide automation against a ROSA or ARO cluster before rolling it out.
* Application backup is yours on every platform. SRE backs up etcd for its own disaster recovery, not for restores you request, and never your volumes.

=== Backup and Restore

AWS Backup supports EKS, and Azure Backup supports AKS, as managed services with backup policies and vaults.
Neither covers ROSA or ARO.
On ROSA and ARO you install the OpenShift API for Data Protection (OADP) Operator, which is based on Velero, and point it at an S3 bucket or Azure storage account.

[cols="1,2,2,2",options="header"]
|===
| |AWS Backup for EKS |Azure Backup for AKS |OADP on ROSA and ARO

|Delivered as
|A managed AWS service
|A managed Azure service, with a backup extension in the cluster
|An Operator you install from the Software Catalog

|What runs in the cluster
|Nothing
|The backup extension
|Velero and its plugins, and optionally a node agent for file-level volume backup

|What it backs up
|Cluster configuration, Kubernetes resources, and EBS, EFS and S3 volumes
|Kubernetes resources and Azure Disk volumes
|Kubernetes resources, and volumes through CSI snapshots or the node agent

|Policies and storage
|Backup plans and vaults, with cross-Region copy
|Backup policies and vaults
|Schedules you define, in a bucket or storage account you own
|===

OADP is configured with one DataProtectionApplication resource.
These samples show its shape on each cloud; this workshop does not run them.

NOTE: *Not validated:* the two OADP samples below, which were not applied to a cluster.

.Sample OADP configuration for ROSA
[%collapsible]
====
On ROSA the `cloud-credentials` secret holds an IAM role ARN rather than access keys, the same pattern Module 2 uses for application pods.

[source,yaml]
----
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa
  namespace: openshift-adp
spec:
  configuration:
    velero:
      defaultPlugins:
        - openshift
        - aws
  backupLocations:
    - velero:
        provider: aws
        default: true
        objectStorage:
          bucket: <bucket-name>
          prefix: velero
        config:
          region: <region>
        credential:
          name: cloud-credentials
          key: credentials
  snapshotLocations:
    - velero:
        provider: aws
        config:
          region: <region>
        credential:
          name: cloud-credentials
          key: credentials
----
====

.Sample OADP configuration for ARO
[%collapsible]
====
[source,yaml]
----
apiVersion: oadp.openshift.io/v1alpha1
kind: DataProtectionApplication
metadata:
  name: dpa
  namespace: openshift-adp

    velero:

        - openshift

=== Cost and Support

Each platform bills a different mix of the same parts.
Prices change often, so this section compares what you pay for, not how much.
The pricing pages in the references have current numbers.

[cols="3,1,1,1,1",options="header"]
|===
|What you pay for |EKS |AKS |ROSA |ARO

|A control plane fee per cluster
|Yes
|Yes
|Yes
|No

|Control plane VMs in your subscription
|No
|No
|No
|Yes, three

|An OpenShift fee per worker vCPU
|No
|No
|Yes
|Yes

|Worker compute, storage and networking
|Yes
|Yes
|Yes
|Yes
|===

* The AKS column is a paid tier. The free tier has no uptime SLA, so it is not a fair comparison for production.
* Worker compute costs about the same on every platform. The OpenShift fee grows with every worker vCPU, so on larger clusters it outweighs the control plane fee, and commitments on that fee matter more than anything else on the bill.
* ROSA and ARO both carry a financially backed SLA and joint support: one case reaches both the cloud provider and Red Hat.

== Where Each Wins

[cols="1,1",options="header"]
|===
|ROSA and ARO win |EKS and AKS win

|SRE monitors and repairs the node OS and platform components around the clock, and watches the upgrades you start or schedule.
|Full control: any add-on, any version, any configuration.

|One support case covers the cloud and the platform.
|Lower platform cost, with no per-vCPU OpenShift fee.

|A tested, integrated stack instead of an add-on matrix you maintain.
|Managed backup services with policies and vaults.

|
|One vendor and one support channel for the whole stack.
|===

== App Teams Will Notice

* Cluster upgrades and SRE maintenance happen on a schedule your platform team agrees with SRE. App teams should expect rolling node restarts during those windows, and use PodDisruptionBudgets and multiple replicas, as on EKS and AKS.
* Backups of application data are still the platform or app team's job. Agree who owns OADP schedules before the first restore request.
