= What Ships and How You Extend It

[.validation]
NOTE: Validated on ROSA HCP 4.20 and 4.22 and ARO 4.21 in October 2026.
Steps and statements that were not checked on a live cluster carry a *Not validated* note.
The comparison tables and summaries come from vendor documentation.

A new EKS cluster comes with a CNI, kube-proxy and CoreDNS, and you add the rest.
A new ROSA or ARO cluster comes with dozens of platform components, each run by an Operator, tested together and upgraded with the cluster.
This section tours what ships, then shows how you add more through the Software Catalog (formerly OperatorHub), using OpenShift GitOps as the example.

== On EKS and AKS

* EKS: you install add-ons such as the EBS CSI driver, the AWS Load Balancer Controller and metrics-server, and keep their versions compatible with the cluster. EKS Auto Mode takes several of these over.
* AKS: Azure Disk and Azure Files CSI drivers ship by default, and you enable add-ons and extensions as needed. AKS Automatic turns on an opinionated set.
* For anything else you use Helm charts or vendor manifests.

== What You Install and What Ships

On ROSA and ARO, every capability a production cluster needs arrives in one of three ways.
The diagram sorts them; the names in code font are the cluster Operators or resources you look up in the exercises.

image::module-01-what-ships.svg["How platform capabilities arrive on ROSA and ARO: shipped and upgraded with the cluster, shipped and configured by you, or added from the Software Catalog",link=self,window=_blank]

=== Ships, Upgraded with the Cluster

These are installed with the cluster, upgraded with it and monitored by SRE.
On EKS and AKS, most of them are add-ons you choose, install and keep compatible yourself.

Pod network (`network`)::
OVN-Kubernetes.
On EKS it is the VPC CNI add-on, which you update; on AKS, the Azure CNI mode you choose at create time.

Cluster DNS (`dns`)::
CoreDNS, run by an Operator.
On EKS it is an add-on you update; on AKS it ships.

Ingress (`ingress`)::
A router with a wildcard apps domain and a cloud load balancer, ready for Routes on day one.
On EKS you install the AWS Load Balancer Controller; on AKS you opt into the app routing add-on.

Block storage (`storage`)::
The EBS CSI driver on ROSA and the Azure Disk CSI driver on ARO, each with a default StorageClass.
On EKS you install the EBS CSI add-on, unless you use Auto Mode; on AKS, Azure Disk ships.

Image registry (`image-registry`)::
An internal registry backed by S3 or Azure storage.
ECR and ACR still work, as they do on EKS and AKS.

Metrics and alerts (`monitoring`)::
Prometheus, Alertmanager and dashboards in the console.
On EKS you add metrics-server and run Prometheus or Amazon Managed Service for Prometheus; on AKS, metrics-server ships and managed Prometheus is an add-on.

Web console (`console`)::
The OpenShift web console for every cluster resource.
On EKS and AKS, the AWS console and the Azure portal show a resource view.

=== Ships, You Configure It

The component is there, but the settings are yours.

Node autoscaling::
A setting on a ROSA machine pool, or a MachineAutoscaler on ARO (Module 4).
On EKS you install Cluster Autoscaler or Karpenter, unless you use Auto Mode; on AKS it is a cluster setting or node auto-provisioning.

Ingress settings::
On ARO, changed through the IngressController resource, never by editing the router Deployment.
On ROSA, SRE manages the default IngressController: you can read it but not edit it.
`rosa edit ingress` changes only its visibility and component routes; for anything else you add a second IngressController (Module 3).

Identity providers::
Configured through OpenShift OAuth (Module 2).
On EKS and AKS, cluster access comes from IAM and Entra ID directly.

=== From the Software Catalog

These are Operators you install, and then run: their capacity, their configuration and their updates are yours.

GitOps::
The OpenShift GitOps Operator, which this page installs.
On EKS, the Argo CD capability runs Argo CD for you; on AKS it is the Flux extension.

Log forwarding::
The Logging Operator (Module 4).
On EKS you install Fluent Bit or the CloudWatch agent; on AKS it is the Container insights add-on.

Shared file storage::
On ROSA, the AWS EFS CSI Driver Operator, with an IAM role.
On ARO, Azure Files ships on clusters created with a service principal, and is off by default on clusters created with managed identities.
On EKS you install the EFS CSI add-on; on AKS, Azure Files ships.

Backup::
The OADP Operator, covered in xref:module-01-who-manages-what.adoc#_backup_and_restore[Backup and Restore].
On EKS and AKS, AWS Backup and Azure Backup are managed services.

The pattern: on ROSA and ARO the infrastructure plumbing ships with the cluster, is upgraded with it and is watched by SRE, while application-facing tools such as GitOps, logging and service mesh come from the Software Catalog and are yours to run.

.In production: Azure services on ARO (reference only)
[%collapsible]
====
On AKS, Azure Policy, Defender for Containers, Container insights, Flux and the Key Vault provider are add-ons or extensions of the cluster resource.
On ARO you get them only by connecting the cluster to Azure Arc and installing each one as an Arc extension, with this status in Microsoft's documentation as of October 2026:

* Azure Policy: validated on ARO. ARO's preinstalled Guardrails conflict with it and must be disabled first, following https://learn.microsoft.com/azure/azure-arc/kubernetes/extensions-release#azure-red-hat-openshift-aro-considerations[Microsoft's steps].
* Defender for Containers: lists ARO, but its support for Arc-enabled clusters is in preview.
* Container insights and managed Prometheus: supported on ARO through Arc (Module 4).
* Flux (GitOps): supported on any CNCF-certified cluster.
On OpenShift, its controllers need the `nonroot` security context constraint (SCC), which you grant to their service accounts before you install the extension, following https://learn.microsoft.com/azure/azure-arc/kubernetes/tutorial-use-gitops-flux2#red-hat-openshift-onboarding-guidance[Microsoft's OpenShift steps].
* Key Vault Secrets Provider: Microsoft recommends the Arc extension on ARO over installing the open source driver yourself.
The extension retires on October 9, 2027, in favor of the Secret Store extension, whose list of supported distributions names OpenShift Kubernetes Distribution but not ARO.

=== Exercise 1: Read the Cluster Version

Every OpenShift cluster has one ClusterVersion resource.
It records the release the cluster runs, its update channel, and its update history.

[source,bash]
----
oc get clusterversion
----

Show the update channel:

[source,bash]
----
oc get clusterversion version \
  --output jsonpath='{.spec.channel}{"\n"}'
----

On ROSA the channel is set by the service and follows your cluster's minor version, such as `stable-4.22`.
On ARO it is empty until you set one, because you start ARO upgrades yourself; Module 4 covers this.
The update history is in xref:module-04-upgrades.adoc#ex-module-04-upgrades-2[Upgrades Exercise 2].

On EKS and AKS the Kubernetes version is a property of the cluster resource in the cloud API.
On OpenShift the version covers the whole platform: Kubernetes and every cluster Operator move together.
On ARO the node operating system moves in the same update; on ROSA it moves when you upgrade each machine pool.
Module 4 covers how that changes upgrades.

.EKS and AKS (reference only)
[%collapsible]
====
[source,bash]
----
aws eks describe-cluster \
  --name <cluster-name> \
  --query cluster.version
----

[source,bash]
----
az aks show \
  --resource-group <resource-group> \
  --name <cluster-name> \
  --query kubernetesVersion
----
====

=== Exercise 2: List the Cluster Operators

Each platform component is run by a cluster Operator.
Its status tells you whether the component is healthy.

[source,bash]
----
oc get clusteroperators
----

Read the three status columns:

* `AVAILABLE`: the component works.
* `PROGRESSING`: the component is rolling out a change, for example during an upgrade.
* `DEGRADED`: the component is not in the state it should be in.

On a healthy cluster every Operator shows `True`, `False`, `False`.
This one command covers every platform component that ships with the cluster, where EKS and AKS have you check each add-on's Deployment and version.
Operators you add from the Software Catalog, such as GitOps, Logging or OADP, are not in this list.

Their ClusterServiceVersions (CSVs) report their health instead.
A CSV is the record that the Operator Lifecycle Manager (OLM) keeps of each installed Operator version.
The selector skips the copies that OLM places in every namespace:

[source,bash]
----
oc get clusterserviceversions \
  --all-namespaces \
  --selector '!olm.copiedFrom'
----

The `PHASE` column shows `Succeeded` for a healthy Operator.

Count the Operators:

[source,bash]
----
oc get clusteroperators \
  --no-headers \
  | wc -l
----

The lists differ between the two platforms.
On ROSA there is no `etcd` Operator, and the Operators that manage machines are missing, because the control plane runs in Red Hat's account.
Control plane components such as `kube-apiserver` still report their status here, but their pods are not in your cluster.
On ARO every Operator runs in your cluster, on the control plane nodes.
ARO also adds its own `aro` Operator, which the service uses to monitor and repair the cluster from inside it.

.EKS and AKS (reference only)
[%collapsible]
====
[source,bash]
----
aws eks list-addons \
  --cluster-name <cluster-name>
----

[source,bash]
----
az aks show \
  --resource-group <resource-group> \
  --name <cluster-name> \
  --query addonProfiles
----

[source,bash]
----
az k8s-extension list \
  --resource-group <resource-group> \
  --cluster-name <cluster-name> \
  --cluster-type managedClusters
----

EKS Auto Mode components do not appear in `aws eks list-addons`, and newer AKS features, such as app routing, KEDA, managed Prometheus and Istio, live in their own profiles of `az aks show`, not in `addonProfiles`.

=== Exercise 3: Map Your Add-ons to Cluster Operators

Pick a component you install yourself on EKS, such as an ingress controller.
Find the Operator that provides it here, and where its pieces run:

[source,bash]
----
oc describe clusteroperator ingress
----

The `Related Objects` list at the end names the namespaces and resources the Operator manages, such as `openshift-ingress-operator` and `openshift-ingress`.

Look at the router pods it runs:

[source,bash]
----
oc get pods \
  --namespace openshift-ingress
----

Each Operator is configured through its own resource, not by editing the Deployments it creates.
For the ingress Operator that resource is the IngressController:

[source,bash]
----
oc get ingresscontrollers \
  --namespace openshift-ingress-operator
----

On ROSA, read the default IngressController but don't edit it: SRE manages it.

Repeat for two more Operators from the diagram above, such as `storage` and `monitoring`.

[#ex-module-01-what-ships-4]
=== Exercise 4: Find the Default StorageClass

[source,bash]
----
oc get storageclass
----

[source,bash]
----
oc get csidrivers
----

On ROSA the default class is backed by the EBS CSI driver, with gp3 volumes.
On ARO the default class is backed by the Azure Disk CSI driver.
Both create `ReadWriteOnce` volumes.
For `ReadWriteMany` storage on ROSA you install the AWS EFS CSI Driver Operator and give it an IAM role.
ARO clusters created with a service principal also ship an `azurefile-csi` class for `ReadWriteMany` volumes.
ARO clusters created with managed identities do not offer Azure Files by default.

The CSI drivers themselves are managed by the `storage` cluster Operator through a ClusterCSIDriver resource:

[source,bash]
----
oc get clustercsidrivers
----

.EKS and AKS (reference only)
[%collapsible]
====
On a new EKS cluster without Auto Mode, there is no EBS CSI driver until you add it, with an IAM role for its service account:

[source,bash]
----
aws eks create-addon \
  --cluster-name <cluster-name> \
  --addon-name aws-ebs-csi-driver \
  --service-account-role-arn <role-arn>
----

AKS ships the Azure Disk and Azure Files drivers and their StorageClasses:

[source,bash]
----
kubectl get storageclass
----
====

=== Exercise 5: Browse the Software Catalog

The Software Catalog lists Operators from catalog sources.
In the web console it is under *Ecosystem*, and it was called OperatorHub in earlier releases.

List the catalog sources the cluster uses:

[source,bash]
----
oc get catalogsources \
  --namespace openshift-marketplace
----

ARO only shows Red Hat's catalogs when the cluster has a Red Hat pull secret.
If `redhat-operators` is missing on ARO, either the cluster has no Red Hat pull secret, or it was added after creation and the sources are still disabled.

On ARO, check which default sources are disabled:

[source,bash]
----
oc get operatorhub cluster \
  --output jsonpath='{.spec.sources}{"\n"}'
----

An empty line means that no default source is disabled.

[source,bash]
----
oc get packagemanifest openshift-gitops-operator \
  --namespace openshift-marketplace \
  --output jsonpath='{.status.defaultChannel}{"\n"}'

=== Exercise 6: Install OpenShift GitOps

A catalog Operator plays the part of an add-on or a Helm chart that you install on EKS or AKS.
Unlike the cluster Operators in Exercise 2, it is not part of the OpenShift release: it follows its own update channel, and OLM installs and updates it.
It is installed with three resources: a namespace, an OperatorGroup and a Subscription.

* The OperatorGroup sets which namespaces the Operator serves.
* The Subscription names the package, the channel to follow, and whether updates are approved automatically.
* OLM then creates an InstallPlan, the pending install or update, which `installPlanApproval: Manual` holds until you approve it.
* The installed version is a ClusterServiceVersion, roughly what a Helm release is to a chart.

Create the namespace:

[source,bash]
----
oc create namespace openshift-gitops-operator
----

Create the OperatorGroup:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-gitops-operator
  namespace: openshift-gitops-operator
spec:
  upgradeStrategy: Default
EOF
----

Create the Subscription:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: openshift-gitops-operator
  namespace: openshift-gitops-operator
spec:
  channel: latest
  installPlanApproval: Automatic
  name: openshift-gitops-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
EOF
----

Watch the install until the ClusterServiceVersion reports `Succeeded`:

[source,bash]
----
oc get clusterserviceversions \
  --namespace openshift-gitops-operator \
  --watch
----

Operators installed for all namespaces, such as the Logging Operator, also list their ClusterServiceVersions here.
Look for the one that starts with `openshift-gitops-operator`.

The Operator creates a default Argo CD instance in the `openshift-gitops` namespace.
Check that its pods are running:

[source,bash]
----
oc get pods \
  --namespace openshift-gitops
----

NOTE: Operators that call cloud APIs, such as the EFS CSI Driver Operator, need an IAM role or managed identity, and on ROSA they should use `installPlanApproval: Manual`, so that an update cannot change the permissions they need without you noticing. OpenShift GitOps calls no cloud APIs, so automatic approval is fine here.

.EKS and AKS (reference only)
[%collapsible]
====
On EKS, the Argo CD capability runs Argo CD for you outside the cluster; you create it in the EKS console or API and connect it to the cluster.

On AKS, GitOps is the Flux extension:

[source,bash]
----
az k8s-extension create \
  --resource-group <resource-group> \
  --cluster-name <cluster-name> \
  --cluster-type managedClusters \
  --extension-type microsoft.flux \
  --name flux
----
====

=== Exercise 7: Sync One Application

Create a namespace for the application:

[source,bash]
----
oc create namespace gitops-hello
----

Label it so the default Argo CD instance may manage it:

[source,bash]
----
oc label namespace gitops-hello \
  argocd.argoproj.io/managed-by=openshift-gitops
----

Create an Argo CD Application that points at this workshop's repository.
Its finalizer makes deleting the Application also delete what it deployed; without it, the deployed resources stay behind:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: gitops-hello
  namespace: openshift-gitops
  finalizers:
  - resources-finalizer.argocd.argoproj.io
spec:
  project: default
  source:
    repoURL: https://github.com/shpwrck/ocp-cloud-workshop.git
    targetRevision: main
    path: exercises/module-01/gitops-hello
  destination:
    server: https://kubernetes.default.svc
    namespace: gitops-hello
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
EOF
----

`oc` may warn that the finalizer name should be domain-qualified and include a path; that warning is harmless.

Check that the application is synced and healthy:

[source,bash]
----
oc get applications.argoproj.io gitops-hello \
  --namespace openshift-gitops
----

[source,bash]
----
oc get pods \
  --namespace gitops-hello
----

Open the Argo CD web console.
Its address is the host of this route:

[source,bash]
----
oc get route openshift-gitops-server \
  --namespace openshift-gitops \
  --output jsonpath='{.spec.host}{"\n"}'
----

[.validation]
NOTE: *Not validated:* the console login itself.
The route answered and Argo CD offered the OpenShift login, but nobody signed in through a browser.

Log in with *Log in via OpenShift*, using your cluster credentials.

=== Clean Up

Delete the application, which also removes what it deployed:

[source,bash]
----
oc delete applications.argoproj.io gitops-hello \
  --namespace openshift-gitops
----

[source,bash]
----
oc delete namespace gitops-hello
----

Keep the OpenShift GitOps Operator installed; later modules do not depend on it, but removing an Operator takes more steps than installing one.

== What Matters

* Platform components are owned by Operators. Editing their resources directly is reverted; you change them through the Operator's configuration resource, such as the IngressController, and only where SRE allows it.
* One health view for the platform: `oc get clusteroperators` covers every component that ships with the cluster, and catalog Operators report through their ClusterServiceVersions. SRE is alerted when a platform Operator degrades, but if your own configuration caused it, such as an identity provider, a webhook or a PodDisruptionBudget, the fix is yours.
* Storage: ROSA ships the EBS CSI driver with a default gp3 StorageClass. Shared (RWX) storage needs the EFS CSI Driver Operator and an IAM role. ARO ships Azure Disk as the default; Azure Files ships on clusters created with a service principal and is disabled by default on clusters created with managed identities.
* ARO needs a Red Hat pull secret before it can install Operators from the Software Catalog.
The install removes the pull secret's `cloud.openshift.com` entry, so an ARO cluster sends no telemetry and is not registered in OpenShift Cluster Manager until you add that entry back, which the Red Hat Lightspeed advisor (formerly Insights Advisor) needs.
ROSA clusters are always registered, with telemetry on.
* On ROSA, the `dedicated-admin` role can install Operators into `openshift-operators` and into projects you create, so you do not need `cluster-admin` to extend the platform. It cannot create other `openshift-` namespaces, such as the one Exercise 6 uses.
* Catalog Operators such as OpenShift GitOps run on your worker nodes and are yours to operate: their capacity, their configuration and approving their updates.
* Helm still works on ROSA and ARO. Use it for vendor software that has no Operator.

== Where Each Wins

[cols="1,1",options="header"]
|===
|ROSA and ARO win |EKS and AKS win

|Ingress, registry, monitoring, storage and console work on day one.
|Smaller footprint: you run only what you choose, and Auto Mode runs its controllers outside your nodes.

|Platform components upgrade together in one tested release.
|Freedom to swap components, such as Cilium or a different ingress.

|One catalog and lifecycle model (Operators) for platform add-ons, with one health view for the components that ship with the cluster.
|Managed GitOps: the EKS Argo CD capability and the AKS Flux extension run without an in-cluster Argo CD to operate.
Flux is a native extension on AKS; ARO gets it only through Azure Arc, after you connect the cluster.

|SRE monitors every component that ships with the cluster and is alerted when one degrades.
|AKS Automatic gives a similar opinionated default set, with AKS add-ons supported by Microsoft.
|===

== App Teams Will Notice

* Application teams get a working Route, a default StorageClass and metrics on day one, with nothing to request from you.
* Teams used to installing their own controllers with Helm will find that cluster-wide components come from the Software Catalog, and installing one needs an administrator.
