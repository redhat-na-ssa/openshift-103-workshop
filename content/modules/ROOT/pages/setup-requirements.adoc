= Setup Requirements

This page lists everything needed to run this workshop.

Each attendee does the hands-on work on one cluster: ROSA or ARO, matching the platform their team runs.
An attendee whose team runs both can have one of each and run every exercise twice.
EKS and AKS appear only as reference blocks, so no EKS or AKS cluster is needed.
The instructor creates the clusters ahead of time.
Several exercises change cluster-wide settings (identity providers, AdminNetworkPolicy, machine pools), so each attendee or pair needs their own cluster.
An attendee needs only the parts of this page for their platform: for ROSA, the ROSA cluster, an AWS account, `rosa` and `aws`; for ARO, the ARO cluster, an Azure subscription and `az`.

== Cluster

[cols="1,3",options="header"]
|===
|Platform |Requirement

|ROSA
a|* ROSA with hosted control planes (HCP), in STS mode (the default).
* Its own OIDC config, not one shared with another attendee's cluster, so that Module 2's trust policies stay scoped to one cluster.
* OpenShift 4.22 or later, for the Red Hat build of Karpenter in Module 4.
* A public API and default ingress.
* At least 32 vCPUs of On-Demand Standard instance quota in the region, the minimum ROSA needs to install.
The AWS default is 5, so an account that has not run ROSA before needs an increase, which can take several hours to approve.
* At least 2 worker nodes, with Service Quotas that allow the cluster to scale out by at least 3 more nodes in Module 4.

Check the quotas before creating the cluster:

[source,bash]
----
rosa verify quota
----

|ARO
a|* Created with managed identities, which Module 2 needs for workload identity. A cluster created with a service principal cannot be converted.
* Created with a Red Hat pull secret, which Module 1 needs to install Operators. If the cluster was created without one, https://learn.microsoft.com/azure/openshift/howto-add-update-pull-secret[add it afterwards].
* The newest OpenShift version ARO offers.
* A public API and default ingress.
* Quota to install: 44 vCPUs, in the regional total and in the VM family of the nodes, Standard DSv5 for the default sizes.
Of those, 8 are for a bootstrap VM that the install removes, 24 for the control plane and 12 for three workers.
A new subscription has less, and Azure can refuse an increase in a region that is short of capacity, so request it early and keep a fallback region in mind.
* Quota for at least 3 more worker nodes in the region, for Module 4.

These resource providers must be registered:

[source,bash]
----
for namespace in \
    Microsoft.RedHatOpenShift \
    Microsoft.Compute \
    Microsoft.Storage \
    Microsoft.Authorization \
    Microsoft.Network; do
  az provider register --wait \
    --namespace "$namespace"
done
----

List the OpenShift versions the region can install, and pick the newest:

[source,bash]
----
az aro get-versions \
  --location <region>
----
|===

ROSA with HCP runs in fewer regions than EKS, and ARO in fewer than AKS, so check that the region you plan to use offers the service.

To create the clusters, follow:

* https://docs.redhat.com/en/documentation/red_hat_openshift_service_on_aws/4/html/install_clusters/index[Creating ROSA with HCP clusters]
* https://learn.microsoft.com/azure/openshift/howto-create-openshift-cluster[Creating ARO clusters with managed identities]

For a production cluster, also read xref:module-01-living-with-the-service.adoc#decide-before-you-create[Decide Before You Create]: some settings can't be changed once the cluster exists.

== Operators and Cluster Components

Nothing needs to be installed before the workshop.
Attendees install these Operators during the exercises:

[cols="1,1,2",options="header"]
|===
|Operator |Module |Notes

|Red Hat OpenShift GitOps
|1
|The Software Catalog example.

|Red Hat OpenShift Logging
|4
|Channel `stable-6.6`. Forwards application logs to CloudWatch and to Azure Monitor Logs through the Logs Ingestion API.

|Red Hat OpenShift Service Mesh 3
|3
|The Ingress Operator starts an Istio control plane, `istiod-openshift-gateway`, when the Gateway API exercise creates a GatewayClass. On 4.20 and 4.21 it did so without an OLM subscription. Where a version installs the Service Mesh 3 Operator from the Red Hat catalog instead, ARO needs its pull secret, and the cluster must not already have an OpenShift Service Mesh 2 subscription.
|===

The default ingress controller, OVN-Kubernetes, the CSI drivers and platform monitoring come with every ROSA and ARO cluster.

== Attendee Accounts, Projects and Roles

[cols="1,3",options="header"]
|===
|Where |What the attendee needs

|ROSA cluster
|Cluster administrator (`cluster-admin`, not `dedicated-admin`), through the temporary admin user or an identity provider.
A cluster has only one temporary admin user.
Either the facilitator creates it and hands out its login command, or each attendee creates it on their own cluster in Module 1, but not both.
On their Red Hat account, permission to manage the cluster in OpenShift Cluster Manager, so they can add identity providers, machine pools and upgrade policies, and turn on AutoNode (the Red Hat build of Karpenter), with the `rosa` CLI.

|ARO cluster
|The kubeadmin credential, and `Contributor` on the cluster's resource group.
`Contributor` lets the attendee read the kubeadmin password and the admin kubeconfig from the cluster resource, so it makes them cluster administrator through Azure.
`Reader` on the subscription, so Module 1 can list the resources and the deny assignment in the cluster's managed resource group, which holds its VMs.

|AWS account
a|Permission to create:

* IAM roles and policies (Module 2 and Module 4)
* A policy attachment on the cluster's worker IAM role, for ECR pulls (Module 2)
* S3 buckets (Module 2)
* ECR repositories (Module 2)
* CloudWatch log groups (Module 4)

Read access to EC2 and Elastic Load Balancing, to look up the cluster's load balancer, network interfaces and NAT gateways (Module 3).

|Azure subscription
a|Permission to create, in a resource group:

* User-assigned managed identities and federated credentials (Module 2)
* Storage accounts, and role assignments on them, which need Owner or User Access Administrator on the resource group (Module 2)
* Container registries (Module 2)
* Log Analytics workspaces and tables, data collection endpoints and rules, a user-assigned managed identity with a federated credential, and a role assignment on the rule (Module 4)

`Reader` on the cluster's managed resource group (the `aro-...` group the cluster creates), to look up its load balancer, public IPs and network interfaces (Module 3).

The subscription must have the `Microsoft.ContainerRegistry` (Module 2), `Microsoft.OperationalInsights` and `Microsoft.Insights` (Module 4) resource providers registered.
A new subscription may not, and an attendee with access only to a resource group cannot register them, so the subscription owner registers them before the day:

[source,bash]
----
for p in Microsoft.ContainerRegistry Microsoft.OperationalInsights Microsoft.Insights; do
  az provider register --namespace "$p"
done
----

In Microsoft Entra ID: permission to create an app registration for the ARO identity provider (Module 2).
|===

The ROSA identity provider in Module 2 is an htpasswd provider created with the `rosa` CLI, so it needs no external application.

== Network and Image Access

Workstations need outbound HTTPS to:

* the AWS and Azure APIs
* console.redhat.com
* sso.redhat.com, where `rosa login` signs you in
* api.openshift.com
* the ROSA and ARO cluster API and application domains. The ROSA with HCP API listens on port 443 and the ARO API on port 6443, so a firewall that allows only 443 blocks the ARO API.
* ghcr.io, where Module 2 copies the sample application's image from

Clusters need outbound access to:

* quay.io
* registry.redhat.io
* registry.access.redhat.com (UBI images for the test pods in Module 3)
* checkip.amazonaws.com (the egress address check in Module 3)
* ghcr.io, for the sample application's image (Modules 2 and 3)
* github.com, where Argo CD clones this workshop's repository (Module 1)
* api.openshift.com, for the update information the upgrade exercises read (Module 4)
* the attendee's ECR and ACR registries

== Verification Checklist

Before the workshop, check each item for every attendee.

The attendee can log in to their cluster:

[source,bash]
----
oc whoami
----

The cluster reports its version and is not upgrading:

[source,bash]
----
oc get clusterversion
----

The ROSA cluster is HCP and on 4.22 or later:

[source,bash]
----
rosa describe cluster \
  --cluster <cluster-name>
----

The ARO cluster is ready:

[source,bash]
----
az aro show \
  --resource-group <resource-group> \
  --name <cluster-name> \
  --query provisioningState
----

The cluster can reach the Software Catalog:

[source,bash]
----
oc get packagemanifests \
  --namespace openshift-marketplace
----

== Cost and Cleanup

The clusters, and the cloud resources attendees create during the workshop, are billed for as long as they exist.
After the workshop, clean up each cloud account in this order.

[tabs]
======
ROSA (AWS)::
+
--
. Detach the ECR read policy from the ROSA worker IAM role. Other ROSA clusters in the account share that role, so do not delete it.
. Delete the IAM roles and policies attendees created, including the Karpenter and log forwarding roles from Module 4.
. Delete the S3 buckets, ECR repositories and CloudWatch log groups attendees created.
. Note the cluster's operator role prefix and OIDC configuration ID, which the last steps need once the cluster is gone.
The roles under `Operator IAM Roles` start with the prefix, and the `OIDC Endpoint URL` of a managed configuration ends with its ID:
+
[source,bash]
----
rosa describe cluster \
  --cluster <cluster-name>
----
. Delete the cluster, and wait for the deletion to finish:
+
[source,bash]
----
rosa delete cluster \
  --cluster <cluster-name> \
  --watch
----
. Delete the cluster's operator roles and OIDC provider, which the cluster deletion leaves behind:
+
[source,bash]
----
rosa delete operator-roles \
  --prefix <operator-role-prefix> \
  --mode auto
----
+
[source,bash]
----
rosa delete oidc-provider \
  --oidc-config-id <oidc-config-id> \
  --mode auto
----
. Delete the cluster's OIDC configuration.
The command refuses if another cluster still uses it:
+
[source,bash]
----
rosa delete oidc-config \
  --oidc-config-id <oidc-config-id> \
  --mode auto
----
. If `rosa create network` built the VPC, delete its CloudFormation stack, whose NAT gateways and VPC endpoints are billed by the hour.
Unless you named it, the stack is called `rosa-network-stack-` followed by the AWS account ID:
+
[source,bash]
----
aws cloudformation delete-stack \
  --stack-name <stack-name> \
  --region <region>
----

The account roles, the `ocm-role` and the `user-role` stay, because other ROSA clusters in the account use them.
For an account that will run no more ROSA clusters, Red Hat's https://docs.redhat.com/en/documentation/red_hat_openshift_service_on_aws/4/html-single/install_clusters/index#rosa-hcp-deleting-cluster[deletion steps] remove them too.
--
ARO (Azure)::
+
--
. Delete the Entra ID app registration for the ARO identity provider.
. Delete the managed identities, storage accounts and container registries attendees created.
. Delete the Log Analytics workspaces, and the data collection rules and endpoints.
. Delete the cluster:
+
[source,bash]
----
az aro delete \
  --resource-group <resource-group> \
  --name <cluster-name>
----
+
It asks you to confirm, takes about 10 minutes, and removes the cluster's managed `aro-...` resource group with it.
. Delete the cluster's managed identities, its virtual network and subnets, and the resource group, if it holds nothing else.
The cluster deletion leaves all of them behind, as https://learn.microsoft.com/azure/openshift/howto-create-openshift-cluster#clean-up[Microsoft's clean-up steps] note.
For a resource group that held only the cluster:
+
[source,bash]
----
az group delete \
  --name <resource-group>
----
. Remove any role assignments that the deleted identities held outside the resource groups you deleted, such as on a virtual network in another resource group.
Azure doesn't delete those with the identities, and the portal's access control (IAM) view lists them as `Identity not found`.
Assignments scoped inside a deleted resource group go with it: with the network and identities in the cluster's resource group, deleting it left none behind.
--
