= Setup Requirements
:hardbreaks-option:

This page lists everything needed to run this workshop.

Attendees do the hands-on work on a ROSA cluster and an ARO cluster.
EKS and AKS appear only as reference blocks, so no EKS or AKS cluster is needed.
The instructor creates the clusters ahead of time.
Several exercises change cluster-wide settings (identity providers, AdminNetworkPolicy, machine pools), so each attendee or pair needs their own ROSA and ARO cluster.

== Cluster

[cols="1,3",options="header"]
|===
|Platform |Requirement

|ROSA
a|* ROSA with hosted control planes (HCP), in STS mode (the default).
* OpenShift 4.22 or later, for the Red Hat build of Karpenter in Module 4.
* A public API and default ingress.
* At least 2 worker nodes, with Service Quotas that allow the cluster to scale out by at least 3 more nodes in Module 4.

Check the quotas before creating the cluster:

[source,bash]
----
rosa verify quota
----

|ARO
a|* Created with managed identities, which Module 2 needs for workload identity. A cluster created with a service principal cannot be converted.
* Created with a Red Hat pull secret, which Module 1 needs to install Operators. If the cluster was created without one, https://learn.microsoft.com/azure/openshift/howto-add-update-pull-secret[add it afterwards].
* The newest OpenShift version ARO offers.
* A public API and default ingress.
* Quota for at least 3 more worker nodes in the region, for Module 4.

These resource providers must be registered:

[source,bash]
----
for namespace in \
    Microsoft.RedHatOpenShift \
    Microsoft.Compute \
    Microsoft.Storage \
    Microsoft.Authorization \
    Microsoft.Network; do
  az provider register --wait \
    --namespace "$namespace"
done
----
|===

To create the clusters, follow:

* https://docs.redhat.com/en/documentation/red_hat_openshift_service_on_aws/4/html/install_clusters/index[Creating ROSA with HCP clusters]
* https://learn.microsoft.com/azure/openshift/howto-understand-managed-identities[Creating ARO clusters with managed identities]

== Operators and Cluster Components

Nothing needs to be installed before the workshop.
Attendees install these Operators during the exercises:

[cols="1,1,2",options="header"]
|===
|Operator |Module |Notes

|Red Hat OpenShift GitOps
|1
|The Software Catalog example.

|Red Hat OpenShift Logging
|4
|Channel `stable-6.6`. Forwards application logs to CloudWatch and to Azure Monitor Logs through the Logs Ingestion API.

|Red Hat OpenShift Service Mesh 3
|3
|Installed by the Ingress Operator when the Gateway API exercise creates a GatewayClass. It needs the Red Hat catalog and registry, so ARO needs its pull secret. The cluster must not already have an OpenShift Service Mesh 2 subscription.
|===

The default ingress controller, OVN-Kubernetes, the CSI drivers and platform monitoring come with every ROSA and ARO cluster.

== Attendee Accounts, Projects and Roles

[cols="1,3",options="header"]
|===
|Where |What the attendee needs

|ROSA cluster
|Cluster administrator, through the temporary admin user or an identity provider.
On their Red Hat account, permission to manage the cluster in OpenShift Cluster Manager, so they can add identity providers, machine pools and upgrade policies, and turn on AutoNode (the Red Hat build of Karpenter), with the `rosa` CLI.

|ARO cluster
|The kubeadmin credential, and `Contributor` on the cluster's resource group.
`Reader` on the subscription, so Module 1 can list the resources and the deny assignment in the cluster's managed resource group, which holds its VMs.

|AWS account
a|Permission to create:

* IAM roles and policies (Module 2 and Module 4)
* A policy attachment on the cluster's worker IAM role, for ECR pulls (Module 2)
* S3 buckets (Module 2)
* ECR repositories (Module 2)
* CloudWatch log groups (Module 4)

Read access to EC2 and Elastic Load Balancing, to look up the cluster's load balancer, network interfaces and NAT gateways (Module 3).

|Azure subscription
a|Permission to create, in a resource group:

* User-assigned managed identities and federated credentials (Module 2)
* Storage accounts, and role assignments on them, which need Owner or User Access Administrator on the resource group (Module 2)
* Container registries (Module 2)
* Log Analytics workspaces and tables, data collection endpoints and rules, a user-assigned managed identity with a federated credential, and a role assignment on the rule (Module 4)

`Reader` on the cluster's managed resource group (the `aro-...` group the cluster creates), to look up its load balancer, public IPs and network interfaces (Module 3).

In Microsoft Entra ID: permission to create an app registration for the ARO identity provider (Module 2).
|===

The ROSA identity provider in Module 2 is an htpasswd provider created with the `rosa` CLI, so it needs no external application.

== Network and Image Access

Workstations need outbound HTTPS to:

* the AWS and Azure APIs
* console.redhat.com
* api.openshift.com
* the ROSA and ARO cluster API and application domains. The ROSA with HCP API listens on port 443 and the ARO API on port 6443, so a firewall that allows only 443 blocks the ARO API.
* ghcr.io, where Module 2 copies the sample application's image from

Clusters need outbound access to:

* quay.io
* registry.redhat.io
* registry.access.redhat.com (UBI images for the test pods in Module 3)
* checkip.amazonaws.com (the egress address check in Module 3)
* ghcr.io, for the sample application's image (Modules 2 and 3)
* the attendee's ECR and ACR registries

== Verification Checklist

Before the workshop, check each item for every attendee.

The attendee can log in to both clusters:

[source,bash]
----
oc whoami
----

Both clusters report their version and are not upgrading:

[source,bash]
----
oc get clusterversion
----

The ROSA cluster is HCP and on 4.22 or later:

[source,bash]
----
rosa describe cluster \
  --cluster <cluster-name>
----

The ARO cluster is ready:

[source,bash]
----
az aro show \
  --resource-group <resource-group> \
  --name <cluster-name> \
  --query provisioningState
----

Both clusters can reach the Software Catalog:

[source,bash]
----
oc get packagemanifests \
  --namespace openshift-marketplace
----

== Cost and Cleanup

The clusters, and the cloud resources attendees create during the workshop, are billed for as long as they exist.
After the workshop, clean up each cloud account in this order.

[tabs]
======
ROSA (AWS)::
+
--
. Detach the ECR read policy from the ROSA worker IAM role. Other ROSA clusters in the account share that role, so do not delete it.
. Delete the IAM roles and policies attendees created, including the Karpenter and log forwarding roles from Module 4.
. Delete the S3 buckets, ECR repositories and CloudWatch log groups attendees created.
. Delete the cluster, following https://docs.redhat.com/en/documentation/red_hat_openshift_service_on_aws/4/html/install_clusters/index[Deleting ROSA with HCP clusters].
--
ARO (Azure)::
+
--
. Delete the Entra ID app registration for the ARO identity provider.
. Delete the managed identities, storage accounts and container registries attendees created.
. Delete the Log Analytics workspaces, and the data collection rules and endpoints.
. Delete the cluster, following https://learn.microsoft.com/azure/openshift/howto-understand-managed-identities[Deleting ARO clusters with managed identities].
--
======
