= Exposing an App

[.validation]
NOTE: Validated on ROSA HCP 4.20 and 4.22 and ARO 4.21 in October 2026.
Steps and statements that were not checked on a live cluster carry a *Not validated* note.
The comparison tables and summaries come from vendor documentation.

On EKS and AKS you add or enable an L7 ingress controller (built into EKS Auto Mode and on by default in AKS Automatic) and bring your own DNS and certificates.
ROSA and ARO arrive with a default ingress controller behind a cloud load balancer, a wildcard DNS name for applications and a certificate for it, so the sample application gets an HTTPS address in one step.
This section exposes the sample application three ways: an OpenShift Route, a standard Kubernetes Ingress, and the Gateway API.

.How a request reaches a pod on each platform
image::module-03-request-path.svg["Request path from client to pod on EKS, AKS, ROSA and ARO",width=100%,link=self,window=_blank]

== On EKS and AKS

* EKS: install the AWS Load Balancer Controller (built in with Auto Mode), then each Ingress creates or joins an Application Load Balancer. The controller also supports the Gateway API.
* AKS: enable the application routing add-on. Its managed NGINX loses Azure support after November 2026, and its Gateway API mode is the path forward.
* You bring DNS (for example ExternalDNS) and certificates (for example cert-manager, AWS Certificate Manager or Azure Key Vault).

== On ROSA and ARO

Do these steps on your cluster.
If you have both, finish them on ROSA, then repeat them on ARO.
Where the two differ, the steps are split into ROSA and ARO tabs.
The sample application from Module 2 runs in the `sample-app` project, behind a Service named `sample-app` on port `8080`.
Its `/healthz` path always answers `200`, so the checks below use it.

[#ex-module-03-exposing-apps-1]
=== Exercise 1: Find the Default Ingress Controller

Every cluster has an IngressController named `default`.
Save the application domain it serves:

[source,bash]
----
APPS_DOMAIN=$(oc get ingresscontroller default \
  --namespace openshift-ingress-operator \
  --output jsonpath='{.status.domain}')
----

[source,bash]
----
echo "$APPS_DOMAIN"
----

The router pods sit behind a Service of type `LoadBalancer`:

[source,bash]
----
oc get service router-default \
  --namespace openshift-ingress
----

The `EXTERNAL-IP` column holds a host name on ROSA and an IP address on ARO.
That is the cloud load balancer the cluster created at install time.

[tabs]
======
ROSA (AWS)::
+
--
Find the load balancer in AWS:

[source,bash]
----
LB_HOST=$(oc get service router-default \
  --namespace openshift-ingress \
  --output jsonpath='{.status.loadBalancer.ingress[0].hostname}')
----

The Service's annotation already names the type:

[source,bash]
----
oc get service router-default \
  --namespace openshift-ingress \
  --output jsonpath='{.metadata.annotations.service\.beta\.kubernetes\.io/aws-load-balancer-type}{"\n"}'
----

It prints `nlb`.
AWS shows the same, `network` and `internet-facing`:

[source,bash]
----
aws elbv2 describe-load-balancers \
  --query "LoadBalancers[?DNSName=='$LB_HOST'].[Type,Scheme]" \
  --output text
----

See the ingress the way the service manages it:

[source,bash]
----
rosa list ingresses \
  --cluster "$CLUSTER"
----

On ROSA, SRE manages the default ingress controller, and `rosa edit ingress` changes only its visibility and component routes.
For anything else, such as sharding, a wildcard or namespace ownership policy, or another load balancer type, you add your own IngressController, or use the AWS Load Balancer Operator for ALBs.
On ROSA with HCP, `rosa edit ingress` refuses those settings.
--
ARO (Azure)::
+
--
Find the load balancer's public IP in Azure:

[source,bash]
----
LB_IP=$(oc get service router-default \
  --namespace openshift-ingress \
  --output jsonpath='{.status.loadBalancer.ingress[0].ip}')
----

[source,bash]
----
MANAGED_RG=$(az aro show \
  --resource-group "$RESOURCE_GROUP" \
  --name "$CLUSTER" \
  --query clusterProfile.resourceGroupId \
  --output tsv)
----

[source,bash]
----
az network public-ip list \
  --resource-group "${MANAGED_RG##*/}" \
  --query "[?ipAddress=='$LB_IP'].name" \
  --output tsv
----

The public IP lives in the cluster's managed resource group.
A deny assignment there lets you read it but not change it.

[#ex-module-03-exposing-apps-2]
=== Exercise 2: Expose the App with a Route

Create an edge-terminated Route: the router terminates TLS with the cluster's wildcard certificate and forwards plain HTTP to the pods.

[source,bash]
----
oc create route edge sample-app \
  --service sample-app \
  --port 8080 \
  --namespace sample-app
----

OpenShift picks the host name `<route>-<project>.<apps domain>`:

[source,bash]
----
ROUTE_HOST=$(oc get route sample-app \
  --namespace sample-app \
  --output jsonpath='{.spec.host}')
----

[source,bash]
----
curl --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  "https://$ROUTE_HOST/healthz"
----

It prints `200`: the app answers over HTTPS with a trusted certificate, and you created no DNS record or certificate.

Try plain HTTP:

[source,bash]
----
curl --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  "http://$ROUTE_HOST/healthz"
----

It prints `503`: an edge Route refuses plain HTTP unless you say otherwise.
Tell the router to redirect it to HTTPS:

[source,bash]
----
oc patch route sample-app \
  --namespace sample-app \
  --type merge \
  --patch '{"spec":{"tls":{"insecureEdgeTerminationPolicy":"Redirect"}}}'
----

[source,bash]
----
curl --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  "http://$ROUTE_HOST/healthz"
----

It now prints `302`, a redirect to the HTTPS address.

.EKS and AKS (reference only)
[%collapsible]
====
EKS: install the AWS Load Balancer Controller, after creating its IAM role.

[source,bash]
----
helm install aws-load-balancer-controller \
  eks/aws-load-balancer-controller \
  --namespace kube-system \
  --set clusterName=<cluster-name> \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller
----

EKS: an Ingress that creates an internet-facing ALB.

[source,yaml]
----
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: sample-app
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/certificate-arn: <certificate-arn>
spec:
  ingressClassName: alb
  rules:
  - host: sample-app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: sample-app
            port:
              number: 8080
----

AKS: enable application routing.

[source,bash]
----
az aks approuting enable \
  --resource-group <resource-group> \
  --name <cluster-name>
----

On AKS the same Ingress uses `ingressClassName: webapprouting.kubernetes.azure.com` and no ALB annotations.

[#ex-module-03-exposing-apps-3]
=== Exercise 3: Use a Standard Ingress

Manifests written for EKS or AKS use Ingress, and OpenShift accepts it.
The annotation asks for an edge-terminated Route:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: sample-app-ingress
  namespace: sample-app
  annotations:
    route.openshift.io/termination: edge
spec:
  rules:
  - host: sample-app-ingress.${APPS_DOMAIN}
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: sample-app
            port:
              number: 8080
EOF
----

OpenShift generated a Route from it:

[source,bash]
----
oc get routes \
  --namespace sample-app
----

The new Route has a generated name that starts with `sample-app-ingress-`.
Its termination shows `edge/Redirect`: a Route generated from an Ingress redirects HTTP to HTTPS without being asked.
Its owner is the Ingress, so OpenShift reverts any edit you make to the Route itself.
Change the Ingress instead.

[source,bash]
----
curl --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  "https://sample-app-ingress.$APPS_DOMAIN/healthz"
----

It prints `200`.

[#ex-module-03-exposing-apps-4]
=== Exercise 4: Use the Gateway API

OpenShift implements the Gateway API with an Envoy-based gateway that the Ingress Operator manages.
Creating the GatewayClass makes the Ingress Operator start an Istio control plane for it, `istiod-openshift-gateway`, in the `openshift-ingress` namespace.
On some OpenShift versions it installs the OpenShift Service Mesh operator first, which takes a few minutes.

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: openshift-default
spec:
  controllerName: openshift.io/gateway-controller/v1
EOF
----

[source,bash]
----
oc wait gatewayclass/openshift-default \
  --for=condition=Accepted \
  --timeout=600s
----

Create a Gateway with an HTTP listener for a new wildcard under the application domain.
Gateways live in the `openshift-ingress` namespace and accept routes from any namespace here:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: workshop
  namespace: openshift-ingress
spec:
  gatewayClassName: openshift-default
  listeners:
  - name: http
    protocol: HTTP
    port: 80
    hostname: "*.gwapi.${APPS_DOMAIN}"
    allowedRoutes:
      namespaces:
        from: All
EOF
----

[source,bash]
----
oc wait gateway/workshop \
  --namespace openshift-ingress \
  --for=condition=Programmed \
  --timeout=600s
----

The Gateway got its own DNS record, next to the router's.
It also got its own load balancer on ROSA (a Classic Load Balancer), and its own public IP and rules on the cluster's Azure load balancer on ARO.
Its Service is named after the Gateway and the GatewayClass, `workshop-openshift-default`:

[source,bash]
----
oc get service \
  --namespace openshift-ingress
----

[source,bash]
----
oc get dnsrecords \
  --namespace openshift-ingress
----

AKS app routing's Gateway API mode works the same way: Istio-managed Envoy behind one LoadBalancer Service per Gateway, named `<gateway>-<class>`.

Attach the sample application with an HTTPRoute in its own project:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: sample-app
  namespace: sample-app
spec:
  parentRefs:
  - name: workshop
    namespace: openshift-ingress
  hostnames:
  - "sample-app.gwapi.${APPS_DOMAIN}"
  rules:
  - backendRefs:
    - name: sample-app
      port: 8080
EOF
----

[source,bash]
----
curl --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  "http://sample-app.gwapi.$APPS_DOMAIN/healthz"
----

[tabs]
======
ROSA (AWS)::
+
--
It prints `200` once the new load balancer is ready, which takes a minute or two.
Until then it prints `503`, from the default router, or `000`, so wait and try again.
--
ARO (Azure)::
+
--
With the default `aroapp.io` domain, the command keeps printing `503`.
Azure manages that DNS zone, so the cluster's DNS configuration names no zone and the Gateway's DNS record is never published.
The name still resolves through the `*.apps` wildcard, to the default router, which has no Route for it.
Send the request straight to the Gateway's address instead:

[source,bash]
----
GW_IP=$(oc get gateway workshop \
  --namespace openshift-ingress \
  --output jsonpath='{.status.addresses[0].value}')
----

[source,bash]
----
curl --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  --resolve "sample-app.gwapi.$APPS_DOMAIN:80:$GW_IP" \
  "http://sample-app.gwapi.$APPS_DOMAIN/healthz"
----

It prints `200`.
To reach the Gateway by name, create the DNS record in a zone you manage.
--
======

The Gateway serves plain HTTP because nothing gave it a certificate.
Unlike a Route, a Gateway listener needs a certificate that you provide, for example from cert-manager, as in <<production-custom-domains,In production: custom domains and certificates>>.

Each Gateway costs its own load balancer on ROSA, and its own public IP and rules on the cluster's Azure load balancer on ARO, so remove this one:

[source,bash]
----
oc delete httproute sample-app \
  --namespace sample-app
----

[source,bash]
----
oc delete gateway workshop \
  --namespace openshift-ingress
----

The `openshift-default` GatewayClass and `istiod-openshift-gateway` stay.
Delete the GatewayClass if you do not want an Istio control plane running.

Remove the Ingress from Exercise 3 as well, which also removes its generated Route:

[source,bash]
----
oc delete ingress sample-app-ingress \
  --namespace sample-app
----

The Route from Exercise 2 stays.
The next section applies network policy to it.

== What Matters

* A Route is OpenShift's own resource, with edge, re-encrypt and passthrough TLS. Ingress objects still work and become Routes.
* On Module 1's xref:module-01-who-manages-what.adoc#_the_responsibility_line[responsibility line], the default router is a platform component that SRE runs, and the Routes, Ingresses and Gateways you create on it are yours, like your workloads.
* OpenShift only turns an Ingress into a Route when it has no `ingressClassName` or uses `openshift-default`. An Ingress that still says `alb` or `webapprouting.kubernetes.azure.com` is silently ignored.
* ALB and NGINX annotations do nothing here. Route behavior is set with `haproxy.router.openshift.io/*` annotations instead, for example timeouts and rewrites.
* On ROSA, SRE owns the default ingress controller's settings, and `rosa edit ingress` changes only its visibility and component routes. For other needs you add another ingress controller, or the AWS Load Balancer Operator for ALBs.
* OpenShift supports the Gateway API from 4.19. Each Gateway needs its own certificate. It gets its own load balancer on ROSA, a Classic Load Balancer rather than a Network Load Balancer like the router's, and its own public IP and rules on the cluster's Azure load balancer on ARO. The ROSA and ARO documentation do not cover it yet, it needs `cluster-admin` (not `dedicated-admin` on ROSA), and on ARO's default domain you manage its DNS yourself, so check it on your clusters before you rely on it.
* ARO has no Application Gateway or Application Gateway for Containers add-on like AKS, so a WAF sits in front of the router: Front Door Premium with Private Link to the internal router, which needs private ingress visibility chosen at create, or Application Gateway pointed at the router. Private apps can use a second IngressController with an internal load balancer.

[#production-custom-domains]
.In production: custom domains and certificates (reference only)
[%collapsible]
====
Production apps use their own host names, so each needs a DNS record and a certificate that renews itself.
Install the cert-manager Operator for Red Hat OpenShift and create an ACME issuer with a DNS-01 solver: Route 53 through an IAM role on ROSA, with the IRSA annotation from xref:module-02-cloud-credentials.adoc[Pod Cloud Credentials], or Azure DNS on ARO, where Red Hat documents a service principal.
A Route serves the issued secret through `spec.tls.externalCertificate`, and a Gateway listener names it in `certificateRefs`, so a Gateway's Certificate goes in `openshift-ingress`.
For DNS, point a record for each host at the router's load balancer (a CNAME on ROSA, an A record on ARO), or let the External DNS Operator create records from Routes after you check that it works with your cluster's cloud credentials.
On ROSA, use the AWS Load Balancer Operator instead of the router when you need an ALB with an ACM certificate or AWS WAF.
The Cloud Experts guides for https://cloud.redhat.com/experts/rosa/dynamic-certificates/[ROSA] and https://cloud.redhat.com/experts/aro/cert-manager/[ARO] walk through the issuer setup.

[.validation]
NOTE: *Not validated:* cert-manager, the External DNS Operator and the AWS Load Balancer Operator, which were not run on a cluster.

This Certificate asks for a custom host's certificate from a ClusterIssuer named `letsencrypt-dns01`, which you set up as the guides show:

[source,yaml]
----
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: sample-app-custom
  namespace: sample-app
spec:
  secretName: sample-app-custom-tls
  dnsNames:
  - sample-app.example.com
  issuerRef:
    kind: ClusterIssuer
    name: letsencrypt-dns01
----

The router serves the secret only after its service account may read it:

[source,bash]
----
oc create role secret-reader \
  --verb get,list,watch \
  --resource secrets \
  --resource-name sample-app-custom-tls \
  --namespace sample-app
----

[source,bash]
----
oc create rolebinding secret-reader-binding \
  --role secret-reader \
  --serviceaccount openshift-ingress:router \
  --namespace sample-app
----

This Route serves the secret for the custom host:

[source,yaml]
----
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: sample-app-custom
  namespace: sample-app
spec:
  host: sample-app.example.com
  to:
    kind: Service
    name: sample-app
  port:
    targetPort: 8080
  tls:
    termination: edge
    insecureEdgeTerminationPolicy: Redirect
    externalCertificate:
      name: sample-app-custom-tls
----

== Where Each Wins

[cols="1,1",options="header"]
|===
|ROSA and ARO win |EKS and AKS win

|Nothing to install: HTTPS on a wildcard domain on day one.
|Deep cloud integration: ALB target groups, AWS WAF and Cognito or OIDC authentication on EKS, Application Gateway on AKS.

|One shared load balancer carries every Route, so a new app adds no cloud cost.
|Traffic goes straight from the ALB to pod IPs, with no in-cluster proxy hop on EKS.

|Routes cover TLS modes that Ingress cannot express, such as re-encrypt.
|The EKS Load Balancer Controller and AKS Application Gateway for Containers map Gateway API onto managed L7 load balancers with no in-cluster proxy.

|The router is upgraded and monitored with the cluster.
|You pick and tune the controller, including its version.
|===

== App Teams Will Notice

* Their app gets a host name like `sample-app-sample-app.apps...` without asking for DNS. They can still set a custom host name, which then needs DNS and a certificate, as in <<production-custom-domains,In production: custom domains and certificates>>.
* The router's default timeout is 30 seconds. Long requests need the `haproxy.router.openshift.io/timeout` annotation on the Route.
* The first namespace to claim a host name owns it. Another project cannot take over the same host.
* Ingress manifests from EKS or AKS need their class and annotations reviewed, not just applied.
