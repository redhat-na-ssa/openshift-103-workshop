= Observability

[.validation]
NOTE: Validated on ROSA HCP 4.20 and 4.22 and ARO 4.21 in October 2026.
Steps and statements that were not checked on a live cluster carry a *Not validated* note.
The comparison tables and summaries come from vendor documentation.

On EKS and AKS you choose a monitoring and logging stack and wire it up, usually CloudWatch or Azure Monitor with managed Prometheus.
ROSA and ARO ship Prometheus, Alertmanager and console dashboards, with platform alerts tuned by SRE.
Getting application logs into CloudWatch or Azure Monitor is your job, and this section does it.

In this section you look at what monitoring ships, add the sample application's metrics and an alert rule, then forward its logs to CloudWatch from ROSA and to Azure Monitor Logs from ARO.

== What You Build and What Ships

.Observability stacks
image::module-04-observability-stack.svg["On EKS and AKS you install collectors and agents that send to managed cloud services. On ROSA and ARO, monitoring ships in the cluster and you add the Logging Operator to send logs to CloudWatch or Log Analytics.",width=100%,link=self,window=_blank]

[cols="2,3,3",options="header"]
|===
|Signal |EKS and AKS |ROSA and ARO

|Platform metrics and alerts
|Container Insights or managed Prometheus, as an add-on you enable
|Ship with the cluster, with platform alerts and dashboards

|Application metrics
|Managed Prometheus scrape configuration, or your own Prometheus
|User workload monitoring, with `ServiceMonitor` and `PrometheusRule` objects

|Dashboards
|Amazon or Azure Managed Grafana, or the cloud console
|The OpenShift console, *Observe* menu

|Application logs
|Container Insights agent, or Fluent Bit you run
|Logging Operator and a `ClusterLogForwarder`, which you install and run

|Control plane logs
|A switch on the cluster, to CloudWatch or diagnostic settings
|ROSA: a log forwarder in OpenShift Cluster Manager. ARO: the API server audit log, through the Logging Operator
|===

The optional box in the diagram is Prometheus remote write, which this workshop does not set up: on ROSA the cluster's Prometheus can send metrics to Amazon Managed Service for Prometheus, and on ARO you check with support first (see What Matters).

== On EKS and AKS

* EKS: CloudWatch Container Insights as an add-on, and Amazon Managed Service for Prometheus with a managed collector.
* AKS: Azure Monitor Container Insights and Azure Monitor managed Prometheus, with Azure Managed Grafana.

=== Exercise 1: Look at What Ships

The platform monitoring stack runs in its own namespace:

[source,bash]
----
oc get pods \
  --namespace openshift-monitoring
----

Count the alert rules that come with the platform:

[source,bash]
----
oc get prometheusrules \
  --all-namespaces \
  --output json \
  | jq '[.items[].spec.groups[].rules[]
      | select(.alert)] | length'
----

Well over a hundred rules cover the nodes, the control plane and every platform Operator.
You did not write or install any of them, and they are updated with each OpenShift release.

In the web console, open *Observe* > *Dashboards* and pick *Kubernetes / Compute Resources / Namespace (Pods)*, then the `sample-app` namespace.
Then open *Observe* > *Alerting*.
The `Watchdog` alert always fires: it proves that alerting works end to end.

.EKS and AKS (reference only)
[%collapsible]
====
EKS, turn on Container Insights with the CloudWatch Observability add-on:

[source,bash]
----
aws eks create-addon \
  --cluster-name my-cluster \
  --addon-name amazon-cloudwatch-observability
----

AKS, turn on managed Prometheus and Container Insights:

[source,bash]
----
az aks update \
  --resource-group my-rg \
  --name my-cluster \
  --enable-azure-monitor-metrics
----

[source,bash]
----
az aks enable-addons \
  --resource-group my-rg \
  --name my-cluster \
  --addons monitoring
----

The alert rules are yours to write, or to import from the recommended sets.

=== Exercise 2: Turn On User Workload Monitoring

Platform monitoring watches the platform.
Your applications' metrics need user workload monitoring, a second Prometheus that reads `ServiceMonitor` and `PrometheusRule` objects in your projects.

Check whether it runs:

[source,bash]
----
oc get pods \
  --namespace openshift-user-workload-monitoring
----

If pods are listed, skip to the next exercise.
If not, check whether the monitoring ConfigMap exists:

[source,bash]
----
oc get configmap cluster-monitoring-config \
  --namespace openshift-monitoring
----

If it does not exist, create it:

[source,bash]
----
oc apply --filename - <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
EOF
----

If it exists, add the line `enableUserWorkload: true` at the top level of its `config.yaml` key:

[source,bash]
----
oc edit configmap cluster-monitoring-config \
  --namespace openshift-monitoring
----

Wait for the user workload Prometheus to start:

[source,bash]
----
oc get pods \
  --namespace openshift-user-workload-monitoring \
  --watch
----

Press Ctrl+C when the `prometheus-user-workload` and `thanos-ruler-user-workload` pods are `Running`.

=== Exercise 3: Scrape the Sample Application

The sample application serves Prometheus metrics on `/metrics`, on the same port as its API.
Tell user workload monitoring to scrape it:

[source,bash]
----
oc apply --filename - <<'EOF'
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: sample-app
  namespace: sample-app
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: sample-app
  endpoints:
  - port: http
    path: /metrics
    interval: 30s
EOF
----

The network policy from xref:module-03-pod-networking.adoc[Pod Networking and Policy] already lets user workload monitoring reach the application.
Wait a minute, so that Prometheus scrapes the application at least once before you send requests.

Send some requests through the application's route:

[source,bash]
----
APP_HOST=$(oc get route sample-app \
  --namespace sample-app \
  --output jsonpath='{.spec.host}')
----

[source,bash]
----
for i in $(seq 1 100); do
  curl -s -o /dev/null "https://${APP_HOST}/"
done
----

If you skipped xref:module-02-cloud-credentials.adoc[Pod Cloud Credentials], every request to `/` returns `500`, because the application has no bucket or container to read.

In the console, open *Observe* > *Metrics* and run this query for the request rate by status code:

[source,promql]
----
sum by (code) (
  rate(sample_app_requests_total{namespace="sample-app"}[5m])
)
----

And this one for the 95th percentile latency:

[source,promql]
----
histogram_quantile(0.95,
  sum by (le) (
    rate(sample_app_request_duration_seconds_bucket{
      namespace="sample-app"}[5m])
  )
)
----

The same queries work from the command line, through the Thanos Querier, the query front end over platform and user workload Prometheus.
ROSA and ARO both expose it as a route:

[source,bash]
----
THANOS_HOST=$(oc get route thanos-querier \
  --namespace openshift-monitoring \
  --output jsonpath='{.spec.host}')
----

[source,bash]
----
curl -sG "https://${THANOS_HOST}/api/v1/query" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  --data-urlencode \
    'query=sum(sample_app_requests_total{namespace="sample-app"})' \
  | jq '.data.result'
----

.EKS and AKS (reference only)
[%collapsible]
====
With the Amazon Managed Service for Prometheus managed collector, scrape targets live in the scraper's Prometheus configuration, not in `ServiceMonitor` objects.
With the Prometheus Operator installed yourself, the `ServiceMonitor` above works as is.

Azure Monitor managed Prometheus reads its own copy of the CRD, in a different API group:

[source,yaml]
----
apiVersion: azmonitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: sample-app
  namespace: sample-app
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: sample-app
  endpoints:
  - port: http
    path: /metrics
----

=== Exercise 4: Add an Alert Rule

Alert when the application fails to read from its object store, which uses the credentials from xref:module-02-cloud-credentials.adoc[Pod Cloud Credentials]:

[source,bash]
----
oc apply --filename - <<'EOF'
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: sample-app
  namespace: sample-app
spec:
  groups:
  - name: sample-app
    rules:
    - alert: SampleAppObjectStoreErrors
      expr: |
        increase(sample_app_object_store_errors_total[5m]) > 0
      for: 1m
      labels:
        severity: warning
      annotations:
        summary: The sample app cannot read its object store.
EOF
----

In the console, open *Observe* > *Alerting* > *Alerting rules* and filter on *Source: User*.
The rule is listed, with `-` in its alert state, while the application reads its bucket or container without errors.
Without the Module 2 credentials every request to `/` fails, so the rule fires a minute after you send requests, as in Exercise 3, and shows it working.

==== Optional: See It Fire

If the application reads its bucket or container without errors, break the read on purpose for a few minutes and watch the alert go off.

[tabs]
======
ROSA (AWS)::
+
--
Save the bucket name:

[source,bash]
----
SAVED_BUCKET=$(oc set env deployment/sample-app \
  --namespace sample-app \
  --list \
  | sed -n 's/^BUCKET=//p')
----

Point the application at a bucket it may not read:

[source,bash]
----
oc set env deployment/sample-app \
  --namespace sample-app \
  BUCKET="$SAVED_BUCKET-missing"
----
--
ARO (Azure)::
+
--
Point the application at a container that does not exist:

[source,bash]
----
oc set env deployment/sample-app \
  --namespace sample-app \
  CONTAINER=missing
----
--
======

Wait for the new pod:

[source,bash]
----
oc rollout status deployment/sample-app \
  --namespace sample-app
----

Wait a minute, so that Prometheus scrapes the new pod once, then send requests with the loop from Exercise 3:

[source,bash]
----
for i in $(seq 1 100); do
  curl -s -o /dev/null "https://${APP_HOST}/"
done
----

Every request now returns `500`.
After about two minutes, ask the Thanos Querier for the alert's state:

[source,bash]
----
curl -sG "https://${THANOS_HOST}/api/v1/query" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  --data-urlencode \
    'query=ALERTS{alertname="SampleAppObjectStoreErrors"}' \
  | jq '.data.result[].metric.alertstate'
----

It prints `"pending"` during the rule's one-minute `for` period, then `"firing"`, once for each of the application's pods.
The console's *Observe* > *Alerting* page shows the same alert.

Put the setting back:

[tabs]
======
ROSA (AWS)::
+
--
[source,bash]
----
oc set env deployment/sample-app \
  --namespace sample-app \
  BUCKET="$SAVED_BUCKET"
----
--
ARO (Azure)::
+
--
[source,bash]
----
oc set env deployment/sample-app \
  --namespace sample-app \
  CONTAINER=sample-app
----
--
======

The alert resolves about five minutes after the last error, when the errors leave the rule's five-minute window.

User-defined alerts go to the platform Alertmanager by default.
Sending them to your team's channels means configuring Alertmanager receivers, which you can delegate to projects with a separate user workload Alertmanager.

=== Exercise 5: Install the Logging Operator

Logging is not part of the platform.
You install the Red Hat OpenShift Logging Operator, which runs a Vector collector on every node, and tell it where to send logs.
This workshop forwards only the sample application's logs, which keeps the cost low.

Create the namespace, OperatorGroup and Subscription:

[source,bash]
----
oc apply --filename - <<'EOF'
apiVersion: v1
kind: Namespace
metadata:
  name: openshift-logging
  labels:
    openshift.io/cluster-monitoring: "true"
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: cluster-logging
  namespace: openshift-logging
spec:
  upgradeStrategy: Default
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: cluster-logging
  namespace: openshift-logging
spec:
  channel: stable-6.6
  installPlanApproval: Automatic
  name: cluster-logging
  source: redhat-operators
  sourceNamespace: openshift-marketplace
EOF
----

On ROSA the `openshift-logging` namespace already exists, and the command only adds the label.
There `oc apply` warns that the namespace is missing the `last-applied-configuration` annotation; that warning is harmless.
On ARO the command creates the namespace, with no warning.

Wait for the Operator to install:

[source,bash]
----
oc get csv \
  --namespace openshift-logging \
  --watch
----

Press Ctrl+C when the `cluster-logging` ClusterServiceVersion shows `Succeeded`.

The collector runs under a service account that you grant permission to read application logs.
Create both before you create a log forwarder:

[source,bash]
----
oc create serviceaccount logging-collector \
  --namespace openshift-logging
----

[source,bash]
----
oc adm policy add-cluster-role-to-user \
  collect-application-logs \
  --serviceaccount logging-collector \
  --namespace openshift-logging
----

=== Exercise 6: Forward Application Logs to Your Cloud

The collector sends the sample application's logs to your cloud's log service: CloudWatch from ROSA, Azure Monitor Logs from ARO.

[tabs]
======
ROSA (AWS)::
+
--
The collector writes to CloudWatch with an IAM role, which it assumes with its service account token.
This is the same STS pattern as in xref:module-02-cloud-credentials.adoc[Pod Cloud Credentials].

Work in your ROSA terminal.
The steps use the `CLUSTER` variable from xref:module-01-who-manages-what.adoc#before-you-start[Before You Start].
If you open a new terminal, set it again:

[source,bash]
----
export CLUSTER=<your-rosa-cluster-name>
----

[discrete]
==== Collect the Values

Collect the values you need; they are the same as in Module 2:

[source,bash]
----
AWS_REGION=$(rosa describe cluster \
  --cluster "$CLUSTER" \
  --output json \
  | jq -r '.region.id')
----

[source,bash]
----
OIDC_PROVIDER=$(oc get authentication.config.openshift.io \
  cluster \
  --output jsonpath='{.spec.serviceAccountIssuer}' \
  | sed 's|^https://||')
----

[source,bash]
----
ACCOUNT_ID=$(aws sts get-caller-identity \
  --query Account \
  --output text)
----

[discrete]
==== Create the IAM Role

Write a trust policy for the collector's service account:

[source,bash]
----
cat > logging-trust.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated":
        "arn:aws:iam::${ACCOUNT_ID}:oidc-provider/${OIDC_PROVIDER}"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "${OIDC_PROVIDER}:sub":
          "system:serviceaccount:openshift-logging:logging-collector"
      }
    }
  }]
}
EOF
----

Write a permissions policy that only allows log groups named after your cluster:

[source,bash]
----
LOG_GROUPS="arn:aws:logs:${AWS_REGION}:${ACCOUNT_ID}:log-group"
----

[source,bash]
----
cat > logging-policy.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "logs:CreateLogGroup",
      "logs:CreateLogStream",
      "logs:DescribeLogGroups",
      "logs:DescribeLogStreams",
      "logs:PutLogEvents",
      "logs:PutRetentionPolicy"
    ],
    "Resource": "${LOG_GROUPS}:workshop-${CLUSTER}*"
  }]
}
EOF
----

Create the role and attach the policy:

[source,bash]
----
aws iam create-role \
  --role-name "${CLUSTER}-logging" \
  --assume-role-policy-document file://logging-trust.json
----

[source,bash]
----
aws iam put-role-policy \
  --role-name "${CLUSTER}-logging" \
  --policy-name cloudwatch-logs \
  --policy-document file://logging-policy.json
----

[discrete]
==== Create the Log Forwarder

Store the role's ARN in a secret that the log forwarder reads:

[source,bash]
----
LOGGING_ROLE_ARN=$(aws iam get-role \
  --role-name "${CLUSTER}-logging" \
  --query Role.Arn \
  --output text)
----

[source,bash]
----
oc create secret generic cloudwatch-role \
  --namespace openshift-logging \
  --from-literal role_arn="$LOGGING_ROLE_ARN"
----

Create the log forwarder.
It reads only the `sample-app` namespace and writes to a log group named `workshop-<cluster>.application`:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: workshop
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  inputs:
  - name: sample-app
    type: application
    application:
      includes:
      - namespace: sample-app
  outputs:
  - name: cloudwatch
    type: cloudwatch
    cloudwatch:
      region: ${AWS_REGION}
      groupName: 'workshop-${CLUSTER}.{.log_type||"none"}'
      authentication:
        type: iamRole
        iamRole:
          roleARN:
            secretName: cloudwatch-role
            key: role_arn
          token:
            from: serviceAccount
  pipelines:
  - name: sample-app-to-cloudwatch
    inputRefs:
    - sample-app
    outputRefs:
    - cloudwatch
EOF
----

[discrete]
==== Check the Logs

Check that the forwarder is ready and its collector pods run:

[source,bash]
----
oc get clusterlogforwarder workshop \
  --namespace openshift-logging \
  --output jsonpath='{.status.conditions[?(@.type=="Ready")].status}'
----

[source,bash]
----
oc get pods \
  --namespace openshift-logging
----

Send a few requests to the application, as in Exercise 3, then read the log group:

[source,bash]
----
aws logs tail "workshop-${CLUSTER}.application" \
  --region "$AWS_REGION" \
  --since 10m
----

Each event is a JSON document with the log line in `message` and the pod's metadata in `kubernetes`.

If the forwarder is ready but nothing arrives, read the collector's log:

[source,bash]
----
oc logs \
  --namespace openshift-logging \
  daemonset/workshop \
  | grep WARN \
  | tail -5
----

`InvalidIdentityTokenException` or `AccessDenied` from `AssumeRoleWithWebIdentity` means the role's trust policy does not match the cluster's OIDC provider or the service account name.
--
ARO (Azure)::
+
--
The collector writes to a Log Analytics workspace through the Azure Monitor Logs Ingestion API.
That needs a custom table, a data collection endpoint and a data collection rule, and an identity allowed to send to the rule.
The identity is a user-assigned managed identity that trusts the collector's service account, the same trust idea as in xref:module-02-cloud-credentials.adoc[Pod Cloud Credentials].
The token differs: the collector does not use the workload identity webhook's token, whose audience is `api://AzureADTokenExchange`.
It projects its own service account token with the audience `openshift`, the same audience ROSA uses, so the federated credential must trust that audience.

Work in your ARO terminal.
The steps use the `CLUSTER` and `RESOURCE_GROUP` variables from xref:module-01-who-manages-what.adoc#before-you-start[Before You Start].
If you open a new terminal, set them again:

[source,bash]
----
export CLUSTER=<your-aro-cluster-name>
----

[source,bash]
----
export RESOURCE_GROUP=<your-resource-group>
----

[discrete]
==== Collect the Values

Look up the cluster's region and OIDC issuer:

[source,bash]
----
LOCATION=$(az aro show \
  --resource-group "$RESOURCE_GROUP" \
  --name "$CLUSTER" \
  --query location \
  --output tsv)
----

[source,bash]
----
OIDC_ISSUER=$(oc get authentication.config.openshift.io \
  cluster \
  --output jsonpath='{.spec.serviceAccountIssuer}')
----

[source,bash]
----
echo "$OIDC_ISSUER"
----

If it prints nothing, the cluster uses a service principal and has no workload identity, as in xref:module-02-cloud-credentials.adoc[Pod Cloud Credentials].
The federated credential step below then fails and no logs arrive, so read the rest of this exercise without running it.

[discrete]
==== Create the Workspace and Table

Create a Log Analytics workspace and a custom table for the application's logs:

[source,bash]
----
az monitor log-analytics workspace create \
  --resource-group "$RESOURCE_GROUP" \
  --workspace-name sample-app-logs \
  --location "$LOCATION"
----

[source,bash]
----
az monitor log-analytics workspace table create \
  --resource-group "$RESOURCE_GROUP" \
  --workspace-name sample-app-logs \
  --name SampleAppLogs_CL \
  --columns \
    TimeGenerated=datetime \
    Message=string \
    Level=string \
    Namespace=string \
    Pod=string
----

[discrete]
==== Create the Data Collection Endpoint and Rule

Create a data collection endpoint, which is the URL the collector sends to:

[source,bash]
----
az monitor data-collection endpoint create \
  --resource-group "$RESOURCE_GROUP" \
  --name sample-app-dce \
  --location "$LOCATION" \
  --public-network-access Enabled
----

Collect the IDs the rule needs:

[source,bash]
----
DCE_ID=$(az monitor data-collection endpoint show \
  --resource-group "$RESOURCE_GROUP" \
  --name sample-app-dce \
  --query id \
  --output tsv)
----

[source,bash]
----
WORKSPACE_ID=$(az monitor log-analytics workspace show \
  --resource-group "$RESOURCE_GROUP" \
  --workspace-name sample-app-logs \
  --query id \
  --output tsv)
----

Write the data collection rule.
It declares the fields the collector sends, and a transformation that maps them to the table's columns.
Set the transformation first:

[source,bash]
----
TRANSFORM="source | project TimeGenerated,\
 Message = message, Level = level,\
 Namespace = tostring(kubernetes.namespace_name),\
 Pod = tostring(kubernetes.pod_name)"
----

Then write the rule:

[source,bash]
----
cat > sample-app-dcr.json <<EOF
{
  "location": "${LOCATION}",
  "properties": {
    "dataCollectionEndpointId": "${DCE_ID}",
    "streamDeclarations": {
      "Custom-SampleAppLogs_CL": {
        "columns": [
          {"name": "TimeGenerated", "type": "datetime"},
          {"name": "message", "type": "string"},
          {"name": "level", "type": "string"},
          {"name": "kubernetes", "type": "dynamic"}
        ]
      }
    },
    "destinations": {
      "logAnalytics": [{
        "name": "workspace",
        "workspaceResourceId": "${WORKSPACE_ID}"
      }]
    },
    "dataFlows": [{
      "streams": ["Custom-SampleAppLogs_CL"],
      "destinations": ["workspace"],
      "outputStream": "Custom-SampleAppLogs_CL",
      "transformKql": "${TRANSFORM}"
    }]
  }
}
EOF
----

Create the rule:

[source,bash]
----
az monitor data-collection rule create \
  --resource-group "$RESOURCE_GROUP" \
  --name sample-app-dcr \
  --location "$LOCATION" \
  --rule-file sample-app-dcr.json
----

[discrete]
==== Create the Managed Identity

Create the managed identity and let it trust the collector's service account:

[source,bash]
----
az identity create \
  --resource-group "$RESOURCE_GROUP" \
  --name sample-app-logging
----

[source,bash]
----
az identity federated-credential create \
  --resource-group "$RESOURCE_GROUP" \
  --identity-name sample-app-logging \
  --name logging-collector \
  --issuer "$OIDC_ISSUER" \
  --subject \
    system:serviceaccount:openshift-logging:logging-collector \
  --audiences openshift
----

Allow the identity to send to the rule:

[source,bash]
----
DCR_ID=$(az monitor data-collection rule show \
  --resource-group "$RESOURCE_GROUP" \
  --name sample-app-dcr \
  --query id \
  --output tsv)
----

[source,bash]
----
PRINCIPAL_ID=$(az identity show \
  --resource-group "$RESOURCE_GROUP" \
  --name sample-app-logging \
  --query principalId \
  --output tsv)
----

[source,bash]
----
az role assignment create \
  --assignee-object-id "$PRINCIPAL_ID" \
  --assignee-principal-type ServicePrincipal \
  --role "Monitoring Metrics Publisher" \
  --scope "$DCR_ID"
----

[discrete]
==== Create the Log Forwarder

Collect the values the log forwarder needs:

[source,bash]
----
DCE_URL=$(az monitor data-collection endpoint show \
  --resource-group "$RESOURCE_GROUP" \
  --name sample-app-dce \
  --query logsIngestion.endpoint \
  --output tsv)
----

[source,bash]
----
DCR_IMMUTABLE_ID=$(az monitor data-collection rule show \
  --resource-group "$RESOURCE_GROUP" \
  --name sample-app-dcr \
  --query immutableId \
  --output tsv)
----

[source,bash]
----
CLIENT_ID=$(az identity show \
  --resource-group "$RESOURCE_GROUP" \
  --name sample-app-logging \
  --query clientId \
  --output tsv)
----

[source,bash]
----
TENANT_ID=$(az account show \
  --query tenantId \
  --output tsv)
----

Create the log forwarder:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: workshop
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  inputs:
  - name: sample-app
    type: application
    application:
      includes:
      - namespace: sample-app
  outputs:
  - name: log-analytics
    type: azureLogsIngestion
    azureLogsIngestion:
      url: ${DCE_URL}
      dcrImmutableId: ${DCR_IMMUTABLE_ID}
      streamName: Custom-SampleAppLogs_CL
      authentication:
        type: workloadIdentity
        workloadIdentity:
          tenantId: ${TENANT_ID}
          clientId: ${CLIENT_ID}
          token:
            from: serviceAccount
  pipelines:
  - name: sample-app-to-log-analytics
    inputRefs:
    - sample-app
    outputRefs:
    - log-analytics
EOF
----

[discrete]
==== Check the Logs

Check that the forwarder is ready and its collector pods run:

[source,bash]
----
oc get clusterlogforwarder workshop \
  --namespace openshift-logging \
  --output jsonpath='{.status.conditions[?(@.type=="Ready")].status}'
----

[source,bash]
----
oc get pods \
  --namespace openshift-logging
----

Send a few requests to the application, as in Exercise 3.
The first records can take several minutes to appear in a new table.
Then query the table:

[source,bash]
----
WORKSPACE_GUID=$(az monitor log-analytics workspace show \
  --resource-group "$RESOURCE_GROUP" \
  --workspace-name sample-app-logs \
  --query customerId \
  --output tsv)
----

[source,bash]
----
az monitor log-analytics query \
  --workspace "$WORKSPACE_GUID" \
  --analytics-query \
    'SampleAppLogs_CL | sort by TimeGenerated desc | take 10' \
  --output table
----

The `Message` column holds the application's own JSON log line, which you can unpack in a query with `parse_json`.

If the forwarder is ready but nothing arrives, read the collector's log:

[source,bash]
----
oc logs \
  --namespace openshift-logging \
  daemonset/workshop \
  | grep -E 'WARN|ERROR' \
  | tail -5
----

`AADSTS700211` or `AADSTS700213`, no matching federated identity record, means the federated credential's issuer, subject or audience does not match the collector's token.
`AADSTS70025`, no configured federated identity credentials, means the federated credential was never created.

Older guides use the `azureMonitor` output type with a workspace shared key.
It sends through the HTTP Data Collector API, which Microsoft stopped supporting in September 2026, and the output is deprecated in OpenShift Logging 6.6.

.In production: API audit logs on ARO (reference only)
[%collapsible]
====
The same forwarder can send the API server audit logs to Log Analytics, for Microsoft Sentinel or your security team.
Give them their own table: they are sensitive, they need the `collect-audit-logs` cluster role, and their volume adds noticeable Log Analytics charges.
A `kubeAPIAudit` filter on the pipeline can drop the events you do not need: an idle validation cluster sent about 1,000 audit events a minute.

Grant the collector's service account the audit role:

[source,bash]
----
oc adm policy add-cluster-role-to-user \
  collect-audit-logs \
  --serviceaccount logging-collector \
  --namespace openshift-logging
----

Create a second custom table, for example `AroAuditLogs_CL`, and add a matching stream and data flow to the data collection rule, as you did for `SampleAppLogs_CL`.
Audit events have no `message` or `level` field, so declare the audit fields you keep instead, for example `verb`, `requestURI`, and `user` and `objectRef` as `dynamic`, and map them in the transformation, for example `User = tostring(user.username)` and `Resource = tostring(objectRef.resource)`.
A changed rule can take about 20 minutes to reach the ingestion endpoint.
Until it does, the collector log shows `InvalidStream` for the new stream and drops those events.

Then add these entries to the `inputs`, `outputs` and `pipelines` lists of the `workshop` forwarder:

[source,yaml]
----
spec:
  inputs:
  - name: api-audit
    type: audit
    audit:
      sources:
      - kubeAPI
      - openshiftAPI
  outputs:
  - name: log-analytics-audit
    type: azureLogsIngestion
    azureLogsIngestion:
      url: <dce-url>
      dcrImmutableId: <dcr-immutable-id>
      streamName: Custom-AroAuditLogs_CL
      authentication:
        type: workloadIdentity
        workloadIdentity:
          tenantId: <tenant-id>
          clientId: <client-id>
          token:
            from: serviceAccount
  pipelines:
  - name: audit-to-log-analytics
    inputRefs:
    - api-audit
    outputRefs:
    - log-analytics-audit
----

.In production: ROSA control plane and audit logs (reference only)
[%collapsible]
====
ROSA control plane logs, including the API server's record of every request, leave through a log forwarder that Red Hat runs outside your cluster, to a CloudWatch log group or an S3 bucket.
Turn it on when you create the cluster: it cannot capture logs from before it was enabled.
Forwarding and storing these logs adds CloudWatch or S3 charges.

The commands use the variables from the ROSA tab of Exercise 6.
For CloudWatch, create the log group:

[source,bash]
----
aws logs create-log-group \
  --log-group-name "rosa-${CLUSTER}-control-plane"
----

Red Hat's central log distribution role writes through a role in your account, whose name must start with `CustomerLogDistribution-`.
Write the role's trust policy, with the principal from the Red Hat documentation:

[source,bash]
----
cat > log-distribution-trust.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS":
        "arn:aws:iam::859037107838:role/ROSA-CentralLogDistributionRole-241c1a86"
    },
    "Action": "sts:AssumeRole"
  }]
}
EOF
----

[source,bash]
----
aws iam create-role \
  --role-name "CustomerLogDistribution-${CLUSTER}" \
  --assume-role-policy-document file://log-distribution-trust.json
----

Allow it to write to the log group:

[source,bash]
----
cat > log-distribution-policy.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["logs:CreateLogStream", "logs:PutLogEvents"],
    "Resource": "${LOG_GROUPS}:rosa-${CLUSTER}-control-plane:*"
  }, {
    "Effect": "Allow",
    "Action": ["logs:DescribeLogGroups", "logs:DescribeLogStreams"],
    "Resource": "*"
  }]
}
EOF
----

[source,bash]
----
aws iam put-role-policy \
  --role-name "CustomerLogDistribution-${CLUSTER}" \
  --policy-name control-plane-logs \
  --policy-document file://log-distribution-policy.json
----

Write the forwarder's configuration.
The `api` group records every request made to the cluster, and `authentication` records logins and token requests:

[source,bash]
----
cat > control-plane-logs.yaml <<EOF
cloudwatch:
  cloudwatch_log_role_arn: "arn:aws:iam::${ACCOUNT_ID}:role/CustomerLogDistribution-${CLUSTER}"
  cloudwatch_log_group_name: "rosa-${CLUSTER}-control-plane"
  groups:
    - api
    - authentication
EOF
----

Create the forwarder on an existing cluster.
`rosa create cluster` takes the same `--log-fwd-config` flag, which is how you turn it on at creation:

[source,bash]
----
rosa create log-forwarder \
  --cluster "$CLUSTER" \
  --log-fwd-config control-plane-logs.yaml
----

`rosa list log-forwarders` shows it `ready`, and logs arrive within minutes, in one log stream per control plane pod, such as `kube-apiserver-...`, `openshift-apiserver-...` and `oauth-openshift-...`, with the audit events among them.
On an idle ROSA 4.22 validation cluster, these two groups sent about 11 MB in ten minutes, roughly 1.6 GB a day.
Remove the forwarder with `rosa delete log-forwarder` and the ID that `rosa list log-forwarders` prints.

S3 needs no IAM role: a bucket policy lets Red Hat's role write objects, and the configuration file names the bucket in an `s3` section instead.
====

.EKS and AKS (reference only)
[%collapsible]
====
On EKS, the CloudWatch Observability add-on from Exercise 1 also ships container logs, with Fluent Bit, to log groups under `/aws/containerinsights/<cluster>/`.
Its agent uses the node IAM role or an EKS Pod Identity association:

[source,bash]
----
aws eks create-pod-identity-association \
  --cluster-name my-cluster \
  --namespace amazon-cloudwatch \
  --service-account cloudwatch-agent \
  --role-arn arn:aws:iam::111122223333:role/my-cw-role
----

EKS control plane logs are a cluster setting:

[source,bash]
----
aws eks update-cluster-config \
  --name my-cluster \
  --logging \
    '{"clusterLogging":[{"types":["api","audit"],"enabled":true}]}'
----

On AKS, Container Insights from Exercise 1 already sends container logs to the `ContainerLogV2` table in Log Analytics, with no table or rule to write.
Control plane logs go to Log Analytics through diagnostic settings:

[source,bash]
----
az monitor diagnostic-settings create \
  --name aks-control-plane \
  --resource <aks-cluster-resource-id> \
  --workspace <workspace-resource-id> \
  --logs '[{"category":"kube-audit-admin","enabled":true}]'
----

ARO can get the same Container Insights experience only by connecting the cluster to Azure Arc first.

== What Matters

* Monitoring splits along Module 1's xref:module-01-who-manages-what.adoc#_the_responsibility_line[responsibility line]: SRE runs platform monitoring, while user workload monitoring, your alert rules, alert receivers and log forwarding are yours.
* Platform monitoring is preconfigured and managed by Red Hat.
User workload monitoring covers your applications, and you may need to turn it on.
* Alertmanager sends no notifications by default, and Red Hat SRE watches the platform with its own tooling.
On day one, configure a receiver, such as PagerDuty, Slack or a webhook, for the platform and user alerts your team owns; on ARO, also set Azure Resource Health alerts on the cluster resource.
Resource Health reports maintenance up to two weeks ahead, maintenance in progress, actions you need to take and an unreachable API server, but it alerts nobody until you create alert rules, and SRE posts its advisories in Service Health.
* For fleet or long-term metrics on ROSA, the platform Prometheus can remote write to Amazon Managed Service for Prometheus with SigV4 and add a cluster ID label to each series.
Do not run a second Prometheus instance of your own: ROSA does not support it.
* CloudWatch Container Insights also runs on ROSA, installed with AWS's Helm chart in its ROSA mode rather than with the EKS add-on.
* Application logging (Vector, optionally Loki for in-cluster storage) is an optional Operator that you install, upgrade and run.
* Log forwarding uses the same short-lived credentials as your applications: an IAM role through STS on ROSA, a managed identity through workload identity on ARO.
* Azure Monitor Container Insights and managed Prometheus, whose metrics Azure Managed Grafana reads, reach ARO through Azure Arc, which Microsoft lists as supported for ARO.
ARO's support policy does not list remote write among the allowed changes to the default Prometheus, so check with support before you send its metrics to Azure Monitor that way.
* ROSA control plane logs, such as the API server audit log, are not on your nodes: you forward them to CloudWatch or S3 with a log forwarder in OpenShift Cluster Manager.
Turn it on when you create the cluster, because it cannot capture logs from before it was enabled.

== Where Each Wins

[cols="1,1",options="header"]
|===
|ROSA and ARO win |EKS and AKS win

|Useful metrics, dashboards and platform alerts from the first minute.
|Managed metrics backends with long-term storage are native, with nothing in the cluster to run.
ROSA reaches them with remote write, and ARO through Azure Arc.

|The same monitoring and logging stack, and the same `ServiceMonitor` objects, on both clouds.
|Native cloud console integration; on ARO, Azure Monitor needs Arc or a log forwarder you build.

|Platform alert rules are written and updated by Red Hat with each release.
|Container logs reach CloudWatch or Log Analytics without a table, rule or forwarder to write.
|===

== App Teams Will Notice

* App teams write their own `ServiceMonitor` and `PrometheusRule` objects in their projects.
Grant them the `monitoring-edit` role in their projects so they can.
* Logs arrive with the application's line as a string field next to Kubernetes metadata.
Structured JSON logs make queries in CloudWatch and Log Analytics much easier.
* A default-deny network policy must allow user workload monitoring, or scraping stops.

== Check Your Understanding

These questions cover the whole module.
Try each one before you open its answer.

. A team runs one replica with a PodDisruptionBudget of `minAvailable: 1`.
What happens at the next upgrade of its nodes?
+
.Answer
[%collapsible]
====
The drain cannot evict the pod, so the update holds on that node.
On ROSA it waits with no time limit unless the machine pool has a node drain grace period.
Run at least two replicas, so the budget can let one go, and find such budgets before an upgrade, as in xref:module-04-upgrades.adoc#ex-module-04-upgrades-4[Upgrades Exercise 4].
====

. After a traffic spike, pods stay `Pending` and no new node joins.
Where do you look?
+
.Answer
[%collapsible]
====
At the pool's maximum size (the machine pool's autoscaling limits on ROSA, the MachineAutoscaler on ARO), at the cloud quota for its instance type, and at whether the pod's node selector and tolerations fit the pool.
The cluster autoscaler adds nodes only to a pool the pending pod can run on, as in xref:module-04-scaling-nodes.adoc#ex-module-04-scaling-nodes-3[Scaling Nodes Exercise 3].
====

. Your new alert rule fires, but nobody is notified.
Why?
+
.Answer
[%collapsible]
====
Alertmanager sends no notifications until you configure a receiver, so the alert shows only in the console.
Add receivers to the platform Alertmanager, or let projects route their own alerts with a separate user workload Alertmanager, as xref:module-04-observability.adoc#ex-module-04-observability-4[Exercise 4] mentions.
