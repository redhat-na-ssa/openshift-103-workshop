= Workshop Instructor

This page is for the instructor who runs a delivery of the workshop.

== What the Workshop Covers

The workshop is for platform engineers who run Amazon EKS or Azure AKS today and now operate ROSA or ARO.
They should be comfortable with `kubectl` and the `aws` or `az` CLI.
Afterwards they can map their EKS and AKS habits to ROSA and ARO, as the workshop's xref:rosa-and-aro:index.adoc#_expectations[Expectations] list.

== Environment and Requirements

Each workshop lists the cluster components, Operators, command-line tools, roles and access it needs on its own page.
Prepare everything for the workshops you deliver:

* xref:rosa-and-aro:setup-requirements.adoc[OpenShift on ROSA and ARO]
// add-workshop.py adds workshops above this line

Each attendee runs the hands-on steps on one cluster, ROSA or ARO, whichever their team runs, and reads the other tab for comparison.
An attendee whose team runs both can have one of each and run every step on both, as xref:rosa-and-aro:index.adoc#_how_the_workshop_works[How the Workshop Works] and xref:rosa-and-aro:setup-requirements.adoc[Setup Requirements] describe.
Several exercises change cluster-wide settings, so each attendee or pair needs a cluster of their own.

Shared by all the workshops: attendees who don't want to install the command-line tools run the workshop CLI tools image on the cluster, as xref:cli-tools.adoc[Shared CLI tools] describes.
Make sure attendees can pull that image, or mirror it for a disconnected cluster.

[#plan-the-clusters]
=== Plan the Clusters

Most of the lead time comes before the first create command.

* Request quota as soon as you know how many clusters you need.
Each ARO cluster needs 44 vCPUs to install, in the regional total and in the VM family, and a new subscription has less.
An AWS account that has not run ROSA before needs 32 vCPUs of On-Demand Standard instances, where the default is 5.
Azure can refuse a request in a region that is short of capacity, so pick a fallback region before you need one.
* Find out who has to act, and ask them early.
ROSA needs a Red Hat organization administrator for the `ocm-role`, an AWS administrator to enable ROSA and create the account roles, and a `user-role` for each person who creates clusters.
ARO needs someone with `Contributor` and `User Access Administrator`, or `Owner`, because the install creates role assignments.
* Allow for the create itself: about 10 minutes for a ROSA cluster, plus about 5 if `rosa create network` builds its VPC, and about 45 minutes for an ARO cluster, which took about an hour when the workshop was validated.
* Create the clusters close to the day.
Neither ROSA nor ARO can be stopped, so a cluster is billed from the moment you create it until you delete it.
* Sign in to `rosa` on the day, not the day before: a `rosa login` session lasts about 10 hours.

xref:rosa-and-aro:module-01-living-with-the-service.adoc[Living With the Service] has the details behind each of these.

[#setup-checklist]
=== Setup Checklist

Work through xref:rosa-and-aro:setup-requirements.adoc[Setup Requirements] for every cluster, then check these items:

* [ ] Each attendee or pair has their own cluster, built as xref:rosa-and-aro:setup-requirements.adoc#_cluster[Cluster] describes: ROSA with hosted control planes on 4.22 or later with its own OIDC config, or ARO created with managed identities and a Red Hat pull secret.
* [ ] Module 4 has room to grow, counted in vCPUs: three more nodes of the scale-lab instance type on both clouds, and on ROSA up to 16 vCPUs for the Karpenter NodePool.
On Azure, check the quota for the worker VM family and the regional total.
* [ ] Every attendee has the roles in xref:rosa-and-aro:setup-requirements.adoc#_attendee_accounts_projects_and_roles[Attendee Accounts, Projects and Roles].
On ROSA, "cluster administrator" means `cluster-admin`, not `dedicated-admin`.
Several exercises need it, such as the `openshift-gitops-operator` namespace in What Ships and the Gateway API in Exposing an App.
* [ ] On ARO, the Entra ID tenant lets users consent to the new app registration, or a tenant administrator is ready to grant admin consent for it.
* [ ] Every workstation has the tools in xref:rosa-and-aro:setup-requirements.adoc#_attendee_workstation[Attendee Workstation], and a bash or zsh shell on Linux or macOS, or WSL on Windows.
The commands use bash syntax, and Upgrades gives its `date` command only for Linux and macOS.
* [ ] Workstations and clusters reach the hosts in xref:rosa-and-aro:setup-requirements.adoc#_network_and_image_access[Network and Image Access].
Clusters also need `github.com`, because Argo CD in the cluster clones this workshop's repository in What Ships Exercise 7, and `registry.access.redhat.com` is needed in Module 1 as well as Module 3.
* [ ] The xref:rosa-and-aro:setup-requirements.adoc#_verification_checklist[Verification Checklist] passes for every attendee.
* [ ] On ROSA, the attendee's AWS credentials belong to the account that owns the cluster.
Otherwise every AWS step in Modules 2 to 4 fails.
* [ ] On ARO, the attendee can create and delete an Entra ID app registration, which Access and Tenancy Exercise 2 creates.

To check the AWS account, have the attendee print the account their `aws` CLI uses, and compare it with the account that owns the cluster:

[source,bash]
----
aws sts get-caller-identity \
  --query Account \
  --output text
----

. Send attendees the xref:attendee.adoc[Workshop attendee] page so they can check their workstation.

[#dry-run]
=== Dry Run

Run one attendee path per platform, end to end, before the day.
The module pages were validated on ROSA HCP 4.20 and 4.22 and on ARO 4.21, so the dry run is also the check on the version you deliver on.

* [ ] Use one ROSA and one ARO cluster built exactly like the attendees' clusters, not an attendee's own cluster: the exercises leave cluster-wide changes behind, such as the identity provider, the project template and AutoNode.
* [ ] Work with an attendee-level account: the same Red Hat organization permissions, AWS permissions and Azure roles your attendees get, so that permission gaps show up now.
* [ ] Run every page in order, from xref:rosa-and-aro:module-01-who-manages-what.adoc#before-you-start[Before You Start] to the Observability clean-up, in one terminal per cluster.
* [ ] Time each page and replace the estimates in the <<agenda,Agenda>> and <<slow-steps,Slow Steps>> with what you measured.
* [ ] On ARO, run the Entra ID sign-in and the developer terminal's login.
* [ ] Run the Gateway API exercise on your version: whether the Ingress Operator installs the Service Mesh Operator first depends on the version.
* [ ] Try the <<if-identity-provider-sign-in-fails,identity provider fallback>> once, so that you can hand it out quickly.
* [ ] Clean up in the order xref:rosa-and-aro:setup-requirements.adoc#_cost_and_cleanup[Cost and Cleanup] gives, to test that too.

[#the-rosa-temporary-administrator]
=== The ROSA Temporary Administrator

A ROSA cluster has only one temporary admin user.
Either you create it on each cluster before the day and hand out its login command, or each attendee creates it in xref:rosa-and-aro:module-01-who-manages-what.adoc#before-you-start[Before You Start], but never both.

If you create it, do so for each cluster, and keep the `oc login` command it prints for that cluster's attendee:

[source,bash]
----
rosa create admin \
  --cluster <cluster-name>
----

When the attendee then runs `rosa create admin` in Before You Start, it says the cluster already has a `cluster-admin` user, and the page tells them to use your `oc login` command instead.
If attendees create it themselves, their `rosa` CLI must be logged in to the Red Hat organization that owns the cluster.
Attendees need that `rosa` login for later steps anyway: the identity provider, machine pools, AutoNode and upgrades.

ARO needs no step from you: an attendee with `Contributor` on the cluster's resource group reads the kubeadmin password with `az` in Before You Start.

=== Common Failures

==== Errors the Exercises Expect

Some messages look like failures but are part of the exercise.
Tell attendees before they ask.

[cols="2,2,3",options="header"]
|===
|Message |Where |Why it is expected

|A `PodSecurity "restricted:latest"` warning
|Workload Security Exercises 1 and 2, and `oc run` in Pod Networking Exercise 2
|It comes from the namespace's `warn` label and blocks nothing.

|`CrashLoopBackOff`
|Workload Security Exercise 1
|The root image cannot write its directory as the user ID OpenShift assigns.

|No new pod, and a `FailedCreate` event
|Workload Security Exercise 2
|The pinned user ID is outside the namespace's range, so admission rejects the pod.

|`NoCredentialsError` or `ClientAuthenticationError`
|Pod Cloud Credentials Exercise 1
|The pod has no cloud credentials yet.

|`503` on plain HTTP
|Exposing an App Exercise 2
|An edge Route refuses plain HTTP until the redirect is set.

|`503` from the Gateway on ARO
|Exposing an App Exercise 4
|The Gateway's DNS record is not published on the default `aroapp.io` domain, so the page sends the request to the Gateway's address instead.

|`000`, and `command terminated with exit code 28`
|Pod Networking and Policy Exercises 3 and 4
|The client is blocked, and curl times out.

|`You may not request a new project via this API`
|Access and Tenancy Exercise 4
|Self-provisioning has just been turned off.

|A warning about a missing `last-applied-configuration` annotation
|Access and Tenancy Exercise 2 (ARO), Observability Exercise 5
|It is harmless.

|The ClusterVersion label is refused on ROSA and accepted on ARO
|Who Manages What Exercise 4
|A managed webhook protects it on ROSA; ARO protects its platform through the deny assignment instead.

|`the server doesn't have a resource type "machinesets"`
|Scaling Nodes Exercise 1 (ROSA)
|ROSA keeps machine pools outside the cluster.

|`Upgradeable=False` with the reason `AdminAckRequired`
|Upgrades Exercise 1
|It is an acknowledgment gate for the next minor version only.

|An empty list of removed APIs
|Upgrades Exercise 4
|Nothing on the cluster calls an API scheduled for removal.
|===

==== Failures and Fixes

[cols="2,2,3",options="header"]
|===
|Symptom |Likely cause |Fix

3+h|Logging in and the terminal

|`oc login` to the ARO cluster times out.
|The network allows only port 443, and the ARO API listens on 6443.
|Allow outbound port 6443 from workstations, as xref:rosa-and-aro:setup-requirements.adoc#_network_and_image_access[Network and Image Access] says.

|The `oc login` command from `rosa create admin` fails right away.
|The new admin is not ready yet.
|Wait about a minute and run it again.

|`rosa create admin` says the cluster already has a `cluster-admin` user.
|You created the temporary admin before the day.
|Run the `oc login` command you handed out.

|`rosa` commands cannot find or change the cluster.
|The `rosa` CLI is not logged in to the Red Hat organization that owns the cluster, or the account lacks permission to manage it in OpenShift Cluster Manager.
|Log in with a token from console.redhat.com for that organization, and grant the permission xref:rosa-and-aro:setup-requirements.adoc#_attendee_accounts_projects_and_roles[Setup] lists.

|`aws` steps fail, or AWS lookups return nothing.
|The `aws` CLI uses credentials for another account.
|Configure credentials for the account that owns the cluster, and check them as <<setup-checklist,Setup Checklist>> shows.

|A command fails because a variable such as `CLUSTER` is empty.
|The attendee opened a new terminal.
|Set the variables again, as <<after-a-closed-terminal,After a Closed Terminal>> shows.

|Output looks like the other platform's.
|An attendee with both clusters ran the step in the other cluster's terminal.
|Each terminal has its own kubeconfig file.
`oc whoami` shows `cluster-admin` on ROSA and `kube:admin` on ARO.

|A command never returns.
|It watches for changes (`--watch`), or `oc rollout status` waits for a pod that cannot start.
|Press Ctrl+C.
For a rollout, see <<repairing-the-sample-application,Repairing the Sample Application>>.

3+h|Module 1: The Service Model

|On ROSA, creating the `openshift-gitops-operator` namespace is refused.
|The attendee is logged in as `dedicated-admin`, which cannot create other `openshift-` namespaces.
|Use the `cluster-admin` login from Before You Start.
The Gateway API in Module 3 needs it too.

|On ARO, `redhat-operators` is missing from the catalog sources, and OpenShift GitOps or Logging never installs.
|The cluster has no Red Hat pull secret, or it was added after creation and the default sources are still disabled.
|Run the OperatorHub check in xref:rosa-and-aro:module-01-what-ships.adoc#ex-module-01-what-ships-5[What Ships Exercise 5], and add the pull secret as Setup links.

|The `gitops-hello` Application does not sync, or its pod stays in `ImagePullBackOff`.
|Cluster egress blocks `github.com`, which Argo CD in the cluster clones the repository from, or `registry.access.redhat.com`, which the pod's image comes from.
|Allow both in the cluster's egress.

3+h|Access and Tenancy

|`rosa create idp` rejects the developer password.
|ROSA requires at least 14 characters, with upper case, lower case, and digits or symbols.
|Choose a password that meets the rule, and use the same one in the developer terminal.

|On ARO, an `az ad app` command right after creating the app says the resource does not exist.
|Entra ID has not made the new application available yet.
|Wait 30 seconds and run it again.

|On ARO, the authentication Operator never starts progressing.
|The identity provider configuration has an error.
|Read the Operator's Degraded message with the command in xref:rosa-and-aro:module-02-access-and-tenancy.adoc#ex-module-02-access-and-tenancy-2[Exercise 2].

|Sign-in fails: Entra ID refuses consent on ARO, or the htpasswd login is refused on ROSA.

[#if-identity-provider-sign-in-fails]
==== If Identity Provider Sign-in Fails

Exercises 3 to 5 of xref:rosa-and-aro:module-02-access-and-tenancy.adoc[Access and Tenancy] use a developer terminal, which needs a working sign-in through the identity provider.
If sign-in fails, for example because the Entra ID tenant blocks user consent or `rosa create idp` could not run, the attendee can run the developer's steps in the administrator terminal instead, impersonating the developer with `--as` and `--as-group`.
The page's own validation of Exercises 4 and 5 was done this way.
Name the groups explicitly, because impersonation may not add the developer's OpenShift Group membership.

`DEV_USER` must be set in the administrator terminal, as Exercise 2 does on both platforms.
Exercise 3 needs a real sign-in, so the attendee reads it instead; its `oc get users` and `oc get identities` stay empty, because nobody signed in.

In xref:rosa-and-aro:module-02-access-and-tenancy.adoc#ex-module-02-access-and-tenancy-4[Exercise 4], create the first project as the developer:

[source,bash]
----
oc new-project dev-sandbox \
  --as "$DEV_USER" \
  --as-group system:authenticated \
  --as-group system:authenticated:oauth
----

After the template is in place, create the second project the same way:

[source,bash]
----
oc new-project dev-team \
  --as "$DEV_USER" \
  --as-group system:authenticated \
  --as-group system:authenticated:oauth
----

Read its quota and limits as the administrator:

[source,bash]
----
oc describe quota \
  --namespace dev-team
----

[source,bash]
----
oc describe limitrange \
  --namespace dev-team
----

After the self-provisioner binding is removed, try once more.
The request is refused with `You may not request a new project via this API`:

[source,bash]
----
oc new-project dev-another \
  --as "$DEV_USER" \
  --as-group system:authenticated \
  --as-group system:authenticated:oauth
----

In xref:rosa-and-aro:module-02-access-and-tenancy.adoc#ex-module-02-access-and-tenancy-5[Exercise 5], check what the developer sees as a member of `team-a`:

[source,bash]
----
oc get projects \
  --as "$DEV_USER" \
  --as-group system:authenticated \
  --as-group team-a
----

[source,bash]
----
oc auth can-i create deployments \
  --namespace team-a \
  --as "$DEV_USER" \
  --as-group team-a
----

Every exercise runs in the terminal opened in xref:rosa-and-aro:module-01-who-manages-what.adoc#before-you-start[Before You Start], with the variables set there.
The kubeconfig file keeps the login, so in a new terminal the attendee runs only the `export` steps again, as that section says:

On ROSA:

[source,bash]
----
export KUBECONFIG=~/.kube/rosa
----

[source,bash]
----
export CLUSTER=<rosa-cluster-name>
----

On ARO:

[source,bash]
----
export KUBECONFIG=~/.kube/aro
----

[source,bash]
----
export CLUSTER=<aro-cluster-name>
----

[source,bash]
----
export RESOURCE_GROUP=<resource-group>
----

Then check the login, which also shows which cluster the terminal points at:

[source,bash]
----
oc whoami
----

ROSA shows `cluster-admin` and ARO shows `kube:admin`.
On a second day, the login itself may have expired, because OAuth access tokens are valid for 24 hours by default.
If `oc whoami` says the attendee is not logged in, log in again as in Before You Start: on ROSA with the `oc login` command from `rosa create admin`, and on ARO with the API URL and password lookups and `oc login`.

[#repairing-the-sample-application]
==== Repairing the Sample Application

If the new pod stays in `ImagePullBackOff` after the switch to ECR or ACR in xref:rosa-and-aro:module-02-cloud-credentials.adoc#ex-module-02-cloud-credentials-2[Pod Cloud Credentials Exercise 2], the old pod keeps serving, and `oc rollout status` waits until the rollout's deadline.

Press Ctrl+C and roll back to the previous image:

[source,bash]
----
oc rollout undo deployment/sample-app \
  --namespace sample-app
----

The attendee then continues with the ghcr.io image, which every later page works with.

If the application still runs the root image, or under `anyuid`, run the last steps of xref:rosa-and-aro:module-02-workload-security.adoc#ex-module-02-workload-security-4[Workload Security Exercise 4]: undo the grant, then switch back to the fixed image.

If the application is missing, for example for an attendee who joins late, rebuild it from the pages:

. Create the namespace and apply the manifest in xref:rosa-and-aro:module-02-workload-security.adoc#ex-module-02-workload-security-1[Workload Security Exercise 1].
. Switch to the fixed image as in xref:rosa-and-aro:module-02-workload-security.adoc#ex-module-02-workload-security-3[Workload Security Exercise 3].
. Run the steps the attendee missed on later pages: the credentials in Pod Cloud Credentials, the Route in Exposing an App Exercise 2, and the policies in Pod Networking and Policy Exercise 3.

Without the credentials, the application answers `500` on `/`, which Observability expects and explains.

[#upgrades-without-a-live-upgrade]
=== Upgrades Without a Live Upgrade

The xref:rosa-and-aro:module-04-upgrades.adoc[Upgrades] page inspects and schedules upgrades but does not run one, because a real upgrade with its node rollout takes an hour or more, so attendees never see the drain and PodDisruptionBudget behavior it describes.
If you want the room to see one, give an optional facilitator demo on a cluster of your own that is one patch release behind: start its upgrade at the beginning of the day, and during Module 4 show `oc adm upgrade` while the update progresses, the cluster Operators reporting `PROGRESSING`, and the nodes rolling, through the machine config pools on ARO or the machine pool upgrade that follows the control plane on ROSA.
If you cannot spare a cluster, show a recording of a real upgrade instead.
On ROSA there is a shorter, real node pool upgrade: create a one-node machine pool one patch release behind the control plane, with `rosa create machinepool` and `--version`, then upgrade it to the control plane's version with `rosa upgrade machinepool`.
On ROSA 4.22 this was validated: the upgrade started about 14 minutes after the command and replaced the node within 3 more, adding the new node before draining the old one.
Two cluster updates were also run during validation.
A ROSA control plane patch upgrade from 4.22.17 to 4.22.18 started about 10 minutes after `rosa upgrade cluster`, finished about 23 minutes later, and left the machine pool on 4.22.17 until its own upgrade.
An ARO patch update from 4.21.22 to 4.21.36 took about 55 minutes for the control plane, and each worker about 10 more, apart from a drain held by a PodDisruptionBudget.
Rehearse whichever you choose.
