= Scaling Nodes

NOTE: Validated on ROSA 4.20 and ARO 4.21 in October 2026.
Steps and statements that were not checked on a live cluster carry a *Not validated* note.
The comparison tables and summaries come from vendor documentation.

EKS Auto Mode, Karpenter and AKS node auto-provisioning pick an instance type for each batch of pending pods, mix spot and on-demand capacity, and consolidate nodes.
ROSA and ARO scale in groups of identical nodes: machine pools on ROSA, MachineSets on ARO, with the cluster autoscaler.
ROSA also offers the Red Hat build of Karpenter from OpenShift 4.22.
This is an area where the native services are ahead, and this section says so.

In this section you add an autoscaling group of nodes to each cluster, push the sample application onto it until new nodes start, and look at who keeps the node OS patched.

== Two Ways to Add Nodes

Every platform in this workshop offers one or both of these models.

.Group autoscaling and provisioning
image::module-04-scaling-models.svg[Group autoscaling grows pre-defined groups of identical nodes. Provisioning picks an instance type for each batch of pending pods.,width=100%]

[cols="2,2,2,2,2",options="header"]
|===
|Platform |Group autoscaling |Provisioning |Where you configure it |Who patches the node OS

|EKS
|Managed node groups with the Cluster Autoscaler, which you install
|Karpenter, which you install, or Auto Mode, which AWS runs
|EKS API, Karpenter `NodePool` objects
|You roll new AMIs, unless Auto Mode replaces nodes for you

|AKS
|Node pools with the built-in cluster autoscaler
|Node auto-provisioning, based on Karpenter
|AKS API, `az aks nodepool`
|You pick a node OS upgrade channel and AKS applies it

|ROSA
|Machine pools with the cluster autoscaler, both run by Red Hat outside your cluster
|Red Hat build of Karpenter, from 4.22
|OpenShift Cluster Manager, `rosa`
|Red Hat builds it; you roll it out to each machine pool

|ARO
|MachineSets with the cluster autoscaler, inside your cluster
|Not on standard ARO
|`oc`, in the cluster
|Red Hat, with each OpenShift update
|===

== On EKS and AKS

* EKS: managed node groups with the Cluster Autoscaler, which you install and keep in step with the Kubernetes version, or Karpenter, or EKS Auto Mode, which also patches and replaces nodes.
* AKS: node pools with the built-in cluster autoscaler, or node auto-provisioning, which is based on Karpenter.
* You own node images, unless Auto Mode or an AKS node OS upgrade channel does it for you.

== On ROSA and ARO

ROSA keeps its machine pools outside your cluster, in OpenShift Cluster Manager, while ARO keeps MachineSets inside it.
So the steps differ between the two clusters, and they appear in a *ROSA (AWS)* tab and an *ARO (Azure)* tab.
Run each tab's steps in that cluster's terminal, the ones you set up in xref:module-01-who-manages-what.adoc#before-you-start[Before You Start].

The ROSA steps use the `CLUSTER` variable set there.
If you open a new ROSA terminal, set it again:

[source,bash]
----
export CLUSTER=<your-rosa-cluster-name>
----

=== Exercise 2: Add an Autoscaling Group of Nodes

You add a group of nodes with the label `workshop=scale-lab` and a matching taint, so that only the sample application lands there.
The group starts small and the cluster autoscaler grows it when pods are pending.

[tabs]
======
ROSA (AWS)::
+
--
NOTE: *Not validated:* the ROSA steps of this exercise, which need the `rosa` CLI, including a machine pool that starts at zero nodes.

A machine pool on ROSA lives in one subnet, so in one availability zone.
Use the subnet of your existing pool:

[source,bash]
----
SUBNET=$(rosa list machinepools \
  --cluster "$CLUSTER" \
  --output json \
  | jq -r '.[0].subnet')
echo "$SUBNET"
----

Create an autoscaling machine pool that starts at zero nodes:

[source,bash]
----
rosa create machinepool \
  --cluster "$CLUSTER" \
  --name scale-lab \
  --subnet "$SUBNET" \
  --instance-type m7i.xlarge \
  --enable-autoscaling \
  --min-replicas 0 \
  --max-replicas 3 \
  --labels workshop=scale-lab \
  --taints workshop=scale-lab:NoSchedule
----

Check the pool:

[source,bash]
----
rosa describe machinepool \
  --cluster "$CLUSTER" \
  --machinepool scale-lab
----

The cluster autoscaler for ROSA runs next to the hosted control plane, so there is nothing to install.
You can see its few cluster-wide settings:

[source,bash]
----
rosa describe autoscaler \
  --cluster "$CLUSTER"
----
--
ARO (Azure)::
+
--
Standard ARO has no pool API, so you copy an existing worker MachineSet in the cluster.
Pick the first worker MachineSet:

[source,bash]
----
SOURCE_MS=$(oc get machinesets \
  --namespace openshift-machine-api \
  -o jsonpath='{.items[0].metadata.name}')
echo "$SOURCE_MS"
----

Write a `jq` filter that renames the copy, adds the label and taint to its nodes, and drops the fields the cluster sets:

[source,bash]
----
cat > scale-lab-ms.jq <<'EOF'
del(.metadata.uid, .metadata.resourceVersion,
    .metadata.creationTimestamp, .metadata.generation,
    .status)
| .metadata.name = $name
| .spec.replicas = 1
| .spec.selector.matchLabels
    ["machine.openshift.io/cluster-api-machineset"] = $name
| .spec.template.metadata.labels
    ["machine.openshift.io/cluster-api-machineset"] = $name
| .spec.template.spec.metadata.labels =
    {"workshop": "scale-lab"}
| .spec.template.spec.taints = [{
    "key": "workshop",
    "value": "scale-lab",
    "effect": "NoSchedule"}]
EOF
----

Create the new MachineSet from the copy:

[source,bash]
----
oc get machineset "$SOURCE_MS" \
  --namespace openshift-machine-api \
  -o json \
  | jq --arg name scale-lab \
      -f scale-lab-ms.jq \
  | oc create -f -
----

The new MachineSet keeps the VM size of the one you copied, which is on ARO's list of supported worker sizes.

Unlike ROSA, the cluster autoscaler is an object in your cluster.
Check whether one exists:

[source,bash]
----
oc get clusterautoscaler
----

If there is none, create it with short scale-down timers for the workshop:

[source,bash]
----
cat <<'EOF' | oc apply -f -
apiVersion: autoscaling.openshift.io/v1
kind: ClusterAutoscaler
metadata:
  name: default
spec:
  scaleDown:
    enabled: true
    delayAfterAdd: 5m
    unneededTime: 5m
EOF
----

Then attach a MachineAutoscaler to the new MachineSet.
It keeps at least one node, because ARO's support policy forbids scaling workers to zero:

[source,bash]
----
cat <<'EOF' | oc apply -f -
apiVersion: autoscaling.openshift.io/v1beta1
kind: MachineAutoscaler
metadata:
  name: scale-lab
  namespace: openshift-machine-api
spec:
  minReplicas: 1
  maxReplicas: 3
  scaleTargetRef:
    apiVersion: machine.openshift.io/v1beta1
    kind: MachineSet
    name: scale-lab
EOF
----

Watch the first Machine become a node:

[source,bash]
----
oc get machines \
  --namespace openshift-machine-api \
  -l machine.openshift.io/cluster-api-machineset=scale-lab \
  -w
----

Press Ctrl+C when its phase is `Running`.
The new node is in the same availability zone as the MachineSet you copied.
--

.EKS and AKS (reference only)
[%collapsible]
====
EKS, a managed node group for the Cluster Autoscaler, which you install yourself.
You also supply the node IAM role and the subnets:

[source,bash]
----
aws eks create-nodegroup \
  --cluster-name my-cluster \
  --nodegroup-name scale-lab \
  --node-role arn:aws:iam::111122223333:role/my-node-role \
  --subnets subnet-0abc1234 \
  --instance-types m7i.xlarge \
  --scaling-config minSize=0,maxSize=3,desiredSize=0 \
  --labels workshop=scale-lab \
  --taints key=workshop,value=scale-lab,effect=NO_SCHEDULE
----

AKS, a node pool with the built-in cluster autoscaler:

[source,bash]
----
az aks nodepool add \
  --resource-group my-rg \
  --cluster-name my-cluster \
  --name scalelab \
  --node-vm-size Standard_D4s_v5 \
  --enable-cluster-autoscaler \
  --min-count 0 \
  --max-count 3 \
  --labels workshop=scale-lab \
  --node-taints workshop=scale-lab:NoSchedule
----

=== Exercise 3: Scale the Sample Application Past Capacity

NOTE: *Not validated:* this exercise on ROSA, which needs the machine pool from Exercise 2.
It was validated on ARO, and the ROSA behavior described below comes from Red Hat's documentation.

Run these steps on both clusters.

Give each sample application pod a CPU request large enough that a few replicas fill a node:

[source,bash]
----
oc set resources deployment/sample-app \
  --namespace sample-app \
  --requests cpu=500m
----

Point the application at the new nodes with a node selector and a toleration:

[source,bash]
----
cat > scale-lab-patch.yaml <<'EOF'
spec:
  template:
    spec:
      nodeSelector:
        workshop: scale-lab
      tolerations:
      - key: workshop
        operator: Equal
        value: scale-lab
        effect: NoSchedule
EOF
----

[source,bash]
----
oc patch deployment/sample-app \
  --namespace sample-app \
  --type merge \
  --patch-file scale-lab-patch.yaml
----

Scale it to more replicas than the group's current nodes can hold:

[source,bash]
----
oc scale deployment/sample-app \
  --namespace sample-app \
  --replicas 10
----

Some pods stay `Pending`:

[source,bash]
----
oc get pods \
  --namespace sample-app \
  -o wide
----

The cluster autoscaler records its decision as an event on the pending pods:

[source,bash]
----
oc get events \
  --namespace sample-app \
  --field-selector reason=TriggeredScaleUp
----

Watch the new nodes join:

[source,bash]
----
oc get nodes \
  -l workshop=scale-lab \
  -L node.kubernetes.io/instance-type \
  -w
----

On ROSA you can also watch the pool's node count from outside the cluster:

[source,bash]
----
rosa list machinepools \
  --cluster "$CLUSTER"
----

New nodes take several minutes to boot, install and join.
Read the rest of this exercise while you wait, then press Ctrl+C when all pods are `Running`.
For a minute, pods from the previous rollout can still run on the regular workers while they are replaced.

What is happening:

* On ROSA, the cluster autoscaler runs in the hosted control plane.
It raises the machine pool's node count, and the HyperShift node pool controller creates EC2 instances in your account.
* On ARO, the cluster autoscaler and the Machine API run in your cluster.
The autoscaler raises the MachineSet's replica count, and the Machine API creates Azure VMs.
* In both cases the new node boots Red Hat Enterprise Linux CoreOS at the exact version that matches an OpenShift release: the cluster's on ARO, its machine pool's on ROSA.
There is no node image for you to choose.

.EKS and AKS (reference only)
[%collapsible]
====
The application steps are the same on EKS and AKS.
With the Cluster Autoscaler on EKS, you would read its decisions from its own logs or events:

[source,bash]
----
kubectl logs \
  --namespace kube-system \

----

=== Exercise 4: Let Karpenter Pick the Nodes (ROSA Only)

NOTE: *Not validated:* this whole exercise.
The validation cluster ran ROSA 4.20, and AutoNode needs 4.22 and the `rosa` and `aws` CLIs.

From OpenShift 4.22, ROSA can run the Red Hat build of Karpenter, called AutoNode in OpenShift Cluster Manager.
Its controller runs in the hosted control plane and launches EC2 instances in your account, so it needs an IAM role.
Standard ARO has no equivalent, so this exercise is for your ROSA cluster only.

Collect the cluster's OIDC issuer and your AWS account ID:

[source,bash]
----
OIDC_PROVIDER=$(oc get authentication.config.openshift.io \
  cluster \
  -o jsonpath='{.spec.serviceAccountIssuer}' \
  | sed 's|^https://||')
ACCOUNT_ID=$(aws sts get-caller-identity \
  --query Account \
  --output text)
----

Write a trust policy that lets the Karpenter service account assume the role:

[source,bash]
----
cat > karpenter-trust.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated":
        "arn:aws:iam::${ACCOUNT_ID}:oidc-provider/${OIDC_PROVIDER}"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "${OIDC_PROVIDER}:sub":
          "system:serviceaccount:kube-system:karpenter"
      }
    }
  }]
}
EOF
----

Create the role and attach the AWS managed policy for ROSA Karpenter:

[source,bash]
----
aws iam create-role \
  --role-name "rosa-karpenter-${CLUSTER}" \
  --assume-role-policy-document file://karpenter-trust.json \
  --tags Key=red-hat-managed,Value=true
----

[source,bash]
----
aws iam attach-role-policy \
  --role-name "rosa-karpenter-${CLUSTER}" \
  --policy-arn \
    arn:aws:iam::aws:policy/service-role/ROSAKarpenterControllerPolicy
----

Turn on AutoNode with that role:

[source,bash]
----
KARPENTER_ROLE_ARN=$(aws iam get-role \
  --role-name "rosa-karpenter-${CLUSTER}" \
  --query Role.Arn \
  --output text)
----

[source,bash]
----
rosa edit cluster \
  --cluster "$CLUSTER" \
  --autonode enabled \
  --autonode-iam-role-arn "$KARPENTER_ROLE_ARN"
----

After a few minutes, Red Hat's node class appears in the cluster.
`OpenshiftEC2NodeClass` is Red Hat's wrapper, and it manages the matching Karpenter `EC2NodeClass`:

[source,bash]
----
oc get openshiftec2nodeclass,ec2nodeclass
----

Wait until both show `default` with `READY` set to `True`.
The `default` class is immutable, and its nodes follow the control plane's OpenShift version.

Create a Karpenter `NodePool` for the sample application.
It allows three instance types and both spot and on-demand capacity, and caps the pool at 16 vCPUs:

[source,bash]
----
cat <<'EOF' | oc apply -f -
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: karpenter-lab
spec:
  template:
    metadata:
      labels:
        workshop: scale-lab
    spec:
      taints:
      - key: workshop
        value: scale-lab
        effect: NoSchedule
      requirements:
      - key: node.kubernetes.io/instance-type
        operator: In
        values: ["m7i.xlarge", "m6i.xlarge", "c7i.2xlarge"]
      - key: karpenter.sh/capacity-type
        operator: In
        values: ["spot", "on-demand"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
  limits:
    cpu: "16"
EOF
----

The NodePool uses the same label and taint as the machine pool, so the sample application can run on either.
Now delete the machine pool.
Its nodes drain, the sample application's pods go back to `Pending`, and Karpenter picks them up:

[source,bash]
----
rosa delete machinepool \
  --cluster "$CLUSTER" \
  scale-lab \
  --yes
----

Watch Karpenter claim nodes for the pending pods:

[source,bash]
----
oc get nodeclaims -w
----

Press Ctrl+C when the node claims are `Ready`, then see which instance types and capacity types it chose:

[source,bash]
----
oc get nodes \
  -l karpenter.sh/nodepool=karpenter-lab \
  -L node.kubernetes.io/instance-type \
  -L karpenter.sh/capacity-type
----

Karpenter batches the pending pods, picks the cheapest instance types that fit them, and prefers spot capacity when the NodePool allows it.
Spot nodes can be reclaimed by AWS at short notice, so allow spot only for workloads that tolerate interruption.
Karpenter nodes also expire after 30 days, which replaces them with fresh ones.

=== Exercise 5: See Who Patches the Node OS

List the nodes with their OS image and kernel, on both clusters:

[source,bash]
----
oc get nodes -o wide
----

Every node runs Red Hat Enterprise Linux CoreOS at the version that belongs to an OpenShift release.
On ARO that is the cluster's release.
On ROSA it is the release of the node's machine pool, which can trail the control plane.
Compare the OS image above with the cluster version:

[source,bash]
----
oc get clusterversion
----

On ARO, the Machine Config Operator rolls OS changes onto nodes, one pool at a time:

[source,bash]
----
oc get machineconfigpools
----

On ROSA the same command finds no pools.
Node configuration and OS updates are driven from the hosted control plane, per machine pool.

Either way, the node OS changes only when the cluster or machine pool takes an OpenShift update.
That is the subject of xref:module-04-upgrades.adoc[Upgrades].

.EKS and AKS (reference only)
[%collapsible]
====
EKS, roll a managed node group to the latest AMI for its Kubernetes version:

[source,bash]
----
aws eks update-nodegroup-version \
  --cluster-name my-cluster \
  --nodegroup-name scale-lab
----

AKS, choose how node images are updated:

[source,bash]
----
az aks update \
  --resource-group my-rg \
  --name my-cluster \
  --node-os-upgrade-channel NodeImage
----

== What Matters

* ROSA and ARO use different tools.
ROSA machine pools are managed through the `rosa` CLI or OpenShift Cluster Manager.
Standard ARO has no pool API, and you edit MachineSets in the cluster with `oc`.
* Each machine pool or MachineSet uses one instance type.
To offer two instance types, or spot and on-demand, you create two groups.
* ROSA machine pools can scale to zero.
* The Red Hat build of Karpenter requires ROSA 4.22.
ARO with hosted control planes has its own autoscaling, in preview.
* Red Hat owns the node OS image.
The node OS changes only when the cluster (ARO) or each machine pool (ROSA) takes an OpenShift update, so staying current on patch releases is how nodes get kernel and OS fixes.
There is no separate node image channel to follow, and no custom AMI or node image to build.

== Where Each Wins

[cols="1,1",options="header"]
|===
|ROSA and ARO win |EKS and AKS win

|No node images to build: Red Hat ships the patched OS in each OpenShift update.
|Karpenter, Auto Mode and node auto-provisioning are mature, flexible and bin-pack well.

|The cluster autoscaler is part of the platform, so there is nothing to install or keep in step with the Kubernetes version.
|Spot and mixed instance types per workload, without one group per type.

|The same machine pool model across both clouds.
|One API for pools on each cloud. Standard ARO has no pool API, so pools are edited inside the cluster.
|===

== App Teams Will Notice

* A pod that triggers a scale-up waits several minutes in `Pending` while a node boots and joins.
Accurate CPU and memory requests decide whether the autoscaler adds a node at all.
* Dedicated groups use labels and taints, so workloads that should land there need a matching node selector and toleration.
* The autoscaler removes a node only when it can move every pod on it.
A PodDisruptionBudget that allows no disruptions, or a pod with local storage, keeps nodes running and costing money.
