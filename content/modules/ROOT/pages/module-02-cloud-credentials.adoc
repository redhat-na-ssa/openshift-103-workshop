= Pod Cloud Credentials

NOTE: This section is an outline. Its diagrams and exercises are being written and validated on ROSA and ARO.

Every real application needs to reach cloud services: object storage, queues, databases, a container registry.
On all four platforms the answer is short-lived credentials tied to a Kubernetes service account, but the setup differs.
This section gives the sample application access to object storage, and pulls a private image from Amazon ECR and Azure Container Registry.

== On EKS and AKS

* EKS Pod Identity: create an association between a service account and an IAM role. No per-cluster OIDC trust to manage. IAM Roles for Service Accounts (IRSA) still works.
* AKS: enable Workload ID on the cluster, create a federated credential on a user-assigned managed identity, and annotate the service account.
* Registries: EKS nodes pull from ECR through the node IAM role, and AKS attaches an ACR to the cluster in one step.

== On ROSA and ARO

Outline of the exercise:

. ROSA: find the cluster's OIDC provider, create an IAM role that trusts the sample application's service account, annotate the service account, and read from an S3 bucket.
. ARO: create a user-assigned managed identity with a federated credential for the service account, grant it access to a storage account, and read from a Blob container.
. Pull a private image from ECR on ROSA, and from ACR on ARO.

== What Matters

* ROSA uses the IRSA mechanism only: the same service account annotation as IRSA on EKS, through the pod identity webhook the cluster already runs. EKS Pod Identity is not available.
* ARO workload identity works only on clusters created with managed identities, which became generally available in February 2026. There is no conversion from a service principal cluster.
* On ROSA, ECR pulls work by attaching an ECR read policy to the worker IAM role. Pull secrets also work, but ECR tokens expire after 12 hours.
* On ARO, ACR pulls use a pull secret.
* The platform's own Operators already use short-lived credentials on both ROSA (STS) and managed-identity ARO.

== Where Each Wins

[cols="1,1",options="header"]
|===
|ROSA and ARO win |EKS and AKS win

|The platform itself runs on short-lived credentials from day one.
|EKS Pod Identity needs no OIDC trust policy per cluster, and AKS Workload ID is one flag.

|One service account pattern (IRSA-style) that EKS engineers already know.
|Registry pulls need no pull secret: node role on EKS, attached ACR on AKS.
|===

== App Teams Will Notice

Nothing changes in application code if it already uses the AWS or Azure SDK default credential chain.
Image references to ECR or ACR keep working once the registry access above is in place.
OpenShift also has a built-in registry and ImageStreams, which track image tags and can redeploy an application when a tag changes; teams can ignore them and keep using ECR or ACR.
