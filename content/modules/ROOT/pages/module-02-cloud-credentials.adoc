= Pod Cloud Credentials

[.validation]
NOTE: Validated on ROSA HCP 4.20 and ARO 4.21 in October 2026.
Steps and statements that were not checked on a live cluster carry a *Not validated* note.
The comparison tables and summaries come from vendor documentation.

Every real application needs to reach cloud services: object storage, queues, databases, a container registry.
On all four platforms the answer is short-lived credentials tied to a Kubernetes service account, but the setup differs.
This section gives the sample application read access to object storage, then pulls its image from Amazon ECR and Azure Container Registry.

image::module-02-token-flow.svg["Token flow from service account to cloud API on all four platforms",link=self,window=_blank]

== On EKS and AKS

* EKS Pod Identity: create an association between a service account and an IAM role. No per-cluster OIDC trust to manage. IAM Roles for Service Accounts (IRSA) still works.
* AKS: enable Workload ID on the cluster, create a federated credential on a user-assigned managed identity, and annotate the service account.
* Registries: EKS nodes pull from ECR through the node IAM role, and AKS attaches an ACR to the cluster in one step.

== On ROSA and ARO

Run the exercises on your cluster, in the administrator terminal from xref:module-02-access-and-tenancy.adoc[Access and Tenancy].
The sample application from xref:module-02-workload-security.adoc[Workload Security Defaults] must be running in the `sample-app` namespace.

The sample application's image ignores the node's own cloud identity on purpose (the EC2 instance role on ROSA, the VM's managed identity on ARO).
The only credentials it can use are the ones you give the pod.

.Exercises on this page

=== Exercise 1: Read from Object Storage

[tabs]
======
ROSA (AWS)::
+
--
Read from Amazon S3.

[.validation]
NOTE: *Not validated:* the AWS steps of this exercise, because AWS credentials for the cluster's account were not available.
On ROSA, the `NoCredentialsError`, and the variables and token audience that the webhook injects, were checked with a placeholder role.

[discrete]
==== Create the Bucket

Look up the cluster's region and your AWS account:

[source,bash]
----
export AWS_REGION=$(rosa describe cluster \
  --cluster "$CLUSTER" \
  --output json | jq -r .region.id)
----

[source,bash]
----
export ACCOUNT_ID=$(aws sts get-caller-identity \
  --query Account \
  --output text)
----

Create a bucket with one object in it:

[source,bash]
----
export BUCKET="sample-app-$ACCOUNT_ID-$CLUSTER"
----

[source,bash]
----
aws s3 mb "s3://$BUCKET" \
  --region "$AWS_REGION"
----

[source,bash]
----
echo "Hello from S3" > hello.txt
----

[source,bash]
----
aws s3 cp hello.txt "s3://$BUCKET/hello.txt"
----

[discrete]
==== See the Pod Fail Without Credentials

Tell the application which bucket to read:

[source,bash]
----
oc set env deployment/sample-app \
  --namespace sample-app \
  BUCKET="$BUCKET" \
  AWS_REGION="$AWS_REGION"
----

[source,bash]
----
oc rollout status deployment/sample-app \
  --namespace sample-app
----

Ask it to list the bucket:

[source,bash]
----
oc exec deployment/sample-app \
  --namespace sample-app \
  -- sample-app list
----

It fails with `NoCredentialsError`: the pod has no AWS credentials yet.

[discrete]
==== Create the Role

Find the cluster's OIDC issuer.
On ROSA the issuer belongs to the cluster's OIDC config, and ROSA created a matching IAM OIDC provider in your account with that config:

[source,bash]
----
export OIDC_PROVIDER=$(rosa describe cluster \
  --cluster "$CLUSTER" \
  --output json \
  | jq -r .aws.sts.oidc_endpoint_url \
  | sed 's|^https://||')
----

Write a trust policy that lets only the `sample-app` service account in the `sample-app` namespace assume the role, on clusters that use this OIDC config:

[source,bash]
----
PROVIDER_ARN="arn:aws:iam::$ACCOUNT_ID:oidc-provider/$OIDC_PROVIDER"
SUBJECT="system:serviceaccount:sample-app:sample-app"
----

[source,bash]
----
cat > trust.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Federated": "$PROVIDER_ARN"},
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "$OIDC_PROVIDER:sub": "$SUBJECT",
        "$OIDC_PROVIDER:aud": "openshift"
      }
    }
  }]
}
EOF
----

Create the role:

[source,bash]
----
export ROLE_ARN=$(aws iam create-role \
  --role-name "sample-app-$CLUSTER" \
  --assume-role-policy-document file://trust.json \
  --query Role.Arn \
  --output text)
----

Let it read the bucket:

[source,bash]
----
cat > s3-read.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:ListBucket", "s3:GetObject"],
    "Resource": [
      "arn:aws:s3:::$BUCKET",
      "arn:aws:s3:::$BUCKET/*"
    ]
  }]
}
EOF
----

[source,bash]
----
aws iam put-role-policy \
  --role-name "sample-app-$CLUSTER" \
  --policy-name s3-read \
  --policy-document file://s3-read.json
----

[discrete]
==== Connect the Service Account

Annotate the service account with the role, exactly as for IRSA on EKS:

[source,bash]
----
oc annotate serviceaccount sample-app \
  --namespace sample-app \
  eks.amazonaws.com/role-arn="$ROLE_ARN"
----

The cluster's pod identity webhook changes pods only when they are created, so restart the application:

[source,bash]
----
oc rollout restart deployment/sample-app \
  --namespace sample-app
----

[source,bash]
----
oc rollout status deployment/sample-app \
  --namespace sample-app
----

See what the webhook injected:

[source,bash]
----
oc exec deployment/sample-app \
  --namespace sample-app \
  -- env | grep AWS_
----

`AWS_ROLE_ARN` and `AWS_WEB_IDENTITY_TOKEN_FILE` point the AWS SDK at the role and at a service account token.
On ROSA that token's audience is `openshift`, which is why the trust policy checks for it; on EKS it is `sts.amazonaws.com`.
The ROSA documentation says the webhook applies `sts.amazonaws.com`, but the webhook on the validation cluster issued `openshift`, so check the token's audience before you write a trust policy.

[discrete]
==== Check the Access

Check the identity and the listing:

[source,bash]
----
oc exec deployment/sample-app \
  --namespace sample-app \
  -- sample-app whoami
----

[source,bash]
----
oc exec deployment/sample-app \
  --namespace sample-app \
  -- sample-app list
----

The application now runs as the `sample-app-<cluster>` role and lists `hello.txt`.
If you see `AccessDenied`, IAM has not finished propagating the new role; wait a few seconds and try again.

==== Create the Storage Account

Look up the cluster's region:

[source,bash]
----
export LOCATION=$(az aro show \
  --name "$CLUSTER" \
  --resource-group "$RESOURCE_GROUP" \
  --query location \
  --output tsv)
----

Create a storage account that accepts only Entra ID authentication, with no shared keys:

[source,bash]
----
export STORAGE_ACCOUNT="sampleapp$(date +%s)"
----

[source,bash]
----
az storage account create \
  --name "$STORAGE_ACCOUNT" \
  --resource-group "$RESOURCE_GROUP" \
  --location "$LOCATION" \
  --sku Standard_LRS \
  --allow-blob-public-access false \
  --allow-shared-key-access false
----

[source,bash]
----
export STORAGE_ID=$(az storage account show \
  --name "$STORAGE_ACCOUNT" \
  --resource-group "$RESOURCE_GROUP" \
  --query id \
  --output tsv)
----

Give yourself permission to write blobs, since shared keys are off:

[source,bash]
----
MY_ID=$(az ad signed-in-user show \
  --query id \
  --output tsv)
----

If you are logged in to `az` as a service principal, that command fails with `/me request is only valid with delegated authentication flow`.
Look up the service principal's ID instead:

[source,bash]
----
MY_ID=$(az ad sp show \
  --id "$(az account show --query user.name --output tsv)" \
  --query id \
  --output tsv)
----

[source,bash]
----
az role assignment create \
  --role "Storage Blob Data Contributor" \
  --assignee "$MY_ID" \
  --scope "$STORAGE_ID"
----

Create a container with one blob in it.
If either of the next two `az storage` commands gives an authorization error, the role assignment has not applied yet; wait a minute or two and try again:

[source,bash]
----
az storage container create \
  --name sample-app \
  --account-name "$STORAGE_ACCOUNT" \
  --auth-mode login
----

[source,bash]
----
echo "Hello from Blob Storage" > hello.txt
----

[source,bash]
----
az storage blob upload \
  --account-name "$STORAGE_ACCOUNT" \
  --container-name sample-app \
  --name hello.txt \
  --file hello.txt \
  --auth-mode login
----

[source,bash]

export CLIENT_ID=$(az identity show \

==== Trust the Cluster's Tokens

Find the cluster's OIDC issuer.
Only clusters created with managed identities have one:

[source,bash]
----
export OIDC_ISSUER=$(az aro show \
  --name "$CLUSTER" \
  --resource-group "$RESOURCE_GROUP" \
  --query clusterProfile.oidcIssuer \
  --output tsv)
----

[source,bash]
----
echo "$OIDC_ISSUER"
----

If it prints nothing, the cluster uses a service principal and has no workload identity.
Stop here and read the rest of this exercise.

[.validation]
NOTE: *Not validated:* the rest of this exercise, because the validation ARO cluster uses a service principal.

Trust tokens from that issuer for the `sample-app` service account:

[source,bash]
----
az identity federated-credential create \
  --name sample-app \
  --identity-name "sample-app-$CLUSTER" \
  --resource-group "$RESOURCE_GROUP" \
  --issuer "$OIDC_ISSUER" \
  --subject system:serviceaccount:sample-app:sample-app \
  --audiences api://AzureADTokenExchange
----

[discrete]
==== Connect the Service Account

Annotate the service account with the identity's client ID, exactly as on AKS:

[source,bash]
----
oc annotate serviceaccount sample-app \
  --namespace sample-app \
  azure.workload.identity/client-id="$CLIENT_ID"
----

Label the pod template so the cluster's pod identity webhook injects the token.
This also rolls out new pods:

[source,bash]
----
oc patch deployment sample-app \
  --namespace sample-app \
  --type merge \
  --patch '{"spec":{"template":{"metadata":{"labels":
    {"azure.workload.identity/use":"true"}}}}}'
----

[source,bash]
----
oc rollout status deployment/sample-app \
  --namespace sample-app
----

See what the webhook injected:

[source,bash]
----
oc exec deployment/sample-app \
  --namespace sample-app \
  -- env | grep AZURE_
----

`AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_FEDERATED_TOKEN_FILE` and `AZURE_AUTHORITY_HOST` are what the Azure SDK's default credential chain looks for.

======

.EKS and AKS (reference only)
[%collapsible]
====
On EKS, the IRSA steps are the same as above, with the issuer from `aws eks describe-cluster`, an IAM OIDC provider you create once per cluster, and `sts.amazonaws.com` as the audience in the trust policy.

EKS Pod Identity needs no OIDC provider and no per-cluster trust policy.
The role trusts the `pods.eks.amazonaws.com` service, and you associate it with the service account after installing the EKS Pod Identity Agent add-on (built into Auto Mode):

[source,bash]
----
aws eks create-pod-identity-association \
  --cluster-name <cluster-name> \
  --namespace sample-app \
  --service-account sample-app \
  --role-arn <role-arn>
----

No service account annotation is needed, and the same role works for any cluster you associate it with.

On AKS, you turn on the OIDC issuer and the workload identity webhook with one command:

[source,bash]
----
az aks update \
  --resource-group <resource-group> \
  --name <cluster-name> \
  --enable-oidc-issuer \
  --enable-workload-identity
----

Then you read the issuer from `az aks show --query oidcIssuerProfile.issuerUrl`, and create the identity, federated credential, service account annotation and pod label exactly as above.

.In production: secrets from Secrets Manager or Key Vault (reference only)
[%collapsible]
====
An application that uses the AWS or Azure SDK can read secrets through the identity from this exercise, with nothing new on the cluster, as on EKS and AKS.

[.validation]
NOTE: *Not validated:* reading or mounting a secret from Secrets Manager or Key Vault, which was not run on a cluster.

On ROSA, let the role from this exercise read one secret:

[source,bash]
----
cat > secret-read.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "secretsmanager:GetSecretValue",
    "Resource": "<secret-arn>"
  }]
}
EOF
----

[source,bash]
----
aws iam put-role-policy \
  --role-name "sample-app-$CLUSTER" \
  --policy-name secret-read \
  --policy-document file://secret-read.json
----

On ARO, give the managed identity from this exercise the Key Vault Secrets User role on a vault that uses the Azure RBAC permission model:

[source,bash]
----
az role assignment create \
  --role "Key Vault Secrets User" \
  --assignee-object-id "$PRINCIPAL_ID" \
  --assignee-principal-type ServicePrincipal \
  --scope <key-vault-resource-id>
----

To mount secrets as files on ROSA, https://docs.redhat.com/en/documentation/red_hat_openshift_service_on_aws/4/html/tutorials/cloud-experts-aws-secret-manager[Red Hat's tutorial] installs the open-source Secrets Store CSI driver and AWS provider with Helm and grants them the privileged SCC; the provider finds the IAM role through the same service account annotation.
On ARO, https://learn.microsoft.com/azure/openshift/howto-use-key-vault-secrets[Microsoft recommends] its Azure Arc Key Vault Secrets Provider extension over that Helm install; check its support status for ARO before you rely on it.
OpenShift's Secrets Store CSI Driver Operator is another route; check its support status on ROSA and on ARO first.

Use Amazon ECR.

[.validation]

Create a repository:

[source,bash]
----
aws ecr create-repository \
  --repository-name "sample-app-$CLUSTER" \
  --region "$AWS_REGION"
----

[source,bash]
----
export ECR="$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com"
----

Copy the sample application's image into it with `oc`, so you need no container engine on your workstation.
First, write ECR credentials to a file:

[source,bash]
----
ECR_PASSWORD=$(aws ecr get-login-password \
  --region "$AWS_REGION")
----

[source,bash]
----
oc registry login \
  --registry "$ECR" \
  --auth-basic "AWS:$ECR_PASSWORD" \
  --to ecr-auth.json
----

Copy the image, keeping both its amd64 and arm64 variants:

[source,bash]
----
oc image mirror \
  --registry-config ecr-auth.json \
  --keep-manifest-list=true \
  ghcr.io/shpwrck/ocp-cloud-workshop/sample-app:1.0 \
  "$ECR/sample-app-$CLUSTER:1.0"
----

Find the IAM role that the cluster's worker nodes use:

[source,bash]
----
export WORKER_ROLE=$(rosa describe cluster \
  --cluster "$CLUSTER" \
  --output json \
  | jq -r .aws.sts.instance_iam_roles.worker_role_arn \
  | sed 's|.*/||')
----

[source,bash]
----
echo "$WORKER_ROLE"
----

Let the nodes read from ECR, as EKS node roles do:

[source,bash]
----
aws iam attach-role-policy \
  --role-name "$WORKER_ROLE" \
  --policy-arn arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryReadOnly
----

Point the application at the ECR image:

[source,bash]
----
oc set image deployment/sample-app \
  --namespace sample-app \
  sample-app="$ECR/sample-app-$CLUSTER:1.0"
----

[source,bash]
----
oc rollout status deployment/sample-app \
  --namespace sample-app
----

[source,bash]
----
oc get pods \
  --namespace sample-app \
  --output 'custom-columns=NAME:.metadata.name,IMAGE:.status.containerStatuses[0].image'
----

The pod pulled from ECR without a pull secret: the kubelet on ROSA nodes gets ECR credentials from the worker role, as on EKS.

.EKS and AKS (reference only)
[%collapsible]
====
EKS node roles must carry ECR pull permissions, so pods pull from ECR in the same account with nothing more to configure.

AKS grants its kubelet identity the `AcrPull` role on a registry in one step, with no pull secret:

[source,bash]
----
az aks update \
  --resource-group <resource-group> \
  --name <cluster-name> \
  --attach-acr <registry-name>
----
====

The sample application now runs with cloud credentials and images from your own registries.
Module 3 exposes it outside the cluster.

== What Matters

* ROSA uses the IRSA mechanism only: the same service account annotation as IRSA on EKS, through the pod identity webhook the cluster already runs. EKS Pod Identity is not available.
* ARO workload identity works only on clusters created with managed identities, which became generally available in February 2026. There is no conversion from a service principal cluster. On ARO, pods also need the `azure.workload.identity/use: "true"` label.
* On ARO, EKS and AKS each cluster has its own OIDC issuer, so IAM trust policies and federated credentials name a specific cluster, and you update them when you replace the cluster. On EKS, Pod Identity avoids this.
* On ROSA the issuer belongs to the OIDC config, which several clusters can share, and then they share its signing key. A trust policy that checks only the service account then trusts it on every one of those clusters. Use one OIDC config per cluster when roles must stay cluster-scoped, and reuse a config when a replacement cluster should keep its trust policies.
* The webhook changes pods only when they are created. Annotate the service account first, then restart the workload.
* On ROSA, the worker IAM role is shared by every cluster created with the same account roles. A policy you attach to it applies to all of them. In production, attach a policy scoped to the repositories each cluster needs. ECR pull secrets also work, but ECR tokens expire after 12 hours.
* On ARO, ACR pulls use a pull secret per namespace, built from registry credentials you have to rotate. ACR repository-scoped tokens are a narrower alternative to the admin credentials.
* The platform's own Operators already use short-lived credentials on both ROSA (STS) and managed-identity ARO. Don't change their roles, role assignments or federated credentials.
* Neither ROSA nor ARO has a managed add-on that mounts AWS Secrets Manager or Azure Key Vault secrets into pods, as EKS and AKS do. Applications can read secrets with the cloud SDK through the pod identity from Exercise 1; mounting them as files needs a CSI driver you install, with privileged SCC grants, or the Azure Arc extension on ARO.

== Where Each Wins

[cols="1,1",options="header"]
|===
|ROSA and ARO win |EKS and AKS win

|ROSA and managed-identity ARO run each platform Operator on its own short-lived, least-privilege credentials; service-principal ARO clusters use a client secret you rotate.
|EKS Pod Identity needs no OIDC trust policy per cluster, and AKS Workload ID is one command on any cluster.

|ROSA uses the IRSA annotation unchanged, so EKS IRSA manifests carry over.
|Registry pulls need no pull secret on AKS (`--attach-acr`), and EKS node roles read ECR by default.

|Applications that read Secrets Manager or Key Vault with the cloud SDK carry over unchanged, on the same pod identity.
|EKS and AKS install the Secrets Manager and Key Vault CSI providers as managed add-ons; ROSA and ARO need a driver you install, or Azure Arc on ARO.
|===

== App Teams Will Notice

Nothing changes in application code if it already uses the AWS or Azure SDK default credential chain: the sample application uses boto3 and `DefaultAzureCredential` unchanged.
Image references to ECR or ACR keep working once the registry access above is in place.
OpenShift also has a built-in registry and ImageStreams, which track image tags and can redeploy an application when a tag changes; teams can ignore them and keep using ECR or ACR.

. An app team's Helm chart sets `runAsUser: 1000` and runs fine on EKS.
On OpenShift its pods never appear.
What do they see, and what do you tell them?
+
.Answer
[%collapsible]
====
No pods, and a `FailedCreate` event: 1000 is outside the namespace's user ID range, so admission rejects the pod, as in xref:module-02-workload-security.adoc#ex-module-02-workload-security-2[Workload Security Exercise 2].
Remove the fixed `runAsUser`, let OpenShift assign the user ID, and build the image so that group 0 can write where it needs to, as in xref:module-02-workload-security.adoc#ex-module-02-workload-security-3[Exercise 3].
Granting `anyuid` also works, but it gives up the isolation the range provides (xref:module-02-workload-security.adoc#ex-module-02-workload-security-4[Exercise 4]).

+
.Answer
[%collapsible]
====
Yes, for a while: OAuth access tokens they already hold stay valid for 24 hours by default, and their User and Identity objects stay.
Delete their OAuthAccessToken objects, User and Identity, and on ARO consider a shorter `accessTokenMaxAgeSeconds`, as xref:module-02-access-and-tenancy.adoc#_what_matters[Access and Tenancy] describes.
====

. A team wants its pods to read S3 or Blob Storage through the node's own identity, as they did on EKS before IRSA.
What do you tell them?
+
.Answer
[%collapsible]
====
Every pod on a node would share that identity.
Give the workload its own instead: an IAM role trusted for its service account on ROSA, or a managed identity with a federated credential on ARO, as in xref:module-02-cloud-credentials.adoc#ex-module-02-cloud-credentials-1[Exercise 1].
The role grants only what that application needs, and its credentials are short-lived.
On ROSA, also keep extra policies off the worker role: every cluster created with the same account roles shares it.
====
