= Pod Networking and Policy

[.validation]
NOTE: Validated on ROSA HCP 4.20 and 4.22 and ARO 4.21 in October 2026.
Steps and statements that were not checked on a live cluster carry a *Not validated* note.
The comparison tables and summaries come from vendor documentation.

With the Amazon VPC CNI and Azure CNI, pods can get addresses from your VPC or virtual network.
ROSA and ARO run OVN-Kubernetes as an overlay: pod addresses never appear in the VPC or virtual network, and traffic leaves the cluster from the node's address unless you assign an egress IP.
This section explains the packet path, then applies network policy at two levels: per project, and cluster-wide.

.Where pod addresses come from, what a database in the same network sees, and where filtering happens
image::module-03-packet-path.svg["Pod packet path with the Amazon VPC CNI, Azure CNI Overlay and OVN-Kubernetes",width=100%,link=self,window=_blank]

== On EKS and AKS

* EKS: pods take VPC addresses, can carry their own security groups, and you plan subnets around address exhaustion. Network policy is a VPC CNI feature you turn on. ClusterNetworkPolicy adds cluster-wide Admin and Baseline tiers (VPC CNI 1.21.1 or later, with network policy enabled), and Auto Mode adds DNS-based policies.
* AKS: choose Azure CNI, Azure CNI Overlay, or Azure CNI powered by Cilium, and a network policy engine.
* Private clusters: the EKS endpoint can switch between public and private at any time, and AKS offers private clusters and API Server VNet Integration.

== On ROSA and ARO

Do these steps on your cluster.
If you have both, finish them on ROSA, then repeat them on ARO.
Where the two differ, the steps are split into ROSA and ARO tabs.
They use the sample application in the `sample-app` project and the Route you created in xref:module-03-exposing-apps.adoc[Exposing an App].

=== Exercise 1: Compare Pod and Node Addresses

List the sample application's pods with their addresses and nodes:

[source,bash]
----
oc get pods \
  --namespace sample-app \
  --output wide
----

Then list the nodes with theirs:

[source,bash]
----
oc get nodes \
  --output wide
----

Pod addresses come from `10.128.0.0/14` by default, and node addresses from the VPC or virtual network.
Save both addresses for one of the sample application's pods:

[source,bash]
----
POD_IP=$(oc get pods \
  --namespace sample-app \
  --selector app.kubernetes.io/name=sample-app \
  --output jsonpath='{.items[0].status.podIP}')
----

[source,bash]
----
NODE_IP=$(oc get pods \
  --namespace sample-app \
  --selector app.kubernetes.io/name=sample-app \
  --output jsonpath='{.items[0].status.hostIP}')
----

Now look at the same split from the cloud side.
The VPC or virtual network knows the node's address, because it belongs to a network interface.
It does not know the pod's address, which belongs to none.
When the pod talks to a database in the same VPC or virtual network, the database sees the node's address, so security groups and firewall rules can tell nodes apart but not pods.

[tabs]
======
ROSA (AWS)::
+
--
Show the cluster's address ranges, in the `Machine CIDR`, `Service CIDR` and `Pod CIDR` lines:

[source,bash]
----
rosa describe cluster \
  --cluster "$CLUSTER"
----

Look up both addresses in the VPC.
The pod's address finds nothing, so its line is empty, and the node's address finds its network interface:

[source,bash]
----
for ip in "$POD_IP" "$NODE_IP"; do
  aws ec2 describe-network-interfaces \
    --filters "Name=addresses.private-ip-address,Values=$ip" \
    --query "NetworkInterfaces[].NetworkInterfaceId" \
    --output text
done
----
--
ARO (Azure)::
+
--
Show the cluster's address ranges:

[source,bash]
----
az aro show \
  --resource-group "$RESOURCE_GROUP" \
  --name "$CLUSTER" \
  --query networkProfile
----

Find the cluster's managed resource group, where its virtual machines and network interfaces live:

[source,bash]
----
MANAGED_RG=$(az aro show \
  --resource-group "$RESOURCE_GROUP" \
  --name "$CLUSTER" \
  --query clusterProfile.resourceGroupId \
  --output tsv)
----

List every private address in it.
The node's address is there, and the pod's is not:

[source,bash]
----
az network nic list \
  --resource-group "${MANAGED_RG##*/}" \
  --query "[].ipConfigurations[].privateIPAddress" \
  --output tsv
----
--

=== Exercise 2: Set Up a Test Client

Run a client pod in its own project, to test connections from outside the sample application's project:

[source,bash]
----
oc new-project net-client
----

[source,bash]
----
oc run client \
  --namespace net-client \
  --image registry.access.redhat.com/ubi9/ubi \
  --command -- sleep infinity
----

`oc run` prints a PodSecurity warning about the pod's security settings.
It is only a warning, and the pod starts.

[source,bash]
----
oc wait pod/client \
  --namespace net-client \
  --for=condition=Ready \
  --timeout=120s
----

Define a shell function that prints the HTTP status the client gets from a URL.
It prints `000` when the connection is blocked:

[source,bash]
----
probe() {
  oc exec client \
    --namespace net-client \
    -- curl \
    --silent \
    --output /dev/null \
    --write-out '%{http_code}\n' \
    --max-time 5 \
    "$1"
}
----

Save the Route's host name, for testing the path through the router from your workstation:

[source,bash]
----
ROUTE_HOST=$(oc get route sample-app \
  --namespace sample-app \
  --output jsonpath='{.spec.host}')
----

Both paths work, because nothing restricts traffic yet:

[source,bash]
----
probe http://sample-app.sample-app.svc:8080/healthz
----

[source,bash]
----
curl --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  "https://$ROUTE_HOST/healthz"
----

=== Exercise 3: Default-Deny the Sample Application's Project

NetworkPolicy works on ROSA and ARO with nothing to enable.
Deny all incoming traffic to every pod in the project:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: sample-app
spec:
  podSelector: {}
  policyTypes:
  - Ingress
EOF
----

Run both checks again.
The client now gets `000`, and the Route returns `503` or times out, because the router is just another source of traffic.
When the client is blocked, `oc` also prints `command terminated with exit code 28`, which is curl's timeout:

[source,bash]
----
probe http://sample-app.sample-app.svc:8080/healthz
----

[source,bash]
----
curl --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  --max-time 10 \
  "https://$ROUTE_HOST/healthz"
----

Allow the router, the user workload monitoring Prometheus (Module 4 scrapes the application's metrics) and pods in the same project.
OpenShift labels the router's namespace with a policy group, so the first rule selects that label instead of a namespace name:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-ingress
  namespace: sample-app
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          policy-group.network.openshift.io/ingress: ""
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-monitoring
  namespace: sample-app
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: openshift-user-workload-monitoring
    ports:
    - protocol: TCP
      port: 8080
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-namespace
  namespace: sample-app
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector: {}
EOF
----

The Route works again, and the client in `net-client` is still blocked:

[source,bash]
----
curl --silent \
  --output /dev/null \
  --write-out '%{http_code}\n' \
  "https://$ROUTE_HOST/healthz"
----

[source,bash]
----
probe http://sample-app.sample-app.svc:8080/healthz
----

Keep these policies.
The sample application keeps them for Module 4.

.EKS and AKS (reference only)
[%collapsible]
====
EKS: network policy is off until you turn it on in the VPC CNI add-on.

[source,bash]
----
aws eks update-addon \
  --cluster-name <cluster-name> \
  --addon-name vpc-cni \
  --configuration-values '{"enableNetworkPolicy":"true"}'
----

AKS: you pick the network plugin when you create the cluster (Azure CNI Overlay if you name none), for example an overlay with the Cilium dataplane.

[source,bash]
----
az aks create \
  --resource-group <resource-group> \
  --name <cluster-name> \
  --network-plugin azure \
  --network-plugin-mode overlay \
  --network-dataplane cilium
----

`az aks update --network-policy` adds or changes the policy engine later, and Azure CNI clusters can move to the Cilium dataplane.

The NetworkPolicy objects themselves are the same on all four platforms.
====

=== Exercise 4: Add a Cluster-Wide Guardrail

NetworkPolicy belongs to whoever administers the project.
An AdminNetworkPolicy belongs to the cluster administrator, and OVN-Kubernetes evaluates it before any NetworkPolicy:

.The three policy tiers
image::module-03-policy-tiers.svg["Order in which OVN-Kubernetes evaluates network policy tiers",width=100%,link=self,window=_blank]

Create a project that holds sensitive data, and label it:

[source,bash]
----
oc new-project restricted-data
----

[source,bash]
----
oc label namespace restricted-data \
  workshop.k8socp.com/sensitivity=high
----

Run a second copy of the sample application in it, as a stand-in for a service with sensitive data:

[source,bash]
----
oc create deployment records \
  --namespace restricted-data \
  --image ghcr.io/shpwrck/ocp-cloud-workshop/sample-app:1.0 \
  --port 8080
----

[source,bash]
----
oc expose deployment records \
  --namespace restricted-data \
  --port 8080
----

[source,bash]
----
oc rollout status deployment/records \
  --namespace restricted-data
----

The client can reach it, and gets `200`:

[source,bash]
----
probe http://records.restricted-data.svc:8080/healthz
----

Now apply a guardrail: only namespaces with the same label may connect to it.
The rules run in order, so the `Allow` rule comes before the `Deny` rule:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: policy.networking.k8s.io/v1alpha1
kind: AdminNetworkPolicy
metadata:
  name: protect-sensitive-data
spec:
  priority: 10
  subject:
    namespaces:
      matchLabels:
        workshop.k8socp.com/sensitivity: high
  ingress:
  - name: allow-same-sensitivity
    action: Allow
    from:
    - namespaces:
        matchLabels:
          workshop.k8socp.com/sensitivity: high
  - name: deny-all-other-namespaces
    action: Deny
    from:
    - namespaces: {}
EOF
----

[source,bash]
----
probe http://records.restricted-data.svc:8080/healthz
----

The client is blocked.
Now act as the project's administrator and try to open the project to everyone with a NetworkPolicy:

[source,bash]
----
oc apply --filename - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-everything
  namespace: restricted-data
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - {}
EOF
----

[source,bash]
----
probe http://records.restricted-data.svc:8080/healthz
----

The client is still blocked.
The AdminNetworkPolicy decided first, so no NetworkPolicy in the project can undo it.

Remove the guardrail and its project:

[source,bash]
----
oc delete adminnetworkpolicy protect-sensitive-data
----

[source,bash]
----
oc delete project restricted-data
----

=== Fixed Egress Addresses (Reference Only)

[.validation]
NOTE: *Not validated:* this section on ARO, where no exercise runs it.
On ROSA 4.22, the sample below was applied after a machine pool added the `k8s.ovn.org/egress-assignable` label to a node: OVN-Kubernetes added `10.0.1.200` to that node's network interface, an `m5.xlarge` reported room for 14 addresses, and a host in the VPC saw the sample application's connections come from `10.0.1.200`.

To give one project its own source address, OVN-Kubernetes offers egress IPs.
This workshop does not set one up, because the cloud constraints differ: on ROSA, you label the nodes that may host egress IPs through a machine pool, and capacity depends on the instance type; on ARO, namespace egress IPs need a cluster created with a private API, private ingress and user-defined routing, where you provide the egress path through a firewall or NAT.
Public ARO clusters, like the ones in this workshop, cannot use them, and the choice cannot be changed after the cluster is created.

An egress IP for the sample application's project looks like this:

[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: EgressIP
metadata:
  name: sample-app
spec:
  egressIPs:
  - 10.0.1.200
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: sample-app
----

=== Restricting Egress (Reference Only)

[.validation]
NOTE: *Not validated:* this section on ARO, where no exercise runs it.
On ROSA, the sample below was applied to a test project with `api.example.com` replaced by `checkip.amazonaws.com`: that host answered, another host timed out, and cluster DNS lookups still worked.

NetworkPolicy in this module controls incoming traffic.
To limit which destinations outside the cluster a project's pods can reach, by CIDR or by DNS name, OVN-Kubernetes offers the EgressFirewall.
A project has at most one, named `default`, and the first rule that matches a connection wins, so allow rules go before the final deny.
A deny for `0.0.0.0/0` also blocks the cluster's API servers, so pods that call the Kubernetes API need an allow rule for them, by address or with a `nodeSelector` rule.
Lookups through the cluster DNS service are not affected.
A `dnsName` rule follows the name by polling DNS at its TTL, so use it for hosts whose addresses rarely change.
Wildcard names depend on improved DNS resolution for egress firewall rules, which is a Technology Preview feature.

This egress firewall allows one external host and denies everything else:

[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: EgressFirewall
metadata:
  name: default
  namespace: <project>
spec:
  egress:
  - type: Allow
    to:
      dnsName: api.example.com
  - type: Deny
    to:
      cidrSelector: 0.0.0.0/0
----

== Private Clusters

On ARO, a private API and private ingress are install-time choices.
On ROSA, you can switch the API and the default ingress between public and private after creation, with `rosa edit cluster` and `rosa edit ingress`.
The ROSA OAuth server follows the API, so a private API also stops web console logins from outside the private network, even behind a public ingress.
On ROSA 4.22 the API stopped answering from outside within a minute of `rosa edit cluster --private`; the console page still loaded, but its sign-in redirect to the OAuth server timed out.
Switching back with `--private=false` brought the API back under the same name, but a resolver that had cached the missing name kept failing for longer.
There is no exercise for this, because a private API would cut your workstation off from the cluster.
What changes is where the control plane runs and how you, and the provider's SRE team, reach it:

ROSA workers always reach the hosted control plane over AWS PrivateLink, public cluster or not.
Switching the ROSA default ingress between public and private with `rosa edit ingress --private` replaces the router's load balancer and its DNS record, so every Route is unreachable for some minutes, and longer from a resolver that has cached the missing name.
ROSA also offers clusters with no internet egress at all (egress zero).

On ARO, egress lockdown (on by default for new clusters) carries the endpoints the service needs through the service itself, so your firewall only has to allow the optional ones, such as `registry.redhat.io`, `quay.io` and `api.openshift.com` for update checks.
The ARO support policy does not allow an HTTPS proxy in the path of the service's own traffic, such as Azure Resource Manager and service logging (Geneva).

== What Matters

* OVN-Kubernetes is the default and the only CNI Red Hat supports. ROSA can be created without a CNI, at create time only, so you can install your own, such as Cilium or Calico, with support from that vendor. ARO is OVN-Kubernetes only.
* Pod addresses never use VPC or virtual network space, so there is no subnet exhaustion from pods. The other side: anything outside the cluster sees node addresses, never pod addresses.
* NetworkPolicy works with nothing to enable. A default-deny policy also blocks the router and monitoring until you allow the router's policy group and the user workload monitoring namespace.
* AdminNetworkPolicy adds cluster-wide rules that project administrators cannot override. Keep its subjects away from `openshift-*` namespaces, which the platform and SRE need.
* Egress IPs give a project a fixed source address, with cloud-specific limits: on AWS the capacity depends on the instance type, and on ARO namespace egress IPs need a private cluster created with user-defined routing. Public ARO clusters cannot use them.
* An EgressFirewall, one per project, limits which destinations outside the cluster its pods can reach, by CIDR or by DNS name. DNS-name rules follow a host's addresses only as often as its TTL, so they suit hosts whose addresses rarely change.
* On ARO, a private API and private ingress are install-time choices. On ROSA, both can be switched later, and a private API also stops web console logins from outside the private network. ROSA workers always reach the hosted control plane over AWS PrivateLink.

== Where Each Wins

[cols="1,1",options="header"]
|===
|ROSA and ARO win |EKS and AKS win

|No pod address planning in your VPC or virtual network (as on Azure CNI Overlay, the AKS default; unlike the VPC CNI).
|With the VPC CNI or an Azure CNI pod subnet, pods are first-class network citizens: routable addresses, security groups for pods (EKS), flow logs by pod address.

|NetworkPolicy, AdminNetworkPolicy and BaselineAdminNetworkPolicy on by default, nothing to enable; a built-in per-project egress firewall by CIDR or DNS name; egress IPs built in (on ARO, only on private clusters with user-defined routing).
|Cilium on AKS adds an eBPF dataplane and, with Advanced Container Networking Services, L7 policy and FQDN policy through a DNS proxy that tracks address changes. EKS Auto Mode adds DNS-based policies.

|A supported private pattern that keeps SRE access working.
|Endpoint visibility can change after the cluster is created, where ARO fixes it at install.
|===

== App Teams Will Notice

* A new project allows all traffic until someone adds policy. If the cluster's project template adds a default-deny policy, their Route returns `503` until they allow the router.
* Databases and APIs outside the cluster see node addresses. Allow-lists that expect a pod or per-app address need an egress IP; on a public ARO cluster, allow-list the cluster's outbound addresses instead.
* Service names resolve the same way as on EKS and AKS: `<service>.<project>.svc`.
* Cluster-wide policies written as EKS ClusterNetworkPolicy must be rewritten as AdminNetworkPolicy or BaselineAdminNetworkPolicy, because the APIs differ.

== Check Your Understanding

These questions cover the whole module.
Try each one before you open its answer.

. A team moves an app from EKS with an Ingress that sets `ingressClassName: alb` and ALB annotations.
On ROSA nothing serves it.
Why, and what are their options?
+
.Answer
[%collapsible]
====
OpenShift turns an Ingress into a Route only when it has no `ingressClassName` or uses `openshift-default`, so an `alb` Ingress is ignored, and ALB annotations do nothing on the router.
Drop the class and use `haproxy.router.openshift.io/*` annotations or a Route, as in xref:module-03-exposing-apps.adoc#ex-module-03-exposing-apps-3[Exposing an App Exercise 3].
If they need an ALB, add the AWS Load Balancer Operator.
====

. Your database team allow-listed pod addresses for an app on EKS with the VPC CNI.
After the move, the database sees a different source address.
What does it see now, and what do you give them?
+
.Answer
[%collapsible]
====
The node's address: pod addresses stay inside the OVN-Kubernetes overlay, as xref:module-03-pod-networking.adoc#ex-module-03-pod-networking-1[Exercise 1] showed.
Allow the worker subnets, or give the project its own source address with an egress IP, whose setup differs by cloud (xref:module-03-pod-networking.adoc#_fixed_egress_addresses_reference_only[Fixed Egress Addresses]).
====

. Your security team wants a rule that no project can override, such as always letting monitoring reach every namespace.
Which policy do you use?
+
.Answer
[%collapsible]
====
An AdminNetworkPolicy, as in xref:module-03-pod-networking.adoc#ex-module-03-pod-networking-4[Exercise 4].
Cluster administrators create it, and OVN-Kubernetes evaluates it before any NetworkPolicy, so a project's own policies cannot override its Allow and Deny rules.
For a default that projects may override, use the BaselineAdminNetworkPolicy, which is evaluated last.
====
